1Database design and the ER model

1.1 Why a design step at all?

Before tables are created someone has to decide which tables, which columns and which keys. If you jump straight to tables you usually get redundancy (the same fact stored many times), missing information (no place to record something the users need) and update problems. Database design is therefore done in phases (figure above):

  1. Requirements collection and analysis — talk to users; list the data to be stored and the operations (transactions) to be run on it.
  2. Conceptual design — describe the data at a high level, independent of any DBMS, using a conceptual data model. The usual model is the Entity–Relationship (ER) model. Output: an ER diagram (the conceptual schema).
  3. Logical design (data-model mapping) — convert the ER schema into the data model of the chosen DBMS: for an RDBMS, into relational tables with primary and foreign keys (section 8).
  4. Schema refinement — check the tables with functional dependencies and normalize them (Unit 4).
  5. Physical design — storage structures, indexes, partitioning, tuning.

1.2 Top-down vs bottom-up design

Top-down approach

Start with the whole enterprise (the “mini-world”), identify the high-level entity types and relationships, then successively refine them: add attributes, split entity types into subclasses (specialization), add constraints.

The ER model is a top-down method: you begin with concepts like STUDENT, COURSE, ENROLS and then detail them.

Bottom-up approach

Start with the basic data items (attributes, existing forms/reports) and combine them into entity types and relationships; group similar entity types into a more general one (generalization).

Normalization (Unit 4) is a bottom-up method: it starts from a universal set of attributes and FDs.

In practice designers mix both (sometimes called inside-out or mixed strategy). The syllabus names the ER model as the top-down approach.

1.3 The ER model in one paragraph

Definition

The Entity–Relationship (ER) model, proposed by Peter Chen (1976), is a high-level conceptual data model that describes the mini-world as a collection of entities (things), their attributes (properties) and the relationships among them, together with constraints such as keys, cardinality ratios and participation. It is drawn as an ER diagram.

Why it is used (course notes, p. 42): it gives a simple, easy-to-understand picture of the data that non-technical users can check; it is independent of any DBMS; and it maps almost mechanically to relational tables.

Three building blocks

Entity (rectangle) — Attribute (ellipse) — Relationship (diamond). The Enhanced/Extended ER (EER) model adds specialization, generalization, categories and aggregation (section 6).

2Entities and attributes

2.1 Entity, entity type, entity set

Definitions
  • Entity — a thing or object in the real world that is distinguishable from all other objects; it may be physical (a student, a car) or conceptual (a course, a loan, a job).
  • Entity type — the description (schema) of a collection of entities that have the same attributes, e.g. STUDENT(roll_no, name, dob). Drawn as a rectangle.
  • Entity set (extension) — the collection of all entities of that type at a particular moment, e.g. the 600 students currently enrolled.

The entity type is like the column headings of a table; the entity set is like the rows present right now. Many books (and exam papers) use “entity set” for both; that is acceptable in answers.

2.2 Attributes and their types

An attribute is a property that describes an entity (or a relationship). Each attribute has a domain (value set): the set of values it may take, e.g. age ∈ integers 16–40. Attributes are drawn as ellipses joined to their entity.

Composite vs simple — how to decide

Make an attribute composite when users sometimes need the whole value and sometimes the parts (search by city, print the full address). If the parts are never used separately, keep it simple.

Derived — why draw it at all?

It documents that users need the value, but it is not stored in the table (it would go stale: age changes every year). It is computed in a query or a view: age = YEAR(CURRENT_DATE) − YEAR(dob).

NULL values appear when an attribute is not applicable (apartment_no for a house) or unknown (phone not given). They are allowed for non-key attributes.

2.3 Keys of an entity type

Key attribute

An attribute (or set of attributes) whose values are distinct for every entity in the entity set, so it can identify each entity uniquely. Shown by underlining. An entity type may have more than one key (e.g. roll_no and email); one is chosen as the primary key.

  • A composite key is shown by underlining a composite attribute, e.g. registration(state, number) for a vehicle.
  • An entity type with no key of its own is a weak entity type (section 5).
  • Super key, candidate key, primary key and alternate key were done in Unit 2; the same meanings apply here.
Correction to the course notes (p. 46)

The course notes say a key attribute “represents the main characteristics of an entity”. More precisely, a key is what uniquely identifies each entity. Being “important” has nothing to do with it: name is an important attribute but it is not a key.

3Relationship types, relationship sets and roles

3.1 Relationship, relationship type, relationship set

Definitions
  • Relationship (instance) — an association among two or more entities, e.g. “Asha works for the Sales department”.
  • Relationship type R among entity types E1, …, En — the schema of a set of similar associations, e.g. WORKS_FOR between EMPLOYEE and DEPARTMENT. Drawn as a diamond joined by lines to the participating entity types.
  • Relationship set — the set of relationship instances of that type at a given moment. Mathematically it is a subset of the Cartesian product E1 × E2 × … × En; each instance ri = (e1, …, en) takes exactly one entity from each participating set.
EMPLOYEE(emp_id, name, dept_id, since)+ WORKS_FOR
FK dept_id → DEPARTMENT(dept_id)
DEPARTMENT(dept_id, dname)
2 tables  ·  underlined = primary key, purple italic = foreign key

Because a relationship set is a set, the same combination of entities cannot appear twice. If an employee could work for the same department in two separate periods and both must be recorded, the relationship alone cannot hold that: model a separate entity (e.g. ASSIGNMENT) instead.

3.3 Roles and recursive relationships

Role name

Each entity type that participates in a relationship plays a particular role in it, written as a label on the connecting line. Role names are optional when the entity types are different (the role is obvious). They are essential in a recursive relationship, where the same entity type participates more than once in different roles.

EMPLOYEE(emp_id, name, supervisor_emp_id)+ SUPERVISES
FK supervisor_emp_id → EMPLOYEE(emp_id)
1 table  ·  underlined = primary key, purple italic = foreign key

Without role names you could not tell, for the instance (e1, e7), who supervises whom. When converted to a table the roles become column names: supervisor_emp_id.

3.4 Attributes of relationship types

A relationship can have its own attributes: since on WORKS_FOR, hours on WORKS_ON, grade on ENROLS. Such an attribute describes the combination, not either entity.

Where can a relationship attribute be moved?
  • 1:1 — the attribute can be moved to either entity type.
  • 1:N — it can be moved only to the N-side entity. since of WORKS_FOR (N employees : 1 department) can become an attribute of EMPLOYEE, because each employee has only one “since”.
  • M:N — it cannot be moved; it depends on both entities together. grade belongs to (student, course), not to either alone.
This is exactly what happens in the table conversion (section 8): the attribute goes wherever the foreign key goes.
Exam phrasing to recognise

“Each instructor teaches a course in a semester” → the semester is an attribute of TEACHES. “Record the grade each student received” → grade is an attribute of ENROLS / TAKES. “The date on which the employee joined the department” → attribute of WORKS_FOR.

4Structural constraints: cardinality and participation

A relationship type usually has rules that limit which combinations of entities may appear in its relationship set. The two kinds of rule together are called the structural constraints of the relationship:

  1. the cardinality ratio (mapping cardinality): the maximum number of relationship instances an entity can take part in;
  2. the participation constraint: the minimum — must every entity take part, or may some stay out?

4.1 Cardinality ratio (mapping cardinality)

Definition

The cardinality ratio of a binary relationship type specifies the maximum number of relationship instances in which an entity can participate, i.e. the number of entities of one set to which an entity of the other set can be associated. The possible ratios are 1:1, 1:N, N:1 and M:N.

RatioMeaning (read both directions!)Example
1 : 1an E1 is related to at most one E2, and an E2 to at most one E1EMPLOYEE manages DEPARTMENT; PERSON holds PASSPORT
1 : Nan E1 to many E2, but an E2 to at most one E1DEPARTMENT has EMPLOYEES; SCIENTIST invents INVENTIONS (course p. 49)
N : 1the same as 1:N, read from the other sideSTUDENT enrols in (one) COURSE (course p. 49)
M : Nan E1 to many E2 and an E2 to many E1EMPLOYEE works on PROJECT; STUDENT takes COURSE
How to find the ratio from an English sentence

Ask two questions: “one A can have how many B?” and “one B can have how many A?”. Write the answer to the first question next to B and the answer to the second next to A.

“A department has many employees; an employee works in only one department” → N next to EMPLOYEE, 1 next to DEPARTMENT → DEPARTMENT 1 — WORKS_FOR — N EMPLOYEE.

Significance of cardinality (asked as “explain its significance”)
  • It records a business rule (“an employee works in only one department”) that the database must enforce.
  • It decides the table design: 1:N → foreign key on the N side, no extra table; M:N → a separate table; 1:1 → foreign key on either side, or merge (section 8). A wrong ratio gives either redundant tables or a schema that cannot store valid data.
  • It fixes the keys of relationship tables and so prevents invalid data (a second department for the same employee is rejected by the PK/UNIQUE).
  • It helps query writers know whether a join returns one row or many.

4.2 Participation constraint

Definition

The participation constraint specifies whether the existence of an entity depends on its being related to another entity through the relationship, i.e. the minimum number of relationship instances each entity must take part in.

  • Total participation (existence dependency): every entity of the set must participate in at least one relationship instance. Drawn as a double line.
  • Partial participation: some entities may not participate. Drawn as a single line.
EMPLOYEE(emp_id, name)
DEPARTMENT(dept_id, dname, emp_id, start_date)+ MANAGES
FK emp_id → EMPLOYEE(emp_id) · UNIQUE(emp_id) · NOT NULL(emp_id)
2 tables  ·  underlined = primary key, purple italic = foreign key
Words that signal participation

Total: “every”, “each … must”, “cannot exist without”, “is always”, “at least one”. Partial: “may”, “some”, “may or may not”, “optionally”, “can have”.

Summer mid-sem example: “Every patient must undergo treatment” → PATIENT total; “a department may or may not have doctors” → DEPARTMENT partial.

4.3 (min, max) notation

Cardinality ratio and participation can be written together as a pair (min, max) on each line, with 0 ≤ min ≤ max and max ≥ 1.

Meaning

(min, max) on the line between entity type E and relationship R means: each entity e of E takes part in at least min and at most max relationship instances of R. min = 0 ⇒ partial participation; min ≥ 1 ⇒ total participation. max = 1 ⇒ e is related to at most one other entity.

Common mistake — the numbers sit on opposite sides

In the 1/N notation the N of WORKS_FOR is written next to EMPLOYEE (many employees per department). In (min,max) notation EMPLOYEE gets (1,1), because each employee takes part in exactly one WORKS_FOR, and DEPARTMENT gets (1,N). So to convert, swap sides: max next to E in (min,max) = the ratio label written next to the other entity.

Rule that works for both arrow styles

Look at where the arrowhead touches. Touching an entity (Korth) → that entity is the “1” side. Touching a diamond (Ramakrishnan) → the entity at the tail is the “many” side (each of its entities has at most one partner). Either way, in the 2023 diagram “A → R1 — B” means each A has at most one B, so A gets B’s key as a foreign key. If a diagram mixes styles or has no marks, state your assumption — the paper explicitly allows “missing data may be suitably assumed”.

4.5 Constraints on ternary relationships

For a relationship of degree 3 or more, the label next to an entity says how many of that entity can be associated with one fixed combination of the other entities.

  • Fix (course, student): at most 1 instructor (the “1”) — a student takes a given course from one instructor.
  • Fix (instructor, student): many courses (N) — one instructor may teach the same student several courses.
  • Fix (instructor, course): many students (M) — a class has many students.
  • Consequence for tables: the key of TEACHES is made of the keys of the non-“1” sides: (course_id, student_id). Section 8, rule 9.
(min,max) on ternary relationships is different

(min,max) next to E in a ternary relationship counts how many instances each single entity e takes part in, not per pair. The two notations are not interchangeable for n-ary relationships — say which one you are using.

4.6 Ternary relationship vs three binary relationships

Can SUPPLY(supplier, part, project) be replaced by three binary relationships CAN_SUPPLY(s,p), USES(p,j), SUPPLIES(s,j)? In general, no.

  • The ternary relationship stores which supplier supplied which part to which project. The binaries store only “S1 can supply P1”, “J1 uses P1”, “S1 supplies something to J1”; combining them may claim a triple that never happened.
  • The binaries may still be useful in addition (e.g. CAN_SUPPLY records suppliers who are able to supply a part even if no project has ordered it).
  • Some ternaries can be replaced: if the relationship is really two independent facts, or by turning the ternary into a (weak) entity with three binary identifying relationships — this is how ternaries are represented in models that only allow binary relationships (UML, crow’s-foot).

5Weak entity types

5.1 Definition and notation

Definitions
  • A strong (regular) entity type has a key attribute of its own.
  • A weak entity type does not have a key attribute of its own. Its entities are identified by being related to specific entities of another entity type, called the identifying (owner) entity type, in combination with some of their own attribute values.
  • The relationship linking a weak entity type to its owner is the identifying relationship.
  • The partial key (or discriminator) is the set of attributes that uniquely identifies weak entities that are related to the same owner entity.
  • Key of a weak entity = primary key of the owner + partial key.

Notation: weak entity type = double rectangle; identifying relationship = double diamond; partial key = dashed underline; the weak entity always has total participation (double line) in the identifying relationship.

LOAN(loan_no, amount)
PAYMENT(loan_no, payment_no, pay_date, pay_amount)+ LOAN_PAYMENT
FK loan_no → LOAN(loan_no) on delete cascade
2 tables  ·  underlined = primary key, purple italic = foreign key

5.2 Properties you must state in an answer

  1. A weak entity cannot exist without its owner (existence dependency) — hence total participation in the identifying relationship. Deleting the owner deletes its weak entities (ON DELETE CASCADE).
  2. The identifying relationship is usually 1 : N from owner to weak entity (one loan, many payments). It can also be 1:1.
  3. The weak entity has a partial key but no full key; its key in the table is (owner key, partial key).
  4. Total participation alone does not make an entity weak: an EMPLOYEE that must work for a DEPARTMENT is still strong because emp_id identifies it. Weak = no key of its own.
  5. A weak entity type can own another weak entity type (BUILDING → FLOOR → ROOM, practice question P1).

5.4 Why have weak entity types at all?

One could always make a weak entity strong by adding a globally unique attribute (payment_id = loan_no + payment_no, or a serial number). We still use weak entities because:

  • It is the natural model: a dependent named “Riya” is meaningful only as a dependent of a particular employee; a room number “101” only inside a building.
  • Adding the owner’s key as an attribute of the weak entity would store it twice (in the entity and in the relationship), which is redundant and can become inconsistent.
  • An artificial id adds a meaningless attribute and an extra uniqueness rule to maintain.
  • It captures the existence dependency explicitly: deleting the owner must delete the dependants (cascade).
  • Specifying the weak entity tells the designer exactly how the key will be formed when converting to tables.

5.5 Can an identifying relationship have degree greater than two?

Yes. A weak entity can be identified by more than one owner; the identifying relationship then has degree 3 or more and the key of the weak entity is the keys of all owners + the partial key.

APPLICANT(app_id, name)
COMPANY(cname, city)
INTERVIEW(app_id, cname, int_date, result)+ INTERVIEWS
FK app_id → APPLICANT(app_id) on delete cascade · FK cname → COMPANY(cname) on delete cascade
3 tables  ·  underlined = primary key, purple italic = foreign key

Other examples: a weak entity EXAM_SLOT identified by (COURSE, SEMESTER, slot_no); a SHIPMENT_LINE identified by (ORDER, WAREHOUSE, line_no).

6Extended ER: specialization, generalization, aggregation

The basic ER model cannot say “a SECRETARY is a kind of EMPLOYEE with extra attributes” or “a manager monitors an assignment (an employee–project pair)”. The Enhanced (Extended) ER model — EER adds superclass/subclass relationships, specialization, generalization, categories and aggregation.

6.1 Superclass, subclass and the IS-A relationship

Definitions
  • A subclass is a subset of the entities of an entity type that need to be represented separately (they have extra attributes or relationships). The entity type is their superclass. The link is the IS-A (ISA) relationship: “a SECRETARY is an EMPLOYEE”.
  • An entity of a subclass is the same real-world entity as in the superclass, just playing a specialised role. It is not a different object.
  • Attribute inheritance: a subclass entity inherits all attributes and all relationships of its superclass and may have its own specific (local) attributes and relationships.

Notation (Korth / course notes): an ISA triangle; the superclass is joined to the triangle, the subclasses hang below. Elmasri uses a circle with d (disjoint) or o (overlapping) and a ⊂ symbol on each subclass line. Write the constraints next to the triangle, as done here.

6.2 Specialization (top-down)

Definition

Specialization is the top-down process of defining a set of subclasses of an entity type, based on some distinguishing characteristic of its entities. One higher-level entity type is broken into lower-level entity types.

EMPLOYEE(emp_id, name, salary)
SECRETARY(emp_id, typing_speed)
FK emp_id → EMPLOYEE(emp_id) on delete cascade
TECHNICIAN(emp_id, tgrade)
FK emp_id → EMPLOYEE(emp_id) on delete cascade
ENGINEER(emp_id, eng_type)
FK emp_id → EMPLOYEE(emp_id) on delete cascade
4 tables  ·  underlined = primary key, purple italic = foreign key

Why specialize? (1) attributes such as typing_speed apply only to some entities — without subclasses they would be NULL for everyone else; (2) some relationships apply only to a subclass (only ENGINEERs belong to a TRADE_UNION).

6.3 Generalization (bottom-up)

Definition

Generalization is the bottom-up process of combining several entity types that share common attributes into a single higher-level (generalized) entity type. The common attributes move up to the superclass; the original types become its subclasses.

6.4 Constraints on specialization / generalization

Disjointness constraint

Disjoint — an entity can belong to at most one subclass (an employee is a secretary or a technician or an engineer).

Overlapping — an entity may belong to more than one subclass (a PERSON can be both an EMPLOYEE and a STUDENT — e.g. a teaching assistant).

Completeness (participation) constraint

Total — every superclass entity must belong to at least one subclass. Drawn as a double line from the superclass.

Partial — a superclass entity may belong to no subclass (an employee who is a manager or accountant is none of the three).

Two more terms
  • Predicate-defined (condition-defined) subclass: membership decided by a condition on a superclass attribute, e.g. job_type = 'Engineer' (attribute-defined specialization). User-defined: the user decides membership entity by entity.
  • Hierarchy vs lattice: in a specialization hierarchy every subclass has one superclass. In a lattice a subclass can have several superclasses (multiple inheritance) — a shared subclass, e.g. ENGINEERING_MANAGER is both an ENGINEER and a MANAGER.
  • Insertion/deletion rules: deleting a superclass entity deletes it from all subclasses; inserting into a superclass with a predicate-defined specialization automatically places it in the matching subclasses.

6.5 Aggregation

Definition

Aggregation is an abstraction in which a relationship (together with its participating entities) is treated as a higher-level entity, so that it can itself participate in another relationship. The basic ER model cannot express relationships among relationships; aggregation removes this limitation. Drawn as a box around the relationship and its entities.

6.6 Composition vs aggregation beyond syllabus

6.7 Categories (union types) beyond syllabus

Sometimes a subclass has several different superclasses and each of its entities belongs to exactly one of them: an OWNER of a vehicle is either a PERSON or a BANK or a COMPANY. 7Drawing an ER diagram from a problem statement

Every end-sem has a 5-mark “design an ER diagram for …” question. The marks go to: correct entities and keys, correct relationships with cardinality and participation, weak entities and special attributes where the story demands them, and a clean diagram with stated assumptions.

7.1 The step method

  1. Underline the nouns in the story. Nouns that have their own properties and many instances become entity types (STUDENT, COURSE). Nouns that only describe something become attributes (name, colour).
  2. Find the key of every entity. If none exists naturally and the entity only makes sense inside another one (a dependent, an instalment, a room in a building, a section of a course), make it a weak entity with a partial key.
  3. Classify attributes: composite (name, address), multivalued (phones, qualifications, emails), derived (age, number_enrolled, total amount). Questions often list them on purpose (“the qualification attribute is multivalued”).
  4. Underline the verbs linking two or more nouns: these are relationship types (teaches, enrols, books). Give each a verb name.
  5. For every relationship decide the cardinality (ask the two “one A has how many B?” questions) and the participation of each side (“every”, “must” → total).
  6. Attach relationship attributes (grade, date, quantity) to the diamond. Decide whether any relationship needs to be ternary, or whether a relationship itself takes part in another (aggregation).
  7. Look for is-a phrases (“some users also act as drivers”, “doctors are permanent, resident or visiting”) → specialization with its disjoint/overlap and total/partial constraints.
  8. Write the assumptions you made, then draw neatly: entities in a row/column, relationships between them, attributes outside, no crossing lines.

Example: Manager — separate entity, attribute, or role?

“Every employee has a manager, but a manager is also an employee” (Mid-Sem 2026). A manager has everything an employee has (id, name, salary), so a separate MANAGER entity would duplicate data. 7.3 Common mistakes

Lose-marks list
  • Putting a foreign key as an attribute in the ER diagram (dept_id inside EMPLOYEE). In ER, links are shown only by relationships; foreign keys appear only after mapping.
  • Forgetting keys, or underlining a non-unique attribute (name).
  • Drawing a weak entity without a double diamond, a partial key or total participation.
  • Writing the cardinality labels on the wrong side (see the tip in 4.1), or mixing notations in one diagram.
  • Making every relationship M:N “to be safe”. The question usually tells you the ratio; read it twice.
  • Relationship names that are nouns (EMPLOYEE–DEPARTMENT); use verbs (WORKS_FOR).
  • Attaching a relationship to an attribute, or an attribute to two entities.
  • Ignoring “minimum number of tables” in the conversion part.

8.3 Rule 3 — multivalued attributes

A multivalued attribute becomes a separate table containing the key of the entity (as a foreign key) and the attribute; the primary key is the combination of both. The entity’s own table keeps the remaining attributes (your class notes: “entity key + MV attribute in a separate table”).

2 tables  ·  underlined = primary key, purple italic = foreign key
Why a separate table? (End-Sem 2024 Q3(b)(i))

A relational column must hold one atomic value (first normal form). Putting several numbers in one cell (“98…, 97…”) breaks 1NF and makes searching or updating a single number impossible. Making columns mobile1, mobile2, mobile3 wastes space, gives NULLs and still limits the count. Repeating the whole student row once per number duplicates name and gender (update anomalies). A separate table STUDENT_mobile_no(roll_no, mobile_no) stores any number of values with no redundancy. Full answer in section 12.

2 tables  ·  underlined = primary key, purple italic = foreign key

Derived attributes are not stored at all (age in section 2) — they are computed in queries or views.

8.13 The whole algorithm on one page

ER → relational, in order
  1. Strong entity → table; composite → components; multivalued → separate table (key + value); derived → not stored.
  2. Weak entity → table with owner key + partial key as PK; owner key is FK with ON DELETE CASCADE; identifying relationship merged.
  3. Binary 1:1 → FK (UNIQUE) in the total side (either side if both partial); merge both tables if both sides total.
  4. Binary 1:N → FK in the N side (NOT NULL if N side total); relationship attributes go with it.
  5. Binary M:N → new table (key1, key2, attributes), PK = key1 + key2.
  6. Recursive → same as above with role-named keys.
  7. n-ary → new table with all keys; PK = keys of the non-“1” sides.
  8. Specialization → option (a)/(b)/(c)/(d).
  9. Aggregation → relationships on the aggregate use the aggregated relationship’s key.

9“Minimum number of tables” — method and class-notes questions

Papers say “convert into relational schema with the minimum number of tables”. This means: apply the merging rules of section 8 wherever they are allowed (1:N, 1:1, weak entities) and create separate tables only where they are unavoidable.

9.1 Counting rule

Minimum tables =

(number of strong entity types) + (number of weak entity types) + (number of M:N relationships) + (number of n-ary relationships, n ≥ 3) + (number of multivalued attributes) − (number of 1:1 relationships with total participation on both sides).

1:N, N:1, 1:1 (not total both) and identifying relationships add nothing. Recursive M:N adds one; recursive 1:N adds nothing. Specialization: + one table per subclass with option (a), or replace the superclass with the subclasses in option (b).

Traps
  • Participation never removes an M:N table (drill D5 below). Only 1:1 total-both reduces the count.
  • A chain of 1:N relationships still needs one table per entity (D4). Entities are never merged through 1:N.
  • A multivalued attribute always costs one extra table, even on a weak entity or a relationship.
  • Merging two entities through 1:1 total-both does not stop other relationships from referring to either key (D2).

Take STUDENT(roll_no, name, gender) with a multivalued attribute mobile_no (a student may have several numbers).

Why it cannot stay in the STUDENT table:

A weak entity set is an entity set that does not have a primary key of its own. 12.3 Specialization, generalization, aggregation, roles

End-Sem 2025Q3(b)(ii)2 marks

Define the concept of aggregation. Give two examples of where this concept is useful.

Show answer

Aggregation is an abstraction through which a relationship set, together with its participating entity sets, is treated as a higher-level entity set, so that it can participate in another relationship. It is needed because the ER model cannot express relationships among relationships. It is drawn as a box around the relationship and its entities.

Example 1: EMPLOYEE works on PROJECT; a MANAGER monitors each (employee, project) assignment.

Example 2: a coaching CENTER offers a COURSE; a VISITOR enquires about a particular course at a particular centre (course notes p. 59). Other uses: a guarantor for a (customer, account) holding; an advisor who approves a (student, course) registration.

Without aggregation a ternary relationship would repeat every (employee, project) pair and could record monitoring of a pair that does not exist in WORKS_ON.

End-Sem 2024Q3(b)(ii)2.5 marks

Explain generalization, specialization and aggregation with the help of overlap and disjoint set examples.

Show answer

Specialization (top-down): defining subclasses of an entity type based on distinguishing characteristics; subclasses inherit all attributes of the superclass and add their own. Disjoint example: EMPLOYEE → SECRETARY, TECHNICIAN, ENGINEER — an employee belongs to at most one.

Generalization (bottom-up): combining entity types with common attributes into a higher-level entity type. Overlapping example: EMPLOYEE and STUDENT generalized to PERSON — a teaching assistant is both.

Disjoint = an entity in at most one subclass; overlapping = an entity may be in several. (Completeness: total = every superclass entity in some subclass; partial = not necessarily.)

Aggregation: treating a relationship with its entities as an entity so it can take part in another relationship — e.g. MANAGER monitors (EMPLOYEE works_on PROJECT), diagram in the previous answer.

Practice P7true / false with reason5 × 1 mark
  1. An entity type with total participation in a relationship must be a weak entity type.
  2. A 1:1 relationship never needs a separate table.
  3. An M:N relationship with total participation on both sides can be merged into one of the entity tables.
  4. For an overlapping, partial specialization, the “subclass tables only” mapping is correct.
  5. A relationship attribute of a 1:N relationship can be placed in the entity on the “1” side.
Show answer
  1. False. Weak means no key of its own. EMPLOYEE may be total in WORKS_FOR and still has emp_id.
  2. True in the standard mapping — the FK goes into one side (or the tables merge). (A separate table is allowed when both sides are partial and you want to avoid NULLs, but it is not needed.)
  3. False. Each entity can still be related to many of the other; one cell cannot hold several keys. M:N always needs its own table.
  4. False. Partial: superclass entities in no subclass would be lost. Overlapping: inherited data would be duplicated in several tables.
  5. False. Each “1”-side entity relates to many N-side entities, so it would need many values. Only the N side has one value.
Last-day checklist for an ER question
  1. Every entity has a key (or is weak with a partial key and double diamond).
  2. Every relationship has cardinality on both sides and the right participation lines.
  3. Special attributes are marked (composite, multivalued, derived) — the question usually names them.
  4. Assumptions are written in a box before the diagram.
  5. For “minimum tables”: merge 1:N and 1:1, keep M:N, n-ary and multivalued tables, merge 1:1 total-both; count and state the total.
