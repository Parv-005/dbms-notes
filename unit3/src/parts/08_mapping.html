8Transforming an ER schema into relational tables

This is the “logical design” step. The rules below are the ones in your class notes (rules 1–7) plus the cases the papers also ask about (recursive, ternary, specialization, aggregation). Each rule shows the ER fragment, the tables produced (computed by the rule program, see section 0), and — for some — the SQL.

Reading the schemas

8.1 Rule 1 — strong entity with simple attributes

Make one table per strong entity type; each simple attribute becomes a column; the key attribute becomes the primary key.

8.2 Rule 2 — composite attributes

Store only the component (leaf) attributes as columns; the composite name itself disappears.

{{er:r2}}{{map:r2}}

8.3 Rule 3 — multivalued attributes

A multivalued attribute becomes a separate table containing the key of the entity (as a foreign key) and the attribute; the primary key is the combination of both. The entity’s own table keeps the remaining attributes (your class notes: “entity key + MV attribute in a separate table”).

{{er:r3}}{{map:r3}}
Why a separate table? (End-Sem 2024 Q3(b)(i))

A relational column must hold one atomic value (first normal form). Putting several numbers in one cell (“98…, 97…”) breaks 1NF and makes searching or updating a single number impossible. Making columns mobile1, mobile2, mobile3 wastes space, gives NULLs and still limits the count. Repeating the whole student row once per number duplicates name and gender (update anomalies). A separate table STUDENT_mobile_no(roll_no, mobile_no) stores any number of values with no redundancy. Full answer in section 12.

8.4 Rule 4 — M:N relationship

Create a separate table for the relationship containing the primary keys of both participating entities (as foreign keys) plus the relationship’s own attributes. Its primary key is the combination of the two foreign keys.

8.5 Rule 5 — 1:N, N:1 and 1:1 relationships (no separate table)

Class notes: “when m:1 or 1:n, no separate table for R is to be made”. Instead, put the primary key of the “1” side as a foreign key into the table of the “N” side, together with the relationship’s attributes. The FK and the N-side table are written as one table, e.g. BR.

Why the N side and never the 1 side?

Each B has one A, so one column in B is enough. If we put b-keys into A instead, an A with five B’s would need five values in one cell — impossible.

1 : 1 (both partial) — either side

Two tables; the relationship can be combined with either of them (class notes “way 1 / way 2”). The FK must be declared UNIQUE, otherwise the table would allow 1:N.

Prefer the side where fewer NULLs result — the side whose participation is closer to total.

8.6 Rule 5′ — the effect of participation

If the N side (the side receiving the FK) has total participation, the foreign key is declared NOT NULL. With partial participation it may be NULL (class notes: “FK can be NULL”).

{{er:r5d}}{{map:r5d}}

For a 1:1 relationship with total participation on one side only, put the FK in the total side (NOT NULL, UNIQUE): every row then has a value, no NULLs.

{{er:r6b}}{{map:r6b}}

8.7 Rule 6 — 1:1 with total participation on both sides

Class notes: “in this particular case we can combine all tables into a single table”. Every A has exactly one B and every B exactly one A, so A, B and R can be merged into one table. a1 and b1 are both candidate keys — either can be the primary key, the other is declared UNIQUE NOT NULL.

8.8 Rule 7 — weak entity type

Class notes: “identifying relation and weak entity set together”. Make one table for the weak entity containing the owner’s primary key (as FK, ON DELETE CASCADE) and its own attributes; PK = owner key + partial key. The identifying relationship needs no table.

8.9 Rule 8 — recursive (unary) relationships

Treat the two roles as two different entities that happen to be the same table: 1:N recursive → a self-referencing foreign key in the same table named after the role; M:N recursive → a separate table with two copies of the key, renamed by role.

8.10 Rule 9 — ternary / n-ary relationships

Always a separate table with the keys of all participating entities as foreign keys. If every side is M/N, all keys together form the PK. A side labelled 1 is determined by all the other sides, so its key is left out: with one “1” side, PK = keys of the other sides. With two “1” sides there are two candidate keys (practice P6).

8.11 Rule 10 — specialization / generalization

There are four standard options. The 2022 PYQ hierarchy (DOCTOR → PERMANENT / RESIDENT / VISITING, disjoint and total) is used to compare them.

(a) One table for the superclass + one for each subclass (always valid)

Each subclass table holds the superclass key (PK and FK to the superclass, ON DELETE CASCADE) plus its own attributes.

{{er:p22c_er}}{{map:p22c_er}}

(b) Only subclass tables (valid only for total specialization)

Each subclass table repeats all inherited attributes. No superclass table, so there is no join to get a full doctor record. Use it only if the specialization is total (otherwise doctors belonging to no subclass would be lost) and preferably disjoint (otherwise inherited data is duplicated). Also no other table can have a single FK to “DOCTOR”.

8.12 Rule 11 — aggregation

The aggregated relationship gets its table as usual (M:N rule). A relationship attached to the aggregate is mapped like an ordinary relationship whose “entity” is the aggregate, i.e. it uses the primary key of the aggregated relationship’s table.

{{er:t_agg2}}{{map:t_agg2}}

MONITORS is N:1 from the aggregate to MANAGER, so its primary key is (emp_id, proj_id) alone. For the “minimum tables” count it could also be merged into WORKS_ON as a nullable mgr_id column, but the separate table is the standard answer and avoids NULLs.

8.13 The whole algorithm on one page

ER → relational, in order
  1. Strong entity → table; composite → components; multivalued → separate table (key + value); derived → not stored.
  2. Weak entity → table with owner key + partial key as PK; owner key is FK with ON DELETE CASCADE; identifying relationship merged.
  3. Binary 1:1 → FK (UNIQUE) in the total side (either side if both partial); merge both tables if both sides total.
  4. Binary 1:N → FK in the N side (NOT NULL if N side total); relationship attributes go with it.
  5. Binary M:N → new table (key1, key2, attributes), PK = key1 + key2.
  6. Recursive → same as above with role-named keys.
  7. n-ary → new table with all keys; PK = keys of the non-“1” sides.
  8. Specialization → option (a)/(b)/(c)/(d).
  9. Aggregation → relationships on the aggregate use the aggregated relationship’s key.

8.14 Worked example: COMPANY (section 7.4) → 6 tables

{{er:company}}
  1. Strong entities: EMPLOYEE(ssn, fname, minit, lname, bdate, address, salary, sex) — name is composite, so its parts are stored. DEPARTMENT(dnumber, dname) with dname UNIQUE (second key); number_of_employees is derived → not stored. PROJECT(pnumber, pname, plocation).
  2. Weak entity: DEPENDENT(ssn, dependent_name, sex, birth_date, relationship), PK (ssn, dependent_name).
  3. 1:1 MANAGES, DEPARTMENT total → FK mgr_ssn (+ start_date) in DEPARTMENT, NOT NULL, UNIQUE.
  4. 1:N WORKS_FOR → dnumber in EMPLOYEE (NOT NULL: employee total); CONTROLS → dnumber in PROJECT; SUPERVISION → supervisor_ssn in EMPLOYEE.
  5. M:N WORKS_ON → WORKS_ON(ssn, pnumber, hours).
  6. Multivalued locations → DEPARTMENT_locations(dnumber, locations).

A foreign-key cycle

EMPLOYEE.dnumber is NOT NULL and references DEPARTMENT; DEPARTMENT.mgr_ssn is NOT NULL and references EMPLOYEE. The very first employee cannot be inserted before its department, and the department not before its manager.
