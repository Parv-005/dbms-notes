3Relationship types, relationship sets and roles

3.1 Relationship, relationship type, relationship set

Definitions
  • Relationship (instance) — an association among two or more entities, e.g. “Asha works for the Sales department”.
  • Relationship type R among entity types E1, …, En — the schema of a set of similar associations, e.g. WORKS_FOR between EMPLOYEE and DEPARTMENT. Drawn as a diamond joined by lines to the participating entity types.
  • Relationship set — the set of relationship instances of that type at a given moment. Mathematically it is a subset of the Cartesian product E1 × E2 × … × En; each instance ri = (e1, …, en) takes exactly one entity from each participating set.
{{erm:t_rel|EMPLOYEE works for DEPARTMENT (course notes p. 43). “since” is an attribute of the relationship, not of either entity.}}

Because a relationship set is a set, the same combination of entities cannot appear twice. If an employee could work for the same department in two separate periods and both must be recorded, the relationship alone cannot hold that: model a separate entity (e.g. ASSIGNMENT) instead.

3.2 Degree of a relationship type

The degree is the number of participating entity types.

DegreeNameExample
1Unary / recursiveEMPLOYEE supervises EMPLOYEE; COURSE is prerequisite of COURSE; PERSON is married to PERSON
2Binary (by far the most common)STUDENT enrols in COURSE
3TernarySUPPLIER supplies PART to PROJECT; INSTRUCTOR teaches COURSE to STUDENT

3.3 Roles and recursive relationships

Role name

Each entity type that participates in a relationship plays a particular role in it, written as a label on the connecting line. Role names are optional when the entity types are different (the role is obvious). They are essential in a recursive relationship, where the same entity type participates more than once in different roles.

{{erm:t_unary|SUPERVISES is recursive: one EMPLOYEE plays the role supervisor, another plays supervisee. Each supervisor has N supervisees; each supervisee has 1 supervisor.}}

Without role names you could not tell, for the instance (e1, e7), who supervises whom. When converted to a table the roles become column names: supervisor_emp_id.

3.4 Attributes of relationship types

A relationship can have its own attributes: since on WORKS_FOR, hours on WORKS_ON, grade on ENROLS. Such an attribute describes the combination, not either entity.

Where can a relationship attribute be moved?
  • 1:1 — the attribute can be moved to either entity type.
  • 1:N — it can be moved only to the N-side entity. since of WORKS_FOR (N employees : 1 department) can become an attribute of EMPLOYEE, because each employee has only one “since”.
  • M:N — it cannot be moved; it depends on both entities together. grade belongs to (student, course), not to either alone.
This is exactly what happens in the table conversion (section 8): the attribute goes wherever the foreign key goes.
Exam phrasing to recognise

“Each instructor teaches a course in a semester” → the semester is an attribute of TEACHES. “Record the grade each student received” → grade is an attribute of ENROLS / TAKES. “The date on which the employee joined the department” → attribute of WORKS_FOR.
