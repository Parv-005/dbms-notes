1Why normalize: redundancy and anomalies

Definition

Normalization is the process of analysing a relation schema using its functional dependencies and keys, and decomposing it into smaller, well-structured relations so that redundancy is minimised and insertion, deletion and update anomalies are removed — without losing information (lossless join) and, if possible, without losing dependencies (dependency preservation).

Take one table that mixes facts about students and courses (the running example of this unit):

RollNameCourseCNameCreditsInstructorOfficeGrade
101AshaCS301DBMS4RaoB-12A
102VikramCS301DBMS4RaoB-12B
101AshaCS302OS3MehtaC-04A
103NehaCS301DBMS4RaoB-12C

Redundancy: “CS301 is DBMS, 4 credits, taught by Rao, office B-12” is stored once per enrolled student. Redundancy causes three anomalies:

AnomalyWhat goes wrong here
InsertionA new course CS305 with no students yet cannot be inserted: the key is (Roll, Course) and Roll would be NULL (entity integrity).
Update (modification)If Rao moves to office B-20, every row of CS301 must change; missing one row leaves the database inconsistent.
DeletionIf Asha drops OS and she was its only student, deleting her row also deletes the fact that OS is taught by Mehta in C-04.

The cure is to store each fact once: Student(Roll, Name), Course(Course, CName, Credits, Instructor), Instructor(Instructor, Office), Enrolment(Roll, Course, Grade). Sections 7–9 show how to get exactly this decomposition mechanically from the FDs.

Informal design guidelines (Elmasri)

  1. Clear semantics: each relation should describe one entity type or one relationship type — do not mix attributes of several entities.
  2. Avoid redundancy and therefore insertion / deletion / update anomalies.
  3. Avoid NULLs as far as possible. NULLs waste space and are ambiguous — a NULL can mean “not applicable”, “unknown” or “known but not recorded yet”. They also make joins and aggregates (COUNT, SUM) behave unexpectedly. If many tuples would have NULL in some attributes, move those attributes to a separate relation.
  4. No spurious tuples: design relations so that joining them on primary key / foreign key attributes gives back only real tuples. Never split a relation so that the common attributes are not a key of either part (section 8).
Tip — the one-line goals of normalization

Remove redundancy → remove anomalies; keep the decomposition lossless (mandatory) and dependency preserving (desirable).

Cost of normalization

More tables mean more joins in queries, so read-heavy systems sometimes deliberately denormalize (section 10). Normalization is the default; denormalization is a performance decision taken later.

2Functional dependencies

Definition

A functional dependency X → Y on relation R means: any two tuples that agree on X must agree on Y. X is the determinant (left-hand side), Y the dependent. “X functionally determines Y”, “Y is functionally dependent on X”.

Formally: for all tuples t1, t2 in every legal state r(R): t1[X] = t2[X] ⇒ t1[Y] = t2[Y].

An FD is a statement about the meaning of the data (Roll → Name because every student has one name), so it must hold in every state of the relation.

Checking an FD on a table instance

Group the rows by the X value; inside each group the Y value must be the same. Example (from the class notes):

AB
a1b1
a2b3
a1b1
a3b3
a2b3

A → B holds: each A value always has the same B (a1→b1, a2→b3, a3→b3).

B → A does not hold: b3 appears with a2 and a3.

Common mistake — an instance can disprove an FD, never prove it

One table state can show that an FD is violated. If it is not violated, all we can say is that the FD may hold — the next inserted row could break it. FDs are declared by the designer from the meaning of the attributes, not inferred from a particular state. (This is 2025 end-sem Q4(a) part (b).)

Remember

“Partial” and “transitive” are always measured against a candidate key: a partial dependency is a non-prime attribute depending on part of a key (breaks 2NF); a transitive dependency is a non-prime attribute depending on a non-key set (breaks 3NF).

3Armstrong’s axioms (inference rules)

Given a set F of FDs, other FDs follow logically from it. The set of all FDs implied by F is the closure of F, written F+. Armstrong’s axioms are the rules used to derive them.

Definition — the three axioms
  1. Reflexivity (IR1): if Y ⊆ X then X → Y. (gives the trivial FDs)
  2. Augmentation (IR2): if X → Y then XZ → YZ. (add the same attributes to both sides)
  3. Transitivity (IR3): if X → Y and Y → Z then X → Z.

They are sound (they never produce an FD that is not implied) and complete (every implied FD can be produced by them).

Derived rules (provable from the three)

RuleStatementProof from IR1–IR3
Union / additivity (IR4)X → Y, X → Z ⊢ X → YZX → Y gives X → XY (augment by X); X → Z gives XY → YZ (augment by Y); transitivity: X → YZ.
Decomposition / projectivity (IR5)X → YZ ⊢ X → Y and X → ZYZ → Y (reflexivity); X → YZ → Y (transitivity). Same for Z.
Pseudo-transitivity (IR6)X → Y, WY → Z ⊢ WX → ZX → Y gives WX → WY (augment by W); WY → Z; transitivity: WX → Z.
Composition (extra)A → B, C → D ⊢ AC → BDAC → BC (augment A → B by C); BC → BD (augment C → D by B); transitivity.
Example — derive FDs (Korth’s classic set)

R(A, B, C, G, H, I), F = {A → B, A → C, CG → H, CG → I, B → H}. Show that A → H, CG → HI and AG → I are in F+.

  • A → B and B → H ⇒ A → H (transitivity).
  • CG → H and CG → I ⇒ CG → HI (union).
  • A → C and CG → I ⇒ AG → I (pseudo-transitivity with W = G).
Common mistake — rules that are NOT valid

You may add attributes to the left (X → Z ⊢ XY → Z is valid: augment, then decompose), but you may not remove them: XY → Z does not give X → Z. Likewise X → Y and Z → Y do not give X → Z. To show a rule is invalid, give a two-row counterexample table. For “AB → C ⊢ A → C”:

ABC
115
126

AB → C holds (the AB values differ), but A → C fails (same A, different C).

Tip — in practice you rarely apply axioms by hand

To test whether X → Y is implied by F, just compute X+ (next section) and check Y ⊆ X+. The closure algorithm is the axioms applied systematically.

4Attribute closure X+

Definition

The closure of an attribute set X under F, written X+, is the set of all attributes that X functionally determines using F (and the axioms).

Algorithm
  1. result := X
  2. repeat: for each FD L → R in F, if L ⊆ result then result := result ∪ R
  3. until result does not change. Then X+ = result.
Example

R(A, B, C, G, H, I), F = {A → B, A → C, CG → H, CG → I, B → H}.

{AG}+ : AG → ABG[A → B] → ABCG[A → C] → ABCGH[CG → H] → ABCGHI[CG → I] = all attributes ✔

{A}+ : A → AB[A → B] → ABC[A → C] → ABCH[B → H]

So AG is a superkey (in fact the candidate key: A+ and G+ = G are not everything).

What closure is used for

QuestionTest
Is X a superkey of R?X+ = all attributes of R.
Is X a candidate key?X is a superkey and no proper subset of X is (check X minus each single attribute).
Does F imply X → Y? (is X → Y in F+?)Y ⊆ X+.
Are F and G equivalent?Every FD of G follows from F and every FD of F follows from G (closure tests both ways).
Is attribute a extraneous in XY → Z? (minimal cover)Z ⊆ (X)+ computed with F (section 6).
Is a decomposition lossless? Dependency preserving?(R1 ∩ R2)+ ⊇ R1 or R2; the res-algorithm (section 8).
Example — equivalence of two FD sets

F = {A → C, AC → D, E → AD, E → H}, G = {A → CD, E → AH}. Are they equivalent?

  • G from F: A+F = ACD ⊇ CD ✔; E+F = EADHC ⊇ AH ✔.
  • F from G: A+G = ACD ⊇ C ✔; (AC)+G = ACD ⊇ D ✔; E+G = EAHCD ⊇ AD and H ✔.

F ≡ G (each covers the other).

Tip — write closures as a chain

In the exam write (AG)+ = AG → ABCG (A→BC) → ABCGHI (CG→HI), naming the FD used at each step. That is what the closure lines in these notes look like.

5Keys from FDs

TermMeaning (in terms of closure)
SuperkeyX with X+ = R (determines every attribute).
Candidate keya minimal superkey: no proper subset is a superkey.

Prime attributebelongs to some candidate key. Non-prime: belongs to none.

“Normal forms based on primary keys” (syllabus) are really based on all candidate keys: prime / non-prime depends on every key, so always find them all.

Method: finding all candidate keys

  1. Split attributes into three groups: never on a right-hand side (must be in every key), only on right-hand sides (in no key), on both sides (may be in a key).
  2. Compute the closure of the “never on RHS” group. If it is all of R, that group is the only candidate key — stop.
  3. Otherwise add “both sides” attributes one at a time, then two at a time, …, computing closures. Skip any set containing a key already found (it would not be minimal).
  4. Shortcut for more keys: if key K contains attribute a and some FD X → a exists, then (K − a) ∪ X is also a superkey — test whether it (or a subset) is a new key.
Example (class notes) — R(ABCDEFG), F = {AB → CD, AF → D, DE → F, C → G, F → E, G → A}
  1. Attributes that never appear on a right-hand side (must be in every key): B.
  2. {B}+ : B — not all attributes, so add attributes from {ACDEFG}.
  3. Candidate keys found (each is minimal — no proper subset’s closure gives all attributes):
    {ABE}+ : ABE → ABCDE[AB → CD] → ABCDEF[DE → F] → ABCDEFG[C → G] = all attributes ✔
    {ABF}+ : ABF → ABCDF[AB → CD] → ABCDFG[C → G] → ABCDEFG[F → E] = all attributes ✔
    {BCE}+ : BCE → BCEG[C → G] → ABCEG[G → A] → ABCDEG[AB → CD] → ABCDEFG[DE → F] = all attributes ✔
    {BCF}+ : BCF → BCFG[C → G] → BCEFG[F → E] → ABCEFG[G → A] → ABCDEFG[AB → CD] = all attributes ✔
    {BEG}+ : BEG → ABEG[G → A] → ABCDEG[AB → CD] → ABCDEFG[DE → F] = all attributes ✔
    {BFG}+ : BFG → BEFG[F → E] → ABEFG[G → A] → ABCDEFG[AB → CD] = all attributes ✔
  4. Candidate keys: {ABE}, {ABF}, {BCE}, {BCF}, {BEG}, {BFG}. Prime attributes: {ABCEFG}; non-prime: {D}.

The class notes found the same six keys (“candidate key must have B”). With six keys, A, B, C, E, F, G are prime and only D is non-prime.

Example (course PDF p. 87) — R(ABCD), F = {A → B, B → C, C → A}

D is never on a RHS, D+ = D. Try AD: {AD}+ : AD → ABD[A → B] → ABCD[B → C] = all attributes ✔ → key. A appears on the RHS of C → A, so replace A by C: CD is a key; C appears in B → C, so BD is a key. Candidate keys: AD, BD, CD.

Counting superkeys

With n attributes, a candidate key K of size k is contained in 2n−k attribute sets (each other attribute is in or out). For several keys use inclusion–exclusion (supersets of K1 and K2 are the supersets of K1 ∪ K2):

#SK = Σ 2n−|Ki| − Σ 2n−|Ki∪Kj| + Σ 2n−|Ki∪Kj∪Kl| − …

Example (mid-sem 2021 Q3(b)) — R(ABCDE), candidate keys A and BC

25−1 + 25−2 − 25−3 (supersets of ABC) = 16 + 8 − 4 = 20 superkeys.

Tip — with many keys, count the complement

Count the sets that are not superkeys (contain no key) and subtract from 2n. E.g. keys A, B, E, CD in R(ABCDE): a non-superkey contains none of A, B, E and not both C and D, so it is one of ∅, C, D → 32 − 3 = 29 (2022 Q3(c)).

6Minimal (canonical) cover

Definition

A minimal cover G of F is a set of FDs equivalent to F (G+ = F+) such that

  1. every FD in G has a single attribute on the right-hand side;
  2. no left-hand side has an extraneous attribute (removing any LHS attribute changes the closure);
  3. no FD is redundant (removing it changes the closure).

A canonical cover (Korth) is the same thing with FDs of equal LHS combined (A → B, A → C written A → BC). It is used for 3NF synthesis and to simplify any FD set.

Algorithm — always in this order
  1. Split every RHS into single attributes (decomposition rule). Delete duplicates and trivial FDs.
  2. Remove extraneous LHS attributes: in XA → B, A is extraneous if B ∈ X+ (closure computed with the current full F). Replace by X → B.
  3. Remove redundant FDs: X → B is redundant if B ∈ X+ computed without that FD. Delete it.
  4. (Optional) Combine FDs with the same LHS → canonical cover.
Example (Korth) — F = {A → BC, B → C, A → B, AB → C}
  1. Split: A → B, A → C, B → C, A → B (duplicate, drop), AB → C.
  2. AB → C: is B extraneous? A+ = ABC ∋ C → yes, it becomes A → C (already present, drop).
  3. A → C: without it, A+ = AB → ABC ∋ C → redundant, delete.

Minimal cover: {A → B, B → C}.

Common mistakes
  • Doing step 3 before step 2 can leave a non-minimal result. Always remove extraneous LHS attributes first.
  • When testing redundancy, compute the closure without the FD being tested — otherwise everything looks redundant.
  • A minimal cover is not unique: a different order of testing can give a different (equally correct) answer. Mention this in the exam.

7Normal forms: 1NF, 2NF, 3NF, BCNF

First normal form (1NF)

Definition

R is in 1NF if the domain of every attribute contains only atomic (indivisible, single) values — no multivalued attributes, no repeating groups, no nested relations. (The relational model assumes 1NF, so every “relation” is in 1NF.)

Not in 1NF (class notes): Colour is multivalued.

ProdIDColourPrice
ID1red, black20
ID2black30
ID3yellow, blue, black40

In 1NF: one value per cell; key becomes (ProdID, Colour).

ProdIDColourPrice
ID1red20
ID1black20
ID2black30
ID3yellow40
ID3blue40
ID3black40

The flattened table now repeats Price (ProdID → Price is a partial dependency on key (ProdID, Colour)) — 1NF does not remove redundancy. The best fix is a separate table: Product(ProdID, Price) and ProductColour(ProdID, Colour). (A composite attribute is made atomic by storing its components as separate columns.)

Second normal form (2NF)

Definition

R is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on every candidate key — i.e. there is no partial dependency of a non-prime attribute on a proper subset of a candidate key.

  • If every candidate key is a single attribute, R is automatically in 2NF (a single attribute has no proper non-empty subset).
  • Partial dependencies of prime attributes are allowed in 2NF and 3NF.
Example (Dhruv’s notes) — R(ABCDE), F = {A → B, BC → D, E → C, D → A}

E is never on a RHS. {AE}+ : AE → ABE[A → B] → ABCE[E → C] → ABCDE[BC → D] = all attributes ✔, and likewise BE and DE. Candidate keys AE, BE, DE; prime A, B, D, E; non-prime C.

E → C: E is part of key AE and C is non-prime → partial dependency → not in 2NF (highest NF = 1NF).

Third normal form (3NF)

Definition (two equivalent forms — learn both)

(a) R is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on a candidate key.

(b) Test form: R is in 3NF if for every non-trivial FD X → A in F+, at least one holds:

  1. X is a superkey of R, or
  2. A is a prime attribute.

Form (b) checks 2NF and 3NF together, so it is the one to use in answers. It is enough to test the FDs of F with single-attribute RHS.

Example (Dhruv’s notes) — R(ABCDE), F = {AB → CD, ABC → E, C → A}

{AB}+ : AB → ABCD[AB → CD] → ABCDE[ABC → E] = all attributes ✔; {BC}+ : BC → ABC[C → A] → ABCD[AB → CD] → ABCDE[ABC → E] = all attributes ✔. Keys AB, BC; prime A, B, C; non-prime D, E.

AB → CD and ABC → E have superkey LHS; C → A has a prime RHS → every FD passes → 3NF. (Not BCNF: C is not a superkey.)

Boyce–Codd normal form (BCNF)

Definition

R is in BCNF if for every non-trivial FD X → A in F+, X is a superkey of R. (“Every determinant is a candidate key.”) BCNF = 3NF without the “A is prime” escape clause, so it is stricter.

Example — 3NF but not BCNF: Teach(Student, Course, Teacher)

Each teacher teaches one course (Teacher → Course); for each course a student has one teacher (Student, Course → Teacher).

Keys {Student, Course} and {Student, Teacher}; all three attributes are prime, so no 2NF/3NF violation is possible → 3NF. But in Teacher → Course, Teacher is not a superkey → not BCNF. Redundancy that remains: “Rao teaches DBMS” is repeated for every student of Rao.

Quick facts (class notes)
  • Every relation with two attributes is in BCNF (the only non-trivial FDs are A → B or B → A, and then the LHS is a key).
  • If all attributes are prime, R is at least in 3NF.
  • If every candidate key is a single attribute, R is at least in 2NF.
  • If the only FDs have a candidate key on the left, R is in BCNF (e.g. A → B, B → C, C → A on R(A, B, C): keys A, B, C).

Method: finding the highest normal form

  1. Find all candidate keys (section 5); list prime and non-prime attributes.
  2. Make a table with one row per FD: is the LHS a superkey? is the RHS prime? Classify each FD as OK, partial (LHS ⊂ key, RHS non-prime), transitive (LHS is not a superkey and not part of a key, RHS non-prime) or BCNF-only violation (LHS not a superkey, RHS prime).
  3. Any partial → 1NF. Else any transitive → 2NF. Else any BCNF-only violation → 3NF. Else BCNF.
Worked example — the running example

R(Roll, Name, Course, CName, Credits, Instructor, Office, Grade) with Roll → Name; Course → CName, Credits, Instructor; Instructor → Office; Roll, Course → Grade.

  1. Attributes that never appear on a right-hand side (must be in every key): Roll, Course. Attributes only on the right-hand side (in no key): Name, CName, Credits, Office, Grade.
  2. {Roll, Course}+ : Roll, Course → Roll, Name, Course[Roll → Name] → Roll, Name, Course, CName, Cr, Instr[Course → CName, Cr, Instr] → Roll, Name, Course, CName, Cr, Instr, Office[Instr → Office] → Roll, Name, Course, CName, Cr, Instr, Office, Grade[Roll, Course → Grade] = all attributes ✔ → {Roll, Course} is the only candidate key (every key must contain it, and it is already a key).
  3. Candidate key: {Roll, Course}. Prime attributes: {Roll, Course}; non-prime: {Name, CName, Credits, Instructor, Office, Grade}.

8Decomposition: lossless join and dependency preservation

Normalizing means replacing R by relations R1, …, Rn (each a subset of R’s attributes). A decomposition must satisfy:

PropertyMeaningStatus
Attribute preservationR1 ∪ … ∪ Rn = R (no attribute lost)mandatory (checked during decomposition)
Lossless joinfor every legal state r: πR1(r) ⋈ … ⋈ πRn(r) = r (no spurious tuples)mandatory
Dependency preservation(F1 ∪ … ∪ Fn)+ = F+, where Fi = FDs of F+ using only Ri’s attributesdesirable (always achievable for 3NF, not always for BCNF)

Lossless vs lossy — spurious tuples

R(A, B, C) with A → B. Decompose on B (not a key of either part) and join back:

πAB = {(a1,b1), (a2,b1)}, πBC = {(b1,c1), (b1,c2)}

Two spurious tuples (red). We get more rows but less information: we can no longer tell which rows are real. That is why it is called lossy.

Splitting on A instead — R1(A, B), R2(A, C) — is lossless, because the common attribute A is a key of R1.

Test 1 — binary decomposition (two relations)

Lossless-join test (the “3 properties”)

R → R1, R2 is lossless if and only if

  1. R1 ∪ R2 = R (attribute preservation);
  2. R1 ∩ R2 ≠ ∅ (there is a common attribute);
  3. R1 ∩ R2 → R1 or R1 ∩ R2 → R2 is in F+ — i.e. the common attributes are a superkey of at least one part. Test it with closure: (R1 ∩ R2)+ ⊇ R1 or ⊇ R2.
Example (class notes) — R(ABCD), F = {C → D, AB → C, C → A}, R1(CD), R2(ABC)

R1 ∩ R2 = C; {C}+ : C → CD[C → D] → ACD[C → A] ⊇ R1(CD) → lossless.

Test 2 — three or more relations

Class-notes method (merge step by step): pick two relations whose intersection is a key of one of them; they join losslessly, so replace them by their union. Repeat. If you end with R, the decomposition is lossless.

Example (class notes) — R(ABCDE), F = {A → B, B → C, C → D, D → E}; R1(ABC), R2(BCD), R3(CDE)
  • R1 ∩ R2 = BC; {BC}+ : BC → BCD[C → D] → BCDE[D → E] ⊇ R2 → merge: R4 = ABCD.
  • R4 ∩ R3 = CD; {CD}+ : CD → CDE[D → E] ⊇ R3 → merge: ABCDE = R → lossless.
Common mistake — “R1 ∩ R2 ∩ R3” is not a test

Intersecting all three at once is wrong (class notes say this too). Test pairs. If no pair can be merged, the merge method fails — but strictly, failure of one merge order does not prove lossiness. The certain test is the chase below; use it when you must prove “lossy” for 3+ relations.

Test 3 — the chase (tableau) algorithm beyond syllabus, but decisive

  1. Make a table: one row per Ri, one column per attribute. Put a where the attribute is in Ri, otherwise bi (a different symbol per row).
  2. For each FD X → Y: if two rows agree on all X columns, make their Y values equal (if either is a, both become a).
  3. Repeat until nothing changes. Lossless ⇔ some row is all a’s.
Example (end-sem 2023 Q3(a) and class notes) — R(ABCD), F = {A → B, B → C, C → D}; R1(AB), R2(AD), R3(CD)

Final tableau after applying the FDs until nothing changes. No row becomes all a’s → lossy.

Rows 1 and 2 agree on A, so they get the same B, then the same C and D — but their C is still a b. Row 3 has C as a, yet it agrees with the others only on D, and D determines nothing, so no row ever becomes all a’s. The merge method agrees: AB ∩ AD = A is a key of AB, giving ABD; then ABD ∩ CD = D with D+ = D → cannot merge → lossy.

Dependency preservation

Definition

Let Fi = the FDs in F+ that involve only attributes of Ri (the projection of F on Ri). The decomposition is dependency preserving if (F1 ∪ … ∪ Fn)+ = F+. Then every FD can be enforced by checking one relation at a time, without joins.

Quick check: if every FD of F lies completely inside some Ri, it is preserved. For the FDs that do not, use the algorithm from the class notes, which avoids computing F+:

Algorithm (test one FD X → Y)

res = X; repeat: for each Ri: res = res ∪ ((res ∩ Ri)+ ∩ Ri) until res stops changing.

X → Y is preserved iff Y ⊆ res. (Closures are taken under the original F.)

9Converting a relation into a required normal form

To 2NF — remove partial dependencies

  1. Find the candidate keys and every partial dependency X → Y (X a proper part of a key, Y non-prime).
  2. For each such X make a relation (X ∪ all non-prime attributes in X+) with key X — take everything X determines, including attributes it determines transitively.
  3. Keep one relation with the full key and the attributes that depend on the whole key.
Running example → 2NF

Partial: Roll → Name, and Course → CName, Credits, Instructor (and, through Instructor, Office). Full: Roll, Course → Grade.

The Course relation is in 2NF but not 3NF: Instructor → Office is transitive. The class-notes example R(ABCD), A → B, C → D goes the same way: R1(AB), R2(CD), and R3(AC) as the joining (key) relation.

To 3NF — synthesis algorithm (lossless and dependency preserving)

Algorithm (Bernstein synthesis)
  1. Find a minimal cover G of F (section 6).
  2. For each LHS X in G make a relation (X ∪ everything X determines in G).
  3. If no relation contains a candidate key of R, add one relation that is just a candidate key (this makes the join lossless).
  4. Remove any relation whose attributes are contained in another.

Result: every relation is in 3NF, the decomposition is always lossless and always dependency preserving.

Example (class notes; also end-sem 2023 Q3(b)) — R(ABCDE), F = {AB → C, C → D, D → E, A → C}
  1. Minimal cover: A → C, C → D, D → E.
  2. One relation per FD (LHS ∪ RHS): (AC), (CD), (DE).
  3. No relation contains a candidate key → add (AB).
  4. Result: R1(AC), R2(CD), R3(DE), R4(AB).

The class notes reach the same four relations CD, DE, AC and AB (“AB joining”). AB → C is not inside any relation, but it is preserved: A → C is, and A → C implies AB → C.

Decomposition approach (equivalent in simple cases): start from the 2NF result and split off each transitive dependency X → Y as (X ∪ (X+ ∩ Ri)), leaving X behind as a foreign key. For the running example: Course(Course, CName, Credits, Instructor) + Instructor(Instructor, Office).

Same example by the decomposition approach — R(ABCDE), F = {AB → C, C → D, D → E, A → C}

Instead of building relations from the minimal cover, keep splitting R on the dependency that breaks the normal form, until every part is in 3NF.

  1. Key and NF. A and B never appear on a RHS, and (AB)+ = ABCDE, so the key is AB. Prime: A, B; non-prime: C, D, E. A → C is a partial dependency (A is part of the key), so R is in 1NF.
  2. To 2NF: remove the partial dependency A → C. Take everything A determines: A+ = ACDE.
    R → R1(A, C, D, E) with key A, and R2(A, B) with key AB. A stays in R2 as the foreign key.
    R1 keeps A → C, C → D, D → E. R2 has no non-trivial FD, so it is in BCNF. The common attribute A is the key of R1, so this split is lossless.
  3. R1 is in 2NF but not 3NF (key A; C → D and D → E are transitive). Split off the last link of the chain first, D → E (D+ ∩ R1 = DE):
    R1 → R11(D, E) with key D, and R12(A, C, D).
    Common attribute D is the key of R11, so the split is lossless. R12 still has A → C, C → D, and C → D is transitive.
  4. Split R12 on C → D (C+ ∩ R12 = CD): R12 → R121(C, D) with key C, and R122(A, C) with key A. Common attribute C is the key of R121, so this split is lossless.
  5. Result: R2(AB), R122(AC), R121(CD), R11(DE). This is the same as synthesis: AB, AC, CD, DE, all in BCNF (so in 3NF too).
  6. Check. Lossless: every step split on a key of one of the two parts. Dependency preserving: A → C is in AC, C → D in CD, D → E in DE, and AB → C follows from A → C.

Decomposition tree: ABCDE → {AB, ACDE}; ACDE → {DE, ACD}; ACD → {CD, AC}.

Common mistake — splitting in the wrong order

From R1(ACDE), splitting off C → D alone as (C, D) leaves (A, C, E). That is lossless, but D → E is now lost: D and E are no longer in the same relation, and (A, C, E) has only A → C and C → E. The fix is to split off X ∪ (X+ ∩ Ri) whenever you split on X: C+ ∩ R1 = CDE, giving (CDE) and (AC). Splitting (CDE) again on D → E gives (CD) and (DE), the same answer. Synthesis can never make this mistake, which is why it is the safer method for 3NF.

When the two approaches differ: on simple chains like this one they give the same relations. On harder inputs, splitting can lose a dependency or need extra splits, while synthesis is guaranteed to be lossless and dependency preserving. If the question says “decompose” without naming a method, either is accepted. If dependency preservation is asked, use synthesis or check the result with the res-algorithm.

To BCNF — decomposition algorithm (lossless, maybe not preserving)

Algorithm
  1. Find an FD X → Y that holds on a relation Ri with X not a superkey of Ri. Take Y = X+ ∩ Ri (minus X) so the split is as large as possible.
  2. Replace Ri by Ra = X ∪ Y (X is its key) and Rb = Ri − Y (keeps X, so the join is lossless).
  3. Repeat on the new relations (using FDs implied on them, not just the given ones) until every relation is in BCNF.
  4. Finally check which FDs of F are preserved (res-algorithm) and say so.
Running example → BCNF
  1. In (Roll, Name, Course, CName, Credits, Instructor, Office, Grade): Roll → Name holds and Roll is not a superkey of it (Roll+ ∩ R = Roll, Name). Split into (Roll, Name) and (Roll, Course, CName, Credits, Instructor, Office, Grade).
  2. In (Roll, Course, CName, Credits, Instructor, Office, Grade): Course → CName, Credits, Instructor, Office holds and Course is not a superkey of it (Course+ ∩ R = Course, CName, Credits, Instructor, Office). Split into (Course, CName, Credits, Instructor, Office) and (Roll, Course, Grade).
  3. In (Course, CName, Credits, Instructor, Office): Instructor → Office holds and Instructor is not a superkey of it (Instructor+ ∩ R = Instructor, Office). Split into (Instructor, Office) and (Course, CName, Credits, Instructor).
  4. No relation has a violating FD any more. Result: R1(Roll, Name), R2(Instructor, Office), R3(Course, CName, Credits, Instructor), R4(Roll, Course, Grade).

10Beyond BCNF: 4NF, 5NF, denormalization beyond syllabus

The course PDF (pp. 98–101) covers these briefly. They are not in the syllabus list, so read once and move on.

Multivalued dependency and 4NF

MVD X →→ Y: each X value is associated with a set of Y values that is independent of the other attributes. Example (course PDF): Faculty(Faculty, Subject, Committee) — Kailash teaches {DBMS, Java, C} and sits on {Placement, Scholarship}; the two sets are independent, so the table must store all 3 × 2 = 6 combinations. The only key is all three attributes, so it is in BCNF, yet it is redundant.

4NF: BCNF and for every non-trivial MVD X →→ Y, X is a superkey. Fix: FacultySubject(Faculty, Subject), FacultyCommittee(Faculty, Committee) — 3 + 2 rows instead of 6.

Join dependency and 5NF

A join dependency says R equals the join of some projections R1, …, Rn. 5NF (project-join NF): every non-trivial join dependency is implied by the candidate keys — the table cannot be split further without loss. Classic case: Agent–Company–Product where “agent sells product for company” follows from the three pairwise facts.

Denormalization

Deliberately merging normalized tables (or storing a derived/duplicate column) to avoid expensive joins in read-heavy systems such as reports and data warehouses. The price is redundancy, so the update anomalies must be handled by the application or triggers.

11One-page revision sheet

FD theory
  • X → Y: equal X ⇒ equal Y in every legal state. Instance can disprove, never prove.
  • Trivial Y ⊆ X · full: no proper subset determines Y · partial: a proper subset does · transitive: X → Z → Y, Z not a key.
  • Axioms: reflexivity, augmentation, transitivity (sound + complete). Derived: union, decomposition, pseudo-transitivity (X→Y, WY→Z ⊢ WX→Z).
  • X+: keep adding RHS of FDs whose LHS is inside. X → Y ∈ F+ ⇔ Y ⊆ X+.
  • Minimal cover: split RHS → drop extraneous LHS attrs → drop redundant FDs.
Keys
  • Superkey: X+ = R. Candidate key: minimal superkey. Prime: in some key.
  • Never-on-RHS attributes are in every key; only-on-RHS attributes in none.
  • Superkeys of one key of size k: 2n−k; several keys: inclusion–exclusion.
Normal forms
  • 1NF atomic values.
  • 2NF no non-prime attribute depends on part of a key.
  • 3NF every non-trivial X → A: X superkey or A prime.
  • BCNF every non-trivial X → A: X superkey.
  • 2 attributes ⇒ BCNF · all attributes prime ⇒ ≥ 3NF · all keys single ⇒ ≥ 2NF.
Decomposition
  • Lossless (2 parts): (R1∩R2)+ ⊇ R1 or R2. 3+: merge pairs / chase.
  • Preserving: res = X; res ∪= ((res∩Ri)+∩Ri); Y ⊆ res.
  • 3NF synthesis: always lossless + preserving. BCNF decomposition: always lossless, not always preserving.

End-sem 2026 Q4(c)5 marks

Explain with suitable examples: (i) Armstrong’s axioms (ii) attribute closure (iii) minimal cover (iv) lossless join decomposition (v) dependency preservation. Illustrate how these concepts help in achieving higher normal forms.

Show answer

Use one relation throughout: R(A, B, C, D), F = {A → B, B → C, A → C, C → D}.

  1. Armstrong’s axioms: reflexivity (Y ⊆ X ⇒ X → Y), augmentation (X → Y ⇒ XZ → YZ), transitivity (X → Y, Y → Z ⇒ X → Z); sound and complete. E.g. A → B, B → C ⇒ A → C; A → B ⇒ AD → BD.
  2. Attribute closure X+: all attributes determined by X. A+ = A → AB → ABC → ABCD, so A is a key; C+ = CD, so C is not.
  3. Minimal cover: equivalent set with single-attribute RHS, no extraneous LHS attributes, no redundant FD. Here A → C is redundant (A → B → C): Fmin = {A → B, B → C, C → D}.
  4. Lossless join: joining the parts returns exactly R. R1(A, B), R2(B, C, D): R1 ∩ R2 = B and B+ = BCD ⊇ R2 → lossless. R1(A, B), R2(C, D) (no common attribute) would be lossy.
  5. Dependency preservation: the FDs of the parts imply all of F. R1(AB), R2(BC), R3(CD) keeps A → B, B → C, C → D (A → C follows) → preserved.

How they help: closure finds the keys, so we can tell prime from non-prime attributes and spot partial/transitive dependencies (R above is in 2NF; B → C, C → D are transitive). The minimal cover gives the relations of the 3NF synthesis (AB, BC, CD). The lossless test guarantees the normalized tables can be joined back without spurious tuples, and the preservation test tells us whether each FD can still be checked inside a single table — 3NF can always keep both; BCNF can always keep the first.

End-sem 2025 Q4(a)3 + 2 marks

(a) Why should NULLs in a relation be avoided as much as possible? Discuss the problem of spurious tuples and how we may prevent it. (b) Why can we not infer a functional dependency automatically from a particular relation state? Explain with an example.

Show answer

(a) NULLs.

  • Wasted storage when an attribute does not apply to many tuples (e.g. Office_phone of employees without an office).
  • Ambiguous meaning: the attribute does not apply / the value is unknown / it exists but is not recorded yet.
  • Problems in operations: joins on a NULL column drop tuples, COUNT/SUM/AVG ignore NULLs, comparisons give UNKNOWN.
  • Guideline: if many tuples would have NULL in some attributes, move those attributes to a separate relation (with the key); if NULLs are unavoidable they should be exceptions.

Spurious tuples are extra, wrong tuples that appear when relations are joined on attributes that are neither a primary key nor a foreign key — i.e. after a lossy decomposition. Example: R(A, B, C) with A → B split into (A, B) and (B, C); joining on B produces combinations that never existed (section 8.1). Prevention: decompose only so that the common attributes of the two parts are a superkey of at least one part ((R1 ∩ R2)+ ⊇ R1 or R2) — join only on primary-key / foreign-key pairs. 3NF synthesis and BCNF decomposition guarantee this.

(b) An FD is a constraint on all possible legal states, determined by the meaning of the attributes. A particular state shows only the current rows; an FD that happens to be satisfied now may be violated by the next insert. Example: if the Student table currently has Name values all distinct, Name → Roll holds in that state — but two students may have the same name, so Name → Roll is not an FD. A state can disprove an FD (two rows with equal X and different Y) but never prove one.

Show that R(S, C, T) with F = {S C → T, T → C} has no BCNF decomposition that is both lossless and dependency preserving.

Keys: SC and ST (T → C, so ST → C). T → C violates BCNF, so R must be split. Any proper decomposition puts the three attributes into relations of at most two attributes each. The FD SC → T needs S, C and T together; in no two-attribute relation can it be checked, and the projections of F on two-attribute relations are only T → C (on TC) or trivial FDs, which do not imply SC → T. So SC → T is lost in every BCNF decomposition. Lossless ones exist (TC + ST), but none preserves SC → T.

Last-day checklist for a normalization question
  1. List all candidate keys (never-on-RHS attributes first) and write prime / non-prime.
  2. For “highest NF”, name the exact FD that breaks the next NF, and say why (part of key / not a key / RHS non-prime).
  3. For 3NF use synthesis from a minimal cover; add a key relation if needed; say “lossless and dependency preserving”.
  4. For BCNF split on a violating FD, recheck the new relations, then test dependency preservation.
  5. For “lossless?”: two relations → intersection closure; three or more → merge pairs or chase. Never intersect all at once.
  6. Underline the key of every final relation.
