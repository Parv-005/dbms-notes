13.1 Keys, superkeys and FDs from an instance

Mid-sem 2021 Q3(b)4 marks

Consider a relation R(A, B, C, D, E). If (A) and (BC) are the candidate keys of R, find the number of superkeys and list them.

Show answer

A superkey is any attribute set containing a candidate key.

  • Containing A: A plus any subset of {B, C, D, E} → 24 = 16.
  • Containing BC: BC plus any subset of {A, D, E} → 23 = 8.
  • Containing both (counted twice): ABC plus any subset of {D, E} → 22 = 4.

Total = 16 + 8 − 4 = 20.

List: A, AB, AC, AD, AE, ABC, ABD, ABE, ACD, ACE, ADE, ABCD, ABCE, ABDE, ACDE, ABCDE (16 with A); BC, BCD, BCE, BCDE (4 more with BC but without A).

20 superkeys.

Mid-sem 2023 Q5(a)2 marks

Is every superkey a candidate key? Give reasons to justify your answer.

Show answer

No. A candidate key is a minimal superkey; every candidate key is a superkey, but a superkey may contain extra attributes. In Student(Roll, Name, Email) with Roll → Name, Email: {Roll} is a candidate key, while {Roll, Name} is a superkey (its closure is all attributes) but not a candidate key, because its proper subset {Roll} is already a superkey.

13.5 Minimal cover and theory

End-sem 2023 COCSC05 Q3(c)4 marks

Explain the canonical (minimal) cover of a set of FDs. Find the canonical cover for F = {BCD → H, A → BC, CD → E, E → C, D → AEH, ABH → BD, DH → C}.

Show answer

A canonical cover Fc is a set equivalent to F (same closure) with no extraneous attribute on either side and no redundant FD, FDs with equal LHS combined (definition and algorithm in section 6).

  1. Split RHS: BCD → H, A → B, A → C, CD → E, E → C, D → A, D → E, D → H, ABH → B (trivial, drop), ABH → D, DH → C.
  2. Extraneous LHS attributes (note D+ = ABCDEH, so D alone determines everything):
    • BCD → H: D+ ∋ H → B and C extraneous → D → H (duplicate).
    • CD → E: D+ ∋ E → C extraneous → D → E (duplicate).
    • DH → C: D+ ∋ C → H extraneous → D → C.
    • ABH → D: {{cl:c23c|AH}} ∋ D, so B is extraneous → AH → D. A+ = ABC and H+ = H do not contain D, so A and H both stay.
  3. Redundant FDs in {D → H, D → E, D → C, D → A, A → B, A → C, E → C, AH → D}: D → C is redundant (D → A → C). Nothing else can be derived without itself.

Fc = {D → AEH, A → BC, E → C, AH → D}.

The checker confirms this set is equivalent to F and minimal. Here every testing order gives the same cover: D → C is the only redundant FD (E → C and A → C have no other source of C).

End-sem 2026 Q4(c)5 marks

Explain with suitable examples: (i) Armstrong’s axioms (ii) attribute closure (iii) minimal cover (iv) lossless join decomposition (v) dependency preservation. Illustrate how these concepts help in achieving higher normal forms.

Show answer

Use one relation throughout: R(A, B, C, D), F = {A → B, B → C, A → C, C → D}.

  1. Armstrong’s axioms: reflexivity (Y ⊆ X ⇒ X → Y), augmentation (X → Y ⇒ XZ → YZ), transitivity (X → Y, Y → Z ⇒ X → Z); sound and complete. E.g. A → B, B → C ⇒ A → C; A → B ⇒ AD → BD.
  2. Attribute closure X+: all attributes determined by X. A+ = A → AB → ABC → ABCD, so A is a key; C+ = CD, so C is not.
  3. Minimal cover: equivalent set with single-attribute RHS, no extraneous LHS attributes, no redundant FD. Here A → C is redundant (A → B → C): Fmin = {A → B, B → C, C → D}.
  4. Lossless join: joining the parts returns exactly R. R1(A, B), R2(B, C, D): R1 ∩ R2 = B and B+ = BCD ⊇ R2 → lossless. R1(A, B), R2(C, D) (no common attribute) would be lossy.
  5. Dependency preservation: the FDs of the parts imply all of F. R1(AB), R2(BC), R3(CD) keeps A → B, B → C, C → D (A → C follows) → preserved.

How they help: closure finds the keys, so we can tell prime from non-prime attributes and spot partial/transitive dependencies (R above is in 2NF; B → C, C → D are transitive). The minimal cover gives the relations of the 3NF synthesis (AB, BC, CD). The lossless test guarantees the normalized tables can be joined back without spurious tuples, and the preservation test tells us whether each FD can still be checked inside a single table — 3NF can always keep both; BCNF can always keep the first.

End-sem 2025 Q4(a)3 + 2 marks

(a) Why should NULLs in a relation be avoided as much as possible? Discuss the problem of spurious tuples and how we may prevent it. (b) Why can we not infer a functional dependency automatically from a particular relation state? Explain with an example.

Show answer

(a) NULLs.

  • Wasted storage when an attribute does not apply to many tuples (e.g. Office_phone of employees without an office).
  • Ambiguous meaning: the attribute does not apply / the value is unknown / it exists but is not recorded yet.
  • Problems in operations: joins on a NULL column drop tuples, COUNT/SUM/AVG ignore NULLs, comparisons give UNKNOWN.
  • Guideline: if many tuples would have NULL in some attributes, move those attributes to a separate relation (with the key); if NULLs are unavoidable they should be exceptions.

Spurious tuples are extra, wrong tuples that appear when relations are joined on attributes that are neither a primary key nor a foreign key — i.e. after a lossy decomposition. Example: R(A, B, C) with A → B split into (A, B) and (B, C); joining on B produces combinations that never existed (section 8.1). Prevention: decompose only so that the common attributes of the two parts are a superkey of at least one part ((R1 ∩ R2)+ ⊇ R1 or R2) — join only on primary-key / foreign-key pairs. 3NF synthesis and BCNF decomposition guarantee this.

(b) An FD is a constraint on all possible legal states, determined by the meaning of the attributes. A particular state shows only the current rows; an FD that happens to be satisfied now may be violated by the next insert. Example: if the Student table currently has Name values all distinct, Name → Roll holds in that state — but two students may have the same name, so Name → Roll is not an FD. A state can disprove an FD (two rows with equal X and different Y) but never prove one.

End-sem 2024 Q4(c)2.5 + 2.5 marks

(i) A university database has a Course table with CourseID, CourseName and ProfessorID. Currently there are no professors assigned to some new courses. Explain how an insertion anomaly could arise and propose a solution. (ii) A hospital database has a PatientTreatment table with PatientID, TreatmentID, PatientName and TreatmentDate. If a patient’s treatment record is deleted, all information about the patient is lost. Describe the deletion anomaly and suggest a normalization strategy.

Show answer

(i) The table mixes facts about courses and about the professor assignment. If professor details are stored in the same table (or the key involves ProfessorID, e.g. (CourseID, ProfessorID) because a course can have several professors), a new course with no professor yet cannot be inserted — part of the key would be NULL — or must be inserted with NULLs. That is an insertion anomaly.

Solution: store each fact in its own relation: Course(CourseID, CourseName) and Teaches(CourseID, ProfessorID) (or Professor(ProfessorID, …) with a nullable FK if one professor per course). A new course is inserted into Course alone; the assignment row is added later. Each relation is in BCNF, and the decomposition is lossless (CourseID is the key of Course).

(ii) With key (PatientID, TreatmentID) and PatientID → PatientName (a partial dependency, so the table is only in 1NF), patient data exist only inside treatment rows. Deleting a patient’s last treatment deletes the patient — a deletion anomaly (and PatientName is repeated per treatment — update anomaly).

Strategy (2NF/3NF): Patient(PatientID, PatientName) and PatientTreatment(PatientID, TreatmentID, TreatmentDate) with PatientID a foreign key. Benefits: the patient survives deletion of treatments, the name is stored once (no update anomaly), and a patient can be registered before any treatment (no insertion anomaly); the join on PatientID is lossless.
