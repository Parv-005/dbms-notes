1Transactions and ACID

Transaction
A transaction is a logical unit of work: a sequence of read/write operations that must be executed as one whole. It ends with commit (make changes permanent) or abort/rollback (undo all its changes). read(X) copies X from disk to a buffer and then to a local variable; write(X) copies the local value to the buffer, and the buffer reaches disk later.

1.1 Transaction states

Active (executing) → Partially committed (last statement done, output still in buffers) → Committed (log forced to disk). Failure from active or partially committed → Failed → Aborted (rolled back). After abort: restart (if the failure was not a logic error) or kill. Committed and aborted are the two terminated states.

1.2 Serial, concurrent, parallel

  • Serial: one transaction runs completely, then the next. Always correct; poor throughput, long waits.
  • Concurrent: operations of several transactions are interleaved on one CPU (while one waits for I/O, another runs). Better throughput and response time, but needs concurrency control.
  • Parallel: operations run at the same instant on multiple CPUs/disks. Concurrency is about interleaving; parallelism is simultaneous execution.

3Schedules and serializability

Key terms
Schedule: the chronological order of operations of a set of transactions, keeping each transaction’s own order. Serial schedule: no interleaving. Serializable schedule: a concurrent schedule equivalent to some serial schedule, so it is correct. With n transactions there are n! serial schedules.

3.1 Conflicting operations

Two operations conflict if they (1) belong to different transactions, (2) access the same item, and (3) at least one is a write. So R–W, W–R and W–W conflict; R–R never does. Swapping two adjacent non-conflicting operations does not change the result.

3.2 Conflict serializability — precedence graph test

  1. One node per transaction.
  2. For every conflicting pair where Ti’s operation comes before Tj’s, add the edge Ti → Tj.
  3. Cycle ⇒ not conflict serializable. No cycle ⇒ conflict serializable; any topological order is an equivalent serial schedule.
Example 1 — cycle
Edges: T1→T2, T1→T3, T2→T1, T2→T3
Cycle: T1 → T2 → T1
⇒ The precedence graph has a cycle, so the schedule is NOT conflict serializable.

r2(B) is before w1(B) (gives T2 → T1), and r1(A) is before w2(A) (gives T1 → T2).

Example 2 — serializable
Edges: T1→T2, T3→T1
No cycle ⇒ the schedule is conflict serializable.
Equivalent serial schedule (topological order): T3 → T1 → T2

T1 → T2 on A; T3 → T1 because w3(B) comes before r1(B).

3.3 View serializability

S and S′ are view equivalent if: (1) the same transaction does the initial read of each item, (2) each read reads the value written by the same writer (reads-from is identical), and (3) the same transaction does the final write of each item. S is view serializable if it is view equivalent to some serial schedule.

  • Every conflict-serializable schedule is view serializable, but not the reverse.
  • A view-serializable schedule that is not conflict serializable always contains a blind write (a write with no read of the item before it).
  • Example: r1(X) w2(X) w1(X) w3(X) is view equivalent to T1 T2 T3 (T3 does the final write), but its graph has a cycle T1 ⇄ T2.
  • Testing view serializability is NP-complete, so conflict serializability is what is used in practice.

4Recoverability

Serializability concerns correctness without failures; recoverability concerns aborts. If Tj reads a value written by Ti, written as “Tj reads from Ti”:

ClassRuleBad example → why
RecoverableIf Tj reads from Ti, then Ti commits before Tj commits.w1(X) r2(X) c2 a1 → T2 committed a dirty value and cannot be undone: non-recoverable.
Cascadeless (ACA)Tj reads X only after the writer Ti has committed. No dirty reads.w1(X) r2(X) r3(X) a1 → T2 and T3 must also abort: cascading rollback.
StrictNo transaction may read or write X until the last writer of X has committed or aborted.w1(X) w2(X) a1 is cascadeless but not strict (undoing T1 would restore a value over T2’s write).

Hierarchy: Strict ⊂ Cascadeless ⊂ Recoverable ⊂ all schedules. Serial schedules are strict. Serializability and recoverability are independent properties: a schedule can be serializable but not recoverable.

How to test a schedule: list every “reads-from” pair (Tj reads X last written by Ti, Ti ≠ Tj). Recoverable: in each pair Ti commits first. Cascadeless: each such read happens after Ti’s commit. Strict: additionally, no write on X happens before the previous writer of X has finished.

5Lock-based concurrency control

Locks
Shared (S) lock, written lock-S(X): read only; many transactions can hold it together. Exclusive (X) lock, written lock-X(X): read and write; only one holder. The lock manager grants a request only if it is compatible with the locks other transactions already hold; otherwise the requester waits.

Upgrade S → X and downgrade X → S are allowed (upgrades only in the growing phase).

Locking alone is not enough: releasing a lock too early (lock-X(A) … unlock(A) … lock-X(B)) still lets another transaction see an inconsistent state. A protocol is needed that says when locks may be released.

5.1 Two-phase locking (2PL) and its variants

2PL: each transaction has a growing phase (it may acquire locks but not release any) followed by a shrinking phase (it may release locks but not acquire any). The moment of the last lock acquisition is the lock point; ordering transactions by lock point gives an equivalent serial order.

ProtocolRuleConflict serializableCascadeless / strictDeadlock-free
Basic 2PLGrowing phase, then shrinking phaseYesNo (cascading rollback possible; may not be recoverable)No
Strict 2PL2PL + hold all X-locks until commit/abortYesStrict, so cascadelessNo
Rigorous 2PL2PL + hold all locks (S and X) until commit/abortYes (serial order = commit order)StrictNo
Conservative (static) 2PLAcquire all locks before the first operation, all or nothingYesNot necessarily (unless combined with strict)Yes (no hold-and-wait)
Common mistake
2PL guarantees conflict serializability but not freedom from deadlock or from cascading rollback. Only conservative 2PL is deadlock-free, and only strict/rigorous 2PL prevent cascading rollback. Rigorous ⊂ strict ⊂ basic 2PL.

6Deadlock and starvation

Deadlock: each transaction in a set waits for a lock held by another in the set (T1 holds A and wants B; T2 holds B and wants A). Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait. Starvation: one transaction waits indefinitely (for example, it is repeatedly chosen as the victim, or S-locks keep being granted ahead of its X request) while the others progress. Fix starvation with FIFO lock queues or by counting rollbacks when choosing the victim.

ApproachHow
PreventionConservative 2PL (lock everything up front); lock items in a fixed order; timestamp schemes:
Wait-die (non-preemptive): an older transaction requesting a lock may wait; a younger one dies (rolls back, restarts with the same timestamp).
Wound-wait (preemptive): an older transaction wounds the younger holder (forces its rollback); a younger one waits.
In both schemes the older transaction is never rolled back, so there is no starvation.
TimeoutRoll back any transaction that waits longer than a limit. Simple, but may roll back transactions that were not deadlocked.
DetectionBuild a wait-for graph (edge Ti → Tj if Ti waits for a lock Tj holds) and check it periodically. A cycle means deadlock.
RecoveryChoose a victim (minimum cost: least work done, fewest locks, fewest rollbacks so far), roll it back (totally or partially), and avoid starvation by including its rollback count in the cost.

6.1 Other protocols beyond syllabus

  • Timestamp ordering: each transaction gets a timestamp TS; each item keeps R-TS and W-TS. A read is rejected if TS < W-TS(X); a write is rejected if TS < R-TS(X) or TS < W-TS(X) (with Thomas’ write rule, an obsolete write is ignored instead). Deadlock-free, but cascading rollback is possible.
  • Validation (optimistic): read phase → validation phase → write phase. Good when conflicts are rare.
  • Multiple granularity: lock a database, table, page or row, using intention locks IS, IX and SIX.
  • Multiversion / snapshot isolation: readers see an old version and never block writers.

7Database recovery

FailureExamplesHandled by
Transaction failureLogical error (bad input, division by zero); system error (deadlock victim)UNDO that transaction
System crashPower failure, OS crash: main memory is lost, disk is safeLog: UNDO uncommitted, REDO committed transactions
Disk (media) failureHead crash: data on disk is lostRestore the latest backup/dump, then REDO from the archived log

Storage: volatile (RAM, lost on a crash) · non-volatile (disk, SSD) · stable storage (in theory never lost; approximated by keeping copies on several disks/sites). The log is kept on stable storage.

7.1 The log

The log is a sequential file of records: <Ti start>, <Ti, X, old value, new value>, <Ti commit>, <Ti abort>. Write-ahead logging (WAL): a log record must reach stable storage before the data page it describes is written to disk, and all of a transaction’s log records, including <commit>, must be on stable storage before it is declared committed. The commit point is the moment the commit record is in the log.

Deferred modificationImmediate modification
When the database is updatedOnly after the transaction commits (writes held in the log/buffers until then)Possibly before commit (written in place)

UNDO and REDO are idempotent: applying them twice (for example, after a crash during recovery) gives the same result. In immediate modification, UNDO is done before REDO.

7.2 Checkpoints

Without checkpoints, recovery would scan the whole log. A checkpoint does three things: (1) write all log records in memory to stable storage, (2) write all modified buffer blocks to disk, (3) write <checkpoint L>, where L is the list of active transactions. On recovery, start from the last checkpoint: transactions that committed before it need nothing; those that committed after it are REDOne; those in L or started after it that have no commit are UNDOne.

Method for “which transactions are undone or redone?” questions
  1. Find the last <checkpoint> before the crash.
  2. Commit before the checkpoint: no action.
  3. Commit between the checkpoint and the crash: REDO (forward pass).
  4. No commit by the crash (active at the checkpoint or started after it): UNDO (backward pass, restore the old values from the log).

7.3 Shadow paging

Keep two page tables. The shadow page table (on disk) is never changed during the transaction; the current page table points to new copies of the modified pages. Commit = atomically switch the root pointer to the current page table. Abort = discard it. No log, so no UNDO and no REDO; but the data becomes fragmented, garbage pages must be collected, commit overhead is high, and it is hard to extend to concurrent transactions.

8Database security

Security vs integrity
Security protects data from unauthorised access, modification or destruction. Integrity keeps data accurate and consistent against mistakes by authorised users (constraints). Security keeps out the wrong people; integrity keeps out wrong values.
CIA triad
Confidentiality: only authorised users can read. Integrity: only authorised, valid changes. Availability: data is accessible when needed (backups, protection against DoS).

Threats: loss of confidentiality, integrity or availability; SQL injection; privilege abuse by insiders; weak authentication; unencrypted backups; malware and denial of service. Control measures: access control, inference control, flow control, encryption. The DBA creates accounts, grants and revokes privileges, assigns security levels and audits.

MechanismKey points
Authentication vs authorizationAuthentication = who are you? (password, OTP, biometrics). Authorization = what may you do? (privileges). Authentication comes first.
DAC (discretionary)The owner grants privileges at their own discretion: GRANT SELECT, UPDATE ON emp TO u1 WITH GRANT OPTION; REVOKE UPDATE ON emp FROM u1 CASCADE;. Revoking cascades to the grants u1 passed on (shown in an authorization graph). Flexible, but cannot control where copied information flows (Trojan horse).
MAC (mandatory)The system assigns security classes to subjects and objects (TS > S > C > U). Bell–LaPadula: no read up (simple security property: read only if class(S) ≥ class(O)) and no write down (*-property: write only if class(S) ≤ class(O)). Used in military and government systems; rigid.
RBAC (role-based)Privileges are granted to roles (clerk, manager); users are assigned roles: CREATE ROLE clerk; GRANT SELECT ON acct TO clerk; GRANT clerk TO asha;. Easy to manage; supports least privilege and separation of duties.
ViewsGrant access to a view that exposes only some rows or columns (for example, hiding salaries).
SQL injectionUser input becomes part of the SQL text: ' OR '1'='1 turns WHERE pwd = '…' into a condition that is always true. Prevent it with parameterised queries / prepared statements, input validation, least-privilege accounts and stored procedures.
EncryptionData at rest (TDE) and in transit (TLS); hash passwords with a salt. Symmetric (AES) or public-key (RSA).
AuditingAn audit trail logs who did what and when; used to detect misuse.
Statistical DB security beyondOnly aggregate queries are allowed, but a series of them can reveal an individual’s value (inference). Counter it with a minimum query-set size, limits on overlap between queries, and added noise.

9Exam checklist

Schedule questions
  1. Write the schedule as r/w operations with transaction subscripts.
  2. Conflict serializable? List the conflicting pairs, draw the precedence graph, look for a cycle; if there is none, give the topological (serial) order.
  3. If it has a cycle, look for blind writes and check view serializability (initial read, reads-from, final write).
  4. Recoverable / cascadeless / strict? List the reads-from pairs and compare them with the commit order.
  5. Possible under 2PL / strict 2PL? Insert lock and unlock instructions and check the phases.
Theory questions
  • ACID: define each property and say which component ensures it (table in §1).
  • Concurrency problems: give the operation pattern plus a numeric example.
  • 2PL variants: draw the lock-count-vs-time sketches and copy the comparison table.
  • Recovery: give the log records, the WAL rule, the UNDO/REDO lists and the checkpoint method.
  • Security: define the term, then DAC/MAC/RBAC with SQL, and SQL injection with a fix.
