4Relational Calculus

4.1 The idea

Definition

Relational calculus is a non-procedural (declarative) formal query language based on first-order predicate logic. A query describes the properties of the tuples wanted — a condition that the answer must satisfy — and says nothing about how to compute it.

Compare the two ways of asking for “names of sailors with rating > 7”:

  • RA (a recipe): first select the rows with rating > 7, then project the name → \pi_{sname}(\sigma_{rating>7}(Sailors)).
  • Calculus (a description): “the set of names n such that some sailor with name n has rating > 7” → { t | \exists s \in Sailors (s.rating > 7 \and t.sname = s.sname) }.

There are two kinds:

  • Tuple Relational Calculus (TRC) — variables stand for whole tuples (rows). SQL is based on TRC.
  • Domain Relational Calculus (DRC) — variables stand for single attribute values (domain elements). QBE (Query-By-Example) is based on DRC.

Key equivalences: \forall x (P(x)) \equiv \not \exists x (\not P(x))  ·  \not(P \and Q) \equiv \not P \or \not Q  ·  \not(P \or Q) \equiv \not P \and \not Q

Free and bound variables. A variable is bound if it is introduced by a quantifier (∃s or ∀s) — it is a local “loop variable”. A variable that is not bound is free. In a calculus query the only free variable must be the result variable written to the left of the bar.

4.3 Tuple relational calculus (TRC)

General form
{ t | P(t) }

“the set of all tuples t for which the formula P(t) is true”. t is a tuple variable; t.A (also written t[A]) is the value of attribute A in t.

Atoms (building blocks of formulas):

  1. s \in R — s is a tuple of relation R;
  2. s.A \theta u.B — compare attributes of two tuple variables, θ ∈ {=, ≠, <, ≤, >, ≥};
  3. s.A \theta c — compare with a constant.

Formulas are built from atoms with ∧, ∨, ¬, ⇒ and the quantifiers \exists s \in R (F), \forall s \in R (F).

Two ways of describing the result tuple

  • Whole tuples of one relation: { t | t \in Sailors \and t.rating > 7 } — t ranges over Sailors, so the result has all four attributes.
  • New tuples (projection / combining tables): t is not bound to any relation; we state the value of each of its attributes, e.g. { t | \exists s \in Sailors (s.rating > 7 \and t.sname = s.sname \and t.rating = s.rating) } — the result has exactly the attributes mentioned for t (sname, rating). This is Korth’s style and what most exams expect.
  • Short-hand used in many books (Navathe, Ramakrishnan): list the output attributes on the left — { s.sname, s.rating | s \in Sailors \and s.rating > 7 }. Accepted in exams; use one style consistently.

Why calculus is immune to the “two Horatios” trap

In P6 and P7 every condition is attached to one sailor variable s, so “red” and “green” must both hold for the same sailor. In RA you had to remember to intersect sids; in calculus it happens naturally.

Writing “for all” correctly

“s reserved every red boat” = for every boat b: if b is red then s reserved b. Two very common mistakes:

  • \forall b \in Boats (b.color = 'red' \and \exists r \ldots) — wrong: demands that every boat is red; false as soon as one blue boat exists. Use ⇒ with ∀.
  • \exists b \in Boats (b.color = 'red' \implies \ldots) — wrong: true for any blue boat (false ⇒ anything is true). Use ∧ with ∃.
Rule of thumb

∃ goes with ∧, ∀ goes with ⇒. And to turn ∀ into something SQL can do, use \forall b (P \implies Q) \equiv \not \exists b (P \and \not Q) — “there is no red boat that s did not reserve” (this is exactly the double NOT EXISTS in section 4.6).

4.4 Safety of expressions

A calculus expression may describe an infinite relation. Example: { t | \not (t \in Sailors) } = “every possible tuple that is not a sailor” — infinitely many, and meaningless. Such expressions are unsafe.

Definition

An expression is safe if every value in its result comes from the domain of the expression — the set of constants appearing in the expression plus the values appearing in the relations it mentions. In practice: bind every variable to a relation (\exists s \in R, \forall s \in R) and never let the result variable range over “anything not in R”.

Only safe expressions are allowed; with this restriction calculus has exactly the power of RA (section 4.7).

4.5 Domain relational calculus (DRC)

General form
{ \langle x1, x2, \ldots, xn \rangle | P(x1, x2, \ldots, xn) }

x1 … xn are domain variables (each stands for one attribute value). Atoms: \langle x1, \ldots, xk \rangle \in R (the values form a tuple of R, in attribute order), x \theta y, x \theta c. Formulas use ∧ ∨ ¬ ⇒ ∃ ∀ as before.

A DRC atom must mention every attribute of the relation (by position). Using the same variable in two atoms expresses a join for free. Below: Sailors ⟨I, N, T, A⟩ (sid, sname, rating, age), Boats ⟨B, BN, C⟩, Reserves ⟨I, B, D⟩.

4.7 Expressive power — Codd’s theorem

{{svg:calc_triangle}}
  • Codd’s theorem: relational algebra, safe tuple relational calculus and safe domain relational calculus are equivalent in expressive power — every query in one can be written in the others.
  • A language with at least this power is relationally complete. SQL is relationally complete and goes beyond (aggregates, ordering, recursion).
  • None of the three (pure forms) can compute aggregates such as SUM, or a transitive closure (“all ancestors”) — that needs extensions.

How calculus questions are asked

The 2025 end-sem gave an Event / Topic / EminentSpeaker / Registration schema and asked “write the relational calculus expressions” for queries like list topic titles handled by speaker ABC from NSUT, find date and speaker of the event whose topic is “Database Handling”, and even rename the relation Event to Event_Detail. Solved answers (TRC, with DRC and RA alternatives) are in section 14.4. Recipe: (1) decide the output attributes; (2) introduce one ∃-variable per table you need; (3) write the join conditions (equal keys) and the selection conditions; (4) assign the output attributes; (5) use ¬∃ for “not”, ∀ … ⇒ for “all”.
