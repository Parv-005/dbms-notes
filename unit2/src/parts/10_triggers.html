10.1 What a trigger is

Definition

A trigger is a named block of procedural code stored in the database that the DBMS executes automatically whenever a specified event occurs on a specified table (or view / schema / database). It follows the ECA model:

  • Event — what fires it: INSERT, UPDATE (optionally of certain columns), DELETE; or a DDL / system event;
  • Condition — optional test (WHEN …); the action runs only if it is true;
  • Action — the SQL / PL/SQL statements executed.

Unlike a stored procedure, a trigger is never called explicitly — the event fires it.

General syntax (Oracle style; MySQL/PostgreSQL are very similar)

CREATE [OR REPLACE] TRIGGER trigger_name
{BEFORE | AFTER | INSTEAD OF}  {INSERT | UPDATE [OF col, ...] | DELETE}  [OR ...]
ON table_name
[REFERENCING OLD AS o NEW AS n]
[FOR EACH ROW]                       -- row-level; omit for statement-level
[WHEN (condition)]
BEGIN
    -- action: SQL statements using :NEW.col and :OLD.col  (MySQL: NEW.col, OLD.col)
END;
  • NEW — the row after the change (available in INSERT and UPDATE triggers). OLD — the row before the change (UPDATE and DELETE). INSERT has no OLD, DELETE has no NEW.
  • A BEFORE row trigger may modify NEW (e.g. convert a name to upper case) before it is stored.
  • To reject the operation, raise an error: Oracle RAISE_APPLICATION_ERROR(-20001, 'msg'), MySQL SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'msg', SQLite SELECT RAISE(ABORT, 'msg').

10.4 Examples

(a) BEFORE (validation) and AFTER (audit) — executed

CREATE TRIGGER trg_no_cut BEFORE UPDATE OF salary ON emp
FOR EACH ROW WHEN NEW.salary < OLD.salary
BEGIN
  SELECT RAISE(ABORT, 'salary cannot be decreased');      -- reject
END;

CREATE TRIGGER trg_audit AFTER UPDATE OF salary ON emp
FOR EACH ROW
BEGIN
  INSERT INTO salary_audit VALUES (OLD.id, OLD.salary, NEW.salary, CURRENT_DATE);
END;

CREATE TRIGGER trg_after_txn
AFTER INSERT ON Transactions
FOR EACH ROW
BEGIN
  IF NEW.trans_type = 'DEPOSIT' THEN
     UPDATE Accounts SET balance = balance + NEW.amount WHERE account_id = NEW.account_id;

     UPDATE Accounts SET balance = balance - NEW.amount WHERE account_id = NEW.account_id;

(c) INSTEAD OF trigger on a view (Oracle)

CREATE VIEW emp_dept_v AS
SELECT e.emp_id, e.name, d.dept_name
FROM   employee e JOIN department d ON d.dept_id = e.dept_id;     -- join view: not directly updatable

CREATE OR REPLACE TRIGGER trg_emp_dept_ins
INSTEAD OF INSERT ON emp_dept_v
FOR EACH ROW
BEGIN
  INSERT INTO employee(emp_id, name, dept_id)
  VALUES (:NEW.emp_id, :NEW.name,
          (SELECT dept_id FROM department WHERE dept_name = :NEW.dept_name));
END;

(d) DDL trigger (Lab exercise 4: “show the use of DDL triggers in response to DDL events”)

-- Oracle: log every CREATE / ALTER / DROP in the schema
CREATE TABLE ddl_log(username VARCHAR2(30), event VARCHAR2(30), obj_name VARCHAR2(60), at_time DATE);

CREATE OR REPLACE TRIGGER trg_ddl_audit
AFTER CREATE OR ALTER OR DROP ON SCHEMA
BEGIN
  INSERT INTO ddl_log VALUES (USER, ORA_SYSEVENT, ORA_DICT_OBJ_NAME, SYSDATE);
END;

-- SQL Server: prevent dropping tables
CREATE TRIGGER trg_no_drop ON DATABASE FOR DROP_TABLE
AS BEGIN
   PRINT 'Dropping tables is not allowed';
   ROLLBACK;
END;

10.5 Use cases, advantages and cautions

Use cases
  • Enforcing complex integrity rules / business rules that CHECK cannot express (multi-table, e.g. “an employee’s salary may not exceed the manager’s”).
  • Auditing — recording who changed what and when.
  • Maintaining derived data — totals, balances, stock levels, denormalised copies.
  • Automatic values — timestamps, generated codes, normalised case.
  • Replication / synchronising tables; sending notifications.
  • Security — blocking operations outside business hours or by certain users; DDL protection.
  • Making views updatable (INSTEAD OF).
Cautions
  • Hidden logic — effects are invisible in the application code; hard to debug.
  • Performance — row-level triggers run for every row of bulk operations.
  • Cascading / recursive triggers — trigger A updates table B whose trigger updates A… can loop (DBMSs limit the depth).
  • Mutating-table errors (Oracle) — a row trigger cannot query the table being modified.
  • Prefer declarative constraints (CHECK, FK) when they suffice — they are faster and clearer.

Trigger vs stored procedure: a procedure is called explicitly (CALL p(…) / EXEC), can take parameters and return values, and can contain COMMIT; a trigger fires implicitly on an event, takes no parameters, and normally cannot COMMIT/ROLLBACK (it runs inside the triggering transaction).

Trigger vs constraint: a constraint (CHECK, FK) is declarative, always enforced on existing and new data, and optimisable; a trigger is procedural and only acts on future events.
