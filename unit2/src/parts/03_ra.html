3Relational Algebra

3.1 What relational algebra is

Definition

Relational algebra (RA) is a procedural, formal query language consisting of a set of operations that take one or two relations as input and produce a new relation as output. A query is written as an expression built from these operations, and the expression also describes the order in which the operations are applied (that is what “procedural” means — you say what you want and how to get it).

  • Closure property: the output of every operation is again a relation, so operations can be nested like arithmetic: \pi_{sname}(\sigma_{rating > 7}(Sailors)). Just as + and × combine numbers, σ, π, ⋈ … combine relations.
  • Set semantics: relations are sets, so results never contain duplicate tuples.
  • Why study it: it is the theoretical foundation of SQL; the DBMS internally translates every SQL query into an RA expression (a query tree) and optimises it by rewriting the expression.

The six fundamental operators are σ, π, ρ, ∪, −, ×: every other operator can be written using them (section 3.10).

3.3 Selection (σ) — choose rows

Definition

\sigma_{P}(R) returns the tuples of R that satisfy the predicate (condition) P. The condition may use attribute names, constants, comparison operators =, ≠, <, ≤, >, ≥ and connectives ∧ (and), ∨ (or), ¬ (not).

{{svg:sel_proj}} {{ra:sel1}} {{ra:sel2}}
  • Degree of the result = degree of R; cardinality ≤ cardinality of R. (The fraction of tuples selected is called the selectivity.)
  • σ is commutative: \sigma_{c1}(\sigma_{c2}(R)) = \sigma_{c2}(\sigma_{c1}(R)), and a cascade of selections can be merged: \sigma_{c1}(\sigma_{c2}(R)) = \sigma_{c1 \and c2}(R).
  • The condition is checked on one tuple at a time. So \sigma_{color='red' \and color='green'}(Boats) is always empty — a single boat cannot have two colours. (“Sailors who reserved a red and a green boat” needs two different tuples — pattern P6 in section 3.14.)

3.4 Projection (π) — choose columns

Definition

\pi_{A1, A2, \ldots, Ak}(R) returns a relation with only the listed attributes of R, in the listed order, with duplicate tuples removed.

{{ra:proj2}}{{ra:proj3}}
  • Degree = number of attributes listed; cardinality ≤ |R| (equal if the list contains a key).
  • \pi_{L1}(\pi_{L2}(R)) = \pi_{L1}(R) when L1 ⊆ L2. π is not commutative in general.
  • σ and π are usually combined: first select the rows, then project the wanted columns:

Duplicates and names

Because π removes duplicates, \pi_{sname}(Sailors) has 9 tuples, not 10. When a question asks about sailors (people) do the logic on the key (sid) and project the names only at the very end — otherwise the two Horatios get merged and answers go wrong (patterns P6, P7).

3.5 Rename (ρ) and assignment (←)

Results of RA expressions have no name. ρ gives a name to a relation and/or its attributes:

  • \rho_{S}(E) — the result of expression E is named S.
  • \rho_{S(B1, B2, \ldots, Bn)}(E) — named S, and its attributes renamed B1 … Bn.
  • \rho_{(B1, \ldots, Bn)}(E) — only attributes renamed.

Example: \rho_{Employee(name, address, phone)}(Student) renames table Student to Employee and its attributes (course PDF).

Why we need it: (1) to join a relation with itself (self-join) — we need two names, e.g. \rho_{S1}(Sailors) and \rho_{S2}(Sailors); (2) to make attribute names match for natural join / union; (3) to name intermediate results.

Assignment T \gets E stores the result of E in a temporary relation T, so a long query can be written in readable steps:

RedBoats \gets \sigma_{color='red'}(Boats) \br RedRes \gets RedBoats \join Reserves \br Answer \gets \pi_{sname}(RedRes \join Sailors)
Exam tip

In exams, writing a long query as 2–4 numbered assignment steps is perfectly acceptable, easier to get right, and easier for the examiner to give marks for.

3.6 Set operations — union (∪), intersection (∩), difference (−)

R and S must be union-compatible (type-compatible): (1) the same number of attributes, and (2) the i-th attribute of R and the i-th attribute of S have the same (compatible) domain. The result takes the attribute names of the first relation. Duplicates are removed.

{{svg:setops}}
{{rel:rs.R}}{{rel:rs.S}}{{ra:union}}{{ra:inter}}{{ra:diff1}}{{ra:diff2}}
  • ∪ and ∩ are commutative and associative; − is neither (R − S ≠ S − R, as the tables show).
  • ∩ is not fundamental: R \cap S = R \minus (R \minus S).
  • Typical use: combine results about the same kind of thing, e.g. \pi_{sid}(\ldots red \ldots) \cap \pi_{sid}(\ldots green \ldots). You can never take the union of Sailors and Boats directly — they are not union-compatible — but you can of two sid-lists.
  • Resource-notes example: \pi_{Name}(Student) \minus \pi_{Name}(Employee) = names of persons who are students but not employees.

3.7 Cartesian product (×)

Definition

R \x S pairs every tuple of R with every tuple of S. Formally R × S = { t q | t ∈ R and q ∈ S }. Degree(R × S) = degree(R) + degree(S); |R × S| = |R| · |S|. Attributes with the same name are distinguished by prefixing the relation name (Emp.dno, Dept.dno).

3.8 Joins

(a) Theta join and equi-join

R \join_{\theta} S = \sigma_{\theta}(R \x S) where θ is a condition such as R.a = S.b or R.a < S.b. When θ uses only equality the join is called an equi-join. Both join columns stay in the result.

{{ra:theta}}

(b) Natural join (⋈)

Definition

R \join S: (1) form R × S; (2) keep only tuples that have equal values on all attributes with the same name in R and S; (3) keep only one copy of each common attribute.

{{ra:natjoin}}
  • Special cases: if R and S have no common attribute, R ⋈ S = R × S. If they have all attributes in common, R ⋈ S = R ∩ S.
  • Natural join is commutative and associative, so Boats \join Reserves \join Sailors needs no brackets.
  • Danger: natural join matches every pair of same-named columns. If Employee and Department both had a column called name, natural join would also require employee.name = department.name — and return almost nothing. Rename first, or use a theta join.

(c) Outer joins — keep the unmatched tuples

An ordinary (inner) join loses tuples that have no partner — Dev (no department) and HR (no employee) above. Outer joins keep them and fill the missing attributes with NULL:

{{svg:join_venn}}
{{ra:ljoin}}{{ra:rjoin}}{{ra:fjoin}}
  • Left outer join ⟕ — all tuples of the left relation; right outer join ⟖ — all of the right; full outer join ⟗ — all of both (= left ⟕ ∪ right ⟖).
  • Use them when the question says “list all departments with their employees, including departments with no employee”.

(d) Semi-join and anti-join beyond syllabus

R \semi S = tuples of R that have at least one match in S (only R’s columns) = \pi_{attrs(R)}(R \join S). R \anti S = tuples of R with no match = R \minus (R \semi S). They correspond to SQL’s EXISTS / NOT EXISTS.

3.9 Division (÷) — the “for ALL” operator

Definition

Let R have attributes X ∪ Y and S have attributes Y. R \div S is the set of X-values x such that for every tuple y in S, the tuple (x, y) is in R:

R \div S = { t[X] | t \in R \and \forall s \in S ( \exists u \in R (u[X] = t[X] \and u[Y] = s[Y]) ) }

Result attributes = attributes of R that are not in S.

When to use division

Whenever the question contains “all”, “every” or “each” in the sense of “related to every one of a set”: students enrolled in all courses, sailors who reserved every red boat, suppliers who supply every red part, customers who ordered every product priced above ₹10,000.

A query language that can express everything the six fundamental operators can express is called relationally complete. SQL is relationally complete (and more, because of aggregates and recursion).

3.11 Extended operators — generalized projection and aggregation

Generalized projection allows arithmetic expressions in the projection list: \pi_{F1, F2, \ldots}(E).

{{ra:gp}}

Aggregation (γ in most books; Korth writes a calligraphic 𝒢): _{G1, \ldots, Gn}\gamma_{F1(A1), \ldots, Fk(Ak)}(E) partitions E into groups having equal values on the grouping attributes G1…Gn (written on the left), and outputs one tuple per group with the aggregate values. Aggregate functions: count, sum, avg, min, max (and count-distinct). Without grouping attributes the whole relation is one group.

3.15 Checklist of common mistakes

  1. Intersecting / subtracting names instead of keys (P6, P7). Work with sid, project sname last.
  2. One σ with “color = red ∧ color = green” — always empty (P6).
  3. Dividend not projected before ÷ (3.9).
  4. Natural join on unintended common attributes — e.g. two tables both having name. Rename first or use ⋈θ.
  5. Union/difference of incompatible relations — both sides must have the same number of attributes with matching domains.
  6. Forgetting ρ in a self-join — you cannot write Sailors.age < Sailors.age.
  7. Using aggregate functions in “basic RA” when the question says “using relational algebra (without aggregates)” — use P12 instead.
  8. Projecting too early — after πsname you can no longer join on sid.
How to write an RA answer in the exam
  1. Write the schema abbreviations you will use. 2. If the query is long, use numbered assignment steps (T1 ← …). 3. Put conditions inside the σ subscript, attribute lists inside the π subscript. 4. For “all” use ÷ (and say “division because of all”), for “not” use −. 5. One line of explanation per step earns method marks even if a small detail is wrong.
