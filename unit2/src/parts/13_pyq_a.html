14.1 Relational model, keys and NULL

Mid-Sem Sep 2024Q3(b)2 marks

Discuss the four reasons that lead to the occurrence of NULL values in a relation.

Show answer

NULL is a special marker meaning “no value is stored”; it is different from 0 or a blank. It occurs because:

  1. Value unknown — it exists but is not known now. E.g. DOB of a patient brought in unconscious.
  2. Value not applicable — the attribute does not apply to that tuple. E.g. spouse_name of an unmarried employee; maiden_name of a man.
  3. Value not yet available / not yet assigned — it will exist later. E.g. grade of a course in progress, dept_id of a newly joined employee.
  4. Value withheld / not recorded — it exists but is intentionally not stored (privacy) or was missed at entry. E.g. a customer who declines to give a phone number.

(NULLs also arise from outer joins and from adding a new column with ALTER TABLE.) Since a comparison with NULL is UNKNOWN, NULLs must be tested with IS NULL, and aggregate functions ignore them.

Mid-Sem Oct 2021Q3(b)4 marks

Consider a relation R(A, B, C, D, E). If (A) and (BC) are the candidate keys of R, find the number of super keys and list them.

Show answer

A super key must contain at least one candidate key.

  • Super keys containing A: A is fixed, each of B, C, D, E may be in or out ⇒ 24 = 16.
  • Super keys containing BC: B, C fixed, A, D, E free ⇒ 23 = 8.
  • Counted twice (contain A and BC): A, B, C fixed, D, E free ⇒ 22 = 4.

Number of super keys = 16 + 8 − 4 = 20.

List. Containing A (16): A, AB, AC, AD, AE, ABC, ABD, ABE, ACD, ACE, ADE, ABCD, ABCE, ABDE, ACDE, ABCDE.
Containing BC but not A (4): BC, BCD, BCE, BCDE.

14.2 Integrity constraints and referential integrity

End-Sem 2023Q2(c)4 marks

What are integrity constraints? How are they useful? Explain any 4 integrity constraints with the help of suitable examples and syntax.

Show answer

Integrity constraints are rules defined on the database schema that every valid database state must satisfy. The DBMS checks them on every INSERT, UPDATE and DELETE and rejects any operation that violates them.

Usefulness: keep data accurate and consistent; prevent duplicates, missing mandatory values and dangling references; defined once in the schema instead of in every program; cannot be bypassed by applications.

  1. Domain constraint (NOT NULL, CHECK, data type, DEFAULT) — each value must come from the attribute’s domain. 
    age    INT CHECK (age BETWEEN 16 AND 40),
name   VARCHAR(40) NOT NULL
    INSERT … age = 12 or a NULL name is rejected.
  2. Key constraint (PRIMARY KEY / UNIQUE) — no two tuples have the same key value. 
    roll_no INT PRIMARY KEY,
email   VARCHAR(50) UNIQUE
    A second student with roll_no 1 is rejected.
  3. Entity integrity — no primary-key attribute may be NULL (a NULL key cannot identify a tuple). Enforced automatically by PRIMARY KEY.
  4. Referential integrity (FOREIGN KEY) — a foreign-key value must match an existing primary-key value of the referenced table, or be NULL. 
    dept_id INT REFERENCES department(dept_id) ON DELETE SET NULL
    Inserting a student with dept_id 99 when no department 99 exists is rejected; deleting a department sets its students’ dept_id to NULL.

Mid-Sem Sep 2024Q3(a)2 marks

Discuss the role of a foreign key constraint in maintaining referential integrity. By providing a referential integrity constraint, what happens when an update or delete or insert operation is performed on a table?

Show answer

A foreign key is an attribute of a child (referencing) table whose values must match the primary key of a parent (referenced) table or be NULL. It ensures that every reference points to a row that really exists — no dangling references — which is referential integrity. E.g. employee.dept_id REFERENCES department(dept_id).

  • INSERT into child (or UPDATE of the FK) with a value not present in the parent → rejected. Inserting into the parent is always fine.
  • DELETE from parent of a row that is referenced → action given by ON DELETE: RESTRICT/NO ACTION (default) rejects the delete; CASCADE deletes the child rows too; SET NULL sets the child FKs to NULL; SET DEFAULT sets them to the default. Deleting a child row is always fine.
  • UPDATE of the parent’s PK that is referenced → action given by ON UPDATE (RESTRICT / CASCADE — child FKs changed to the new value / SET NULL).
FOREIGN KEY (dept_id) REFERENCES department(dept_id)
    ON DELETE CASCADE ON UPDATE CASCADE
Mid-Sem Sep 2026Q2(a)2 marks

What is the role of a Foreign Key in maintaining referential integrity? How is the referential integrity constraint applied in an SQL query?

Show answer

Role: a foreign key links a child table to a parent table; the DBMS guarantees every FK value equals some existing PK value of the parent (or is NULL). Hence an order cannot belong to a non-existent customer, and a customer who still has orders cannot be silently deleted.

Applying it in SQL — column level, table level, or later with ALTER TABLE, optionally with referential actions:

CREATE TABLE customer (cust_id INT PRIMARY KEY, name VARCHAR(40));

CREATE TABLE orders (
  order_id INT PRIMARY KEY,
  cust_id  INT,
  CONSTRAINT fk_ord_cust FOREIGN KEY (cust_id)
      REFERENCES customer(cust_id)
      ON DELETE CASCADE           -- delete a customer ⇒ delete his orders
      ON UPDATE CASCADE
);

ALTER TABLE orders ADD CONSTRAINT fk_ord_cust2
      FOREIGN KEY (cust_id) REFERENCES customer(cust_id);   -- adding it later

Then INSERT INTO orders VALUES (1, 999); fails if customer 999 does not exist.

End-Sem 2025 (ITITC05)Q2(b)4 marks

Explain referential integrity constraint. Assume that a row in the parent table, whose primary key value = 5, is deleted. Discuss in detail what consequence this deletion has on the child table under the referential integrity constraint.

Show answer

Referential integrity: if FK of child relation R1 references PK of parent R2, then for every tuple t1 of R1, t1[FK] is NULL or t1[FK] = t2[PK] for some tuple t2 of R2.

Let parent department(dept_id PK) and child employee(emp_id, dept_id FK), and suppose employees E1, E3 have dept_id = 5. DELETE FROM department WHERE dept_id = 5;

  • If no child row has FK = 5: the delete simply succeeds; the child table is unaffected.
  • ON DELETE RESTRICT / NO ACTION (default): the delete is rejected with an error because E1 and E3 still refer to 5; both tables unchanged. The user must first delete/reassign those employees.
  • ON DELETE CASCADE: department 5 is deleted and E1 and E3 are deleted automatically (and, if other tables reference E1/E3 with CASCADE, the deletion continues down the chain).
  • ON DELETE SET NULL: department 5 is deleted; E1 and E3 remain with dept_id = NULL (allowed only if the column is nullable).
  • ON DELETE SET DEFAULT: E1 and E3 get the column default (e.g. 0 = “unassigned”), which must itself exist in the parent.
{{svg:fk_actions}}

In every case the database never ends up with a child row pointing to the deleted key 5 — that is the guarantee of referential integrity.

End-Sem 2024Q2(a)(i)2.5 marks

The following table has two attributes A and C where A is the primary key and C is the foreign key referencing A with on-delete cascade. Tuples (A, C): (2,4), (3,4), (4,3), (5,2), (7,2), (9,5), (6,4). Justify the set of all tuples that must be additionally deleted to preserve referential integrity when the tuple (2,4) is deleted.

Show answer

C references A in the same table with ON DELETE CASCADE, so deleting a tuple with A = x deletes every tuple whose C = x, and so on recursively.

  1. Delete (2,4). Tuples with C = 2: (5,2) and (7,2) → deleted.
  2. (5,2) deleted ⇒ tuples with C = 5: (9,5) → deleted.
  3. (7,2) deleted ⇒ tuples with C = 7: none. (9,5) deleted ⇒ tuples with C = 9: none. Chain stops.
{{svg:cascade_chain}}

Additionally deleted: (5,2), (7,2), (9,5). Remaining: (3,4), (4,3), (6,4).

(The remaining tuples are consistent: C = 4 and C = 3 refer to A = 4 and A = 3, which still exist.)

Mid-Sem Oct 2021Q2(c)4 marks

Explain the concept of referential integrity constraint. Write an SQL query to apply referential integrity constraint on the relations Worker(Worker_Id, First_name, salary, joining_date, department) and Title(Worker_ref_id, Worker_title, affected_from).

Show answer

Referential integrity requires that a foreign-key value in the referencing table either be NULL or match an existing primary-key value in the referenced table, so that no row refers to a non-existent row. Here Title.Worker_ref_id must refer to an existing Worker.Worker_Id.

CREATE TABLE Worker (
  Worker_Id     INT          PRIMARY KEY,
  First_name    VARCHAR(30)  NOT NULL,
  salary        INT          CHECK (salary > 0),
  joining_date  DATE,
  department    VARCHAR(20)
);
CREATE TABLE Title (
  Worker_ref_id INT          NOT NULL,
  Worker_title  VARCHAR(30)  NOT NULL,
  affected_from DATE,
  PRIMARY KEY (Worker_ref_id, Worker_title, affected_from),
  CONSTRAINT fk_title_worker FOREIGN KEY (Worker_ref_id)
      REFERENCES Worker(Worker_Id)
      ON DELETE CASCADE ON UPDATE CASCADE
);
-- or, if Title already exists:
ALTER TABLE Title ADD CONSTRAINT fk_title_worker
      FOREIGN KEY (Worker_ref_id) REFERENCES Worker(Worker_Id) ON DELETE CASCADE;

Effect: a title for worker 42 cannot be inserted unless worker 42 exists; deleting a worker deletes his title rows.

Mid-Sem Sep 2025Q4(b)2 marks

From the previous question, suppose a student with StudentID = S101 is deleted from the database. What referential action should be enforced on the Enrollment table (CASCADE / SET NULL / RESTRICT) to maintain data integrity? Justify your choice.

Show answer

ON DELETE CASCADE is the appropriate action (with RESTRICT as the safer alternative if records must be preserved).

  • An Enrollment row only describes a relationship between a student and a course; it has no meaning without its student (it is existence-dependent, like a weak entity). When S101 is removed, S101’s enrollment rows should go too → CASCADE.
  • SET NULL is not acceptable: StudentID in Enrollment is NOT NULL and part of the UNIQUE (StudentID, CourseID, Semester) rule; an enrollment “of nobody” is meaningless and would violate those constraints.
  • RESTRICT would refuse to delete S101 while enrollments exist. Use it if the university must keep academic records (transcripts) permanently — then students are never physically deleted, only marked inactive.
FOREIGN KEY (StudentID) REFERENCES Student(StudentID) ON DELETE CASCADE

Mid-Sem Sep 2024Q4(b)2 marks

Sailors(sid, sname, rating, age), Boats(bid, bname, color), Reserves(sid, bid, date). Write in relational algebra: 1. names of sailors who have not reserved a red boat; 2. names of sailors who have reserved at least two boats; 3. names of sailors who have reserved all boats; 4. name and age of the oldest sailor.

Show answer

1. Not reserved a red boat (all sailors − those who did; subtract sids, not names):

RedSids \gets \pi_{sid}(\sigma_{color='red'}(Boats) \join Reserves) \br Result \gets \pi_{sname}((\pi_{sid}(Sailors) \minus RedSids) \join Sailors)

2. At least two (different) boats (self-join of Reserves):

\pi_{sname}(\pi_{R1.sid}(\rho_{R1}(Reserves) \join_{R1.sid = R2.sid \and R1.bid \ne R2.bid} \rho_{R2}(Reserves)) \join Sailors)

3. All boats (division):

\pi_{sname}((\pi_{sid, bid}(Reserves) \div \pi_{bid}(Boats)) \join Sailors)

4. Oldest sailor (all sailors − those younger than someone):

Younger \gets \pi_{S1.sid}(\rho_{S1}(Sailors) \join_{S1.age < S2.age} \rho_{S2}(Sailors)) \br Result \gets \pi_{sname, age}((\pi_{sid}(Sailors) \minus Younger) \join Sailors)

(With aggregation: \pi_{sname, age}(Sailors \join_{age = m} \gamma_{max(age) \to m}(Sailors)).)

Schemas for an event “5-day workshop on Qiskit”: Event(EventId, EventName, Organizer, EventDept, Location, Date, Emailid, Phone, Address), Topic(TopicId, EventId, TopicTitle, Date, TimeDuration), EminentSpeaker(EventId, TopicId, SpeakerName, Institution, TopicTitle), Registration(ParticipantId, ParticipantName, EventId, ParticipantInstitution, Fee, Category). Write the relational calculus expressions for: a. renaming the relation “Event” into “Event_Detail” [1M]; b. list Topic-Title handled by the eminent speaker “ABC” who belongs to the institution “NSUT” [1M]; c. find date and eminent speaker name of the event reserved for the topic title “Database Handling” [2M]; d. find all the participant names who have registered their category as “PG Student” [1M].

Show answer

Tuple relational calculus is used; the DRC form is given as an alternative.

(a) Rename Event to Event_Detail

Relational calculus has no rename operator — a query simply defines a new relation, so we define Event_Detail as the set of all Event tuples:

Event\_Detail = { t | t \in Event }

(In relational algebra this is \rho_{Event\_Detail}(Event); in SQL ALTER TABLE Event RENAME TO Event_Detail;)

(b) Topic titles handled by speaker ABC of NSUT

{ t | \exists s \in EminentSpeaker (s.SpeakerName = 'ABC' \and s.Institution = 'NSUT' \and t.TopicTitle = s.TopicTitle) }

DRC: { \langle TT \rangle | \exists E, T (\langle E, T, 'ABC', 'NSUT', TT \rangle \in EminentSpeaker) }

(c) Date and speaker name for topic “Database Handling”

The topic’s date is in Topic, the speaker in EminentSpeaker; join them on TopicId (and EventId):

{ t | \exists p \in Topic \exists s \in EminentSpeaker (p.TopicTitle = 'Database Handling' \and s.TopicId = p.TopicId \and s.EventId = p.EventId \and t.Date = p.Date \and t.SpeakerName = s.SpeakerName) }

DRC: { \langle D, N \rangle | \exists T, E, TD (\langle T, E, 'Database Handling', D, TD \rangle \in Topic \and \exists I, TT (\langle E, T, N, I, TT \rangle \in EminentSpeaker)) }

(If “date of the event” is meant, take D from Event instead: add \exists e \in Event (e.EventId = p.EventId \and t.Date = e.Date).)

(d) Participants registered as “PG Student”

{ t | \exists r \in Registration (r.Category = 'PG Student' \and t.ParticipantName = r.ParticipantName) }

DRC: { \langle N \rangle | \exists P, E, I, F (\langle P, N, E, I, F, 'PG Student' \rangle \in Registration) }

End-Sem 2025 (ITITC05)Q2(c)4 marks

What is the difference between relational algebra and relational calculus? What are aggregate functions in SQL?

Show answer

Relational algebra vs relational calculus

Relational algebraRelational calculus
procedural — specifies what to retrieve and the sequence of operationsnon-procedural (declarative) — specifies only what to retrieve
based on set theory / algebra of operatorsbased on first-order predicate logic
queries are expressions of operators σ, π, ρ, ∪, −, ×, ⋈, ÷queries are formulas {t | P(t)} (TRC) or {⟨x1..xn⟩ | P} (DRC) with ∃, ∀, ∧, ∨, ¬
order of evaluation fixed by the expressionno order specified
always finite (safe) resultsunsafe expressions possible; restricted to safe ones
“for all” via division ÷“for all” via ∀
e.g. \pi_{name}(\sigma_{age>20}(Student))e.g. { t | \exists s \in Student (s.age > 20 \and t.name = s.name) }

Both have the same expressive power (Codd’s theorem, for safe calculus); RA is closer to query execution plans, TRC to SQL.

Aggregate functions

Functions that take a set of values (a column of a group of rows) and return a single summary value: COUNT, SUM, AVG, MIN, MAX. Syntax FUNC([DISTINCT] column); used in SELECT and HAVING, usually with GROUP BY; all ignore NULLs except COUNT(*).

SELECT dept_id, COUNT(*) AS n, AVG(salary) AS avg_sal, MAX(salary) AS top
FROM   employee
GROUP  BY dept_id
HAVING COUNT(*) >= 3;

Output on the sample DB: dept 10 → 3 employees, dept 20 → 4 (section 7.3).
