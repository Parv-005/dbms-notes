11.1 What NoSQL is and why it appeared

Definition

NoSQL (“Not only SQL”) is a family of non-relational database systems that store data in models other than tables — key-value pairs, documents, wide columns or graphs — and are designed for flexible (schema-less) data, very large volumes and horizontal scaling across many commodity machines.

Why it appeared (mid-2000s, Google BigTable 2006, Amazon Dynamo 2007): web-scale companies faced

  • Big data — the 3 V’s: huge volume, high velocity (millions of writes per second), great variety (semi-structured and unstructured data: JSON, logs, posts, images, sensor readings).
  • Changing structure — social-media posts with optional photos/videos/polls/tags; product catalogues whose attributes differ by category. A fixed relational schema needs ALTER TABLE for every change.
  • Scaling limits — an RDBMS scales mainly vertically (bigger server); joins and ACID across many machines are expensive.
  • Availability — a global service must keep answering even when some servers or network links fail.

Example: why an online shop needs flexibility prof’s handout

An online shop stores customer details, product information, shopping carts, customer reviews and order history. Products do not all have the same attributes: a mobile phone has RAM and storage, a shirt has size and colour. In one relational product table this means many NULL columns, or a new column with ALTER TABLE for every new category. A NoSQL document store simply gives each product the fields it needs:

{ "_id": 1, "name": "Galaxy M35", "price": 15999, "ram": "8 GB", "storage": "128 GB" }
{ "_id": 2, "name": "Linen shirt", "price": 1299, "size": "M", "colour": "blue" }
Important

NoSQL does not mean “no SQL” or that SQL is eliminated. It means “Not Only SQL”: alternative approaches used alongside relational databases.

11.2 Features of NoSQL databases

  • Flexible / dynamic schema (schema-on-read) — records in the same collection may have different fields; no ALTER needed.
  • Horizontal scalability — data is sharded (partitioned) across nodes; add nodes to add capacity.
  • Replication and fault tolerance — copies on several nodes; no single point of failure.
  • High performance for simple operations by key; data that is read together is stored together (denormalised, aggregate-oriented), so few or no joins.
  • BASE instead of strict ACID (most systems; many now offer ACID for single documents or even multi-document transactions).
  • Usually open source, often accessed through APIs rather than SQL (each has its own query language: MongoDB Query Language, CQL for Cassandra, Cypher for Neo4j).

11.4 CAP theorem and BASE

{{svg:cap}}
ACID (RDBMS)

Atomicity, Consistency, Isolation, Durability — every committed transaction is all-or-nothing and immediately visible to everyone. Pessimistic: correctness first.

BASE (most NoSQL)

Basically Available — the system always answers (maybe with partial/stale data); Soft state — data may change over time even without input, as replicas synchronise; Eventually consistent — if no new updates arrive, all replicas eventually hold the same value. Optimistic: availability first.

Which one should we use? prof’s handout

SQL: structured data, relationships and reliable transactions, e.g. banking and financial systems. NoSQL: large amounts of varied or rapidly changing data, e.g. social media, real-time applications, recommendation systems. Neither is universally better; the choice depends on the application’s requirements.

How to answer “which database would you choose and why?”

These questions (e-commerce like Amazon, social-media content, product reviews + transactions) almost always have the answer polyglot persistence — use both: an RDBMS for data needing ACID and integrity (orders, payments, inventory, user accounts) and NoSQL for high-volume, variable or read-heavy data (product catalogue → document store, carts/sessions → key-value, reviews/browsing history/clickstream → document or wide-column, recommendations → graph). Justify each choice by one property from the table (schema flexibility, horizontal scaling, ACID, joins). Full model answers are in section 14.7.

11.6 Popular NoSQL databases used in real life prof’s handout

Each popular product is built for one way of storing data. Know these three with their type, one example and uses.

MongoDB — document database
  • Stores data as documents in a JSON-like format (internally BSON). Each document has a unique _id.
  • A group of related documents is a collection (≈ a table); documents in one collection may have different fields.
  • Example: an e-commerce product catalogue: one product has size and colour, another has RAM and storage.
  • Used for: e-commerce sites, content management systems, mobile apps, product catalogues.
  • Why useful: flexible structure when different records have different fields.
db.products.insertOne(
  { name: "Shirt", size: "M" })
db.products.find(
  { price: { $lt: 2000 } })
Redis — key-value database
  • An in-memory data store: data is kept mainly in RAM, so access is very fast.
  • Stores key → value pairs; a value is retrieved directly by its key.
  • Example: a website stores your login session in Redis, so it can check it quickly on every page without going to the main database.
  • Used for: caching frequently used data, user session management, real-time applications, gaming (leaderboards).

Apache Cassandra — wide-column database
  • A distributed database that spreads huge amounts of data across many servers, with no single master (no single point of failure).
  • Organises data in rows with flexible groups of columns: different rows may have different columns.
  • Example: a social-media platform where millions of users create posts, comments and activity records every second. Cassandra spreads this workload over many servers.
  • Used for: large-scale data management, activity and event tracking, IoT, distributed applications.
  • Why useful: high availability, distributed storage and horizontal scalability.

11.8 Challenges and limitations of NoSQL prof’s handout

  1. Lack of standardisation: there is no common query language like SQL. Each NoSQL database has its own data model and query method, so learning and switching between them is hard.
  2. Data consistency: distributed NoSQL systems often put availability and performance before immediate consistency (eventual consistency, BASE). An update may not be visible on every server at the same moment.
  3. Complex relationships: relationships and multi-table joins are not handled as conveniently as in relational databases; they need extra application code or a different data design.
  4. Data duplication (denormalisation): for speed, the same data is often stored in several places. Updating every copy is harder, and copies can become inconsistent (the update anomaly of Unit 4).

Other commonly cited limits: weaker or limited multi-record transactions (ACID) in many systems, integrity constraints left to the application, fewer mature tools and experts.

Exam: “advantages and limitations of NoSQL” (5 marks)

Advantages: flexible schema · horizontal scalability · high availability through replication · fast simple reads/writes at huge volume · handles structured, semi-structured and unstructured data. Limitations: the four points above. Add one real database per point (e.g. MongoDB for flexible schema, Cassandra for scaling, Redis for speed).
