1Structure of Relational Databases

1.1 The relational model and RDBMS

A data model is a set of concepts used to describe the structure of a database (data, relationships, constraints) and the operations on it. In Unit 1 you met the hierarchical (tree) and network (graph) models. The relational model, proposed by Dr. E. F. Codd (IBM, 1970), represents everything — both data and the relationships between data — as tables, which mathematically are relations.

Definition

Relational model: a data model in which the database is a collection of relations (tables); each relation has a fixed set of named columns (attributes) and a set of rows (tuples); relationships between relations are represented by matching values (keys and foreign keys) rather than by pointers.

RDBMS (Relational DataBase Management System): a DBMS based on the relational model — Oracle, MySQL, PostgreSQL, Microsoft SQL Server, IBM DB2, SQLite, MS Access. All of them use SQL as their language.

Why it won over the older models:

  • Simple — users see only tables, no pointers or physical paths.
  • Data independence — queries say what data is needed, not how to navigate to it, so the storage can change without changing programs.
  • Solid mathematical foundation — set theory and first-order logic (relational algebra and calculus, sections 3–4), which makes query optimisation possible.
  • Powerful declarative language (SQL) and built-in integrity constraints (section 2).

Mathematical definition

Let D1, D2, …, Dn be the domains of attributes A1, …, An. A relation r on schema R(A1, …, An) is a subset of the Cartesian product D1 × D2 × … × Dn. Each tuple t = ⟨v1, …, vn⟩ has vi ∈ Di (or NULL). We write t[A] or t.A for the value of attribute A in tuple t.

This is why the model is called relational: a table is a mathematical relation (a set of ordered n-tuples) — not because tables are “related” to each other.

Schema vs instance — an analogy

The schema is like the declaration of a variable (int marks[60]), the instance is its current value. The schema of STUDENT stays the same all semester; the instance changes every time a student is admitted or leaves.

1.3 Properties (characteristics) of relations

  1. Each relation has a distinct name within the database.
  2. Each cell contains exactly one atomic (indivisible) value — no lists, no sets, no nested tables. (This is the First Normal Form, studied in Unit 4.) A student’s three phone numbers cannot be stored in one cell.
  3. Attribute names are distinct within a relation, and all values in one column come from the same domain.
  4. No two tuples are identical — a relation is a set, so duplicates are not allowed. Consequence: every relation has at least one key (at worst, the set of all its attributes).
  5. The order of tuples is irrelevant — tuples are identified by their values, not by their position (“row 3” has no meaning).
  6. The order of attributes is irrelevant as long as each value is referred to by its attribute name.
Correction (course PDF p. 70)

The PDF lists “Attribute domain has no significance” and “Tuple has no duplicate value”. The intended (and correct) properties are “the order of attributes has no significance” and “a relation has no duplicate tuples”. A single tuple may of course contain the same value twice (e.g. ⟨5, 5⟩).

SQL tables vs relations

A SQL table is a multiset (bag): unless you declare a PRIMARY KEY or UNIQUE constraint, it may contain duplicate rows, and SELECT keeps duplicates unless you write DISTINCT. Relational algebra (pure theory) never has duplicates.

1.4 NULL values

NULL is a special marker meaning “no value is stored here”. It is not zero, not an empty string and not a space.

Reasons for the occurrence of NULL values in a relation PYQ Mid-Sem 2024

  1. Value unknown — a value exists but is not known at present. Example: a patient’s date of birth is not known at admission.
  2. Value not applicable / does not exist — the attribute does not apply to this tuple. Example: spouse_name of an unmarried employee; apartment_no for someone living in an independent house.
  3. Value not yet available — it will exist later. Example: grade of a course still in progress; return_date of a book not yet returned.
  4. Value withheld / not recorded — it exists but has been deliberately left out (privacy, missing information at entry time). Example: a customer who refused to give a phone number.

NULLs also appear mechanically: when a column is added with ALTER TABLE … ADD (existing rows get NULL), when an INSERT does not mention a column that has no DEFAULT, and in the result of an outer join (padding).

Why NULLs cause trouble

  • Any comparison with NULL (=, <, >, <>) gives UNKNOWN, not TRUE/FALSE ⇒ SQL uses three-valued logic (section 6.3). Hence WHERE x = NULL never matches — you must write x IS NULL.
  • Aggregate functions ignore NULLs (AVG(salary) averages only the non-NULL salaries) — results may surprise you (section 7.1).
  • Ambiguity: a NULL does not tell you which of the four meanings applies.
  • NOT IN with a sub-query that returns a NULL returns no rows at all (section 9.4).

Good design therefore avoids NULLs where possible: use NOT NULL, sensible DEFAULTs, or move optional attributes to a separate table.

1.5 Keys

A key is an attribute or a set of attributes whose values uniquely identify each tuple of a relation. Keys also connect relations (foreign keys).

{{svg:keys_venn}}
Definitions
  • Super key — any set of attributes that uniquely identifies every tuple: no two distinct tuples can ever have the same values on it. It may contain extra, unnecessary attributes.
  • Candidate key — a minimal super key: no proper subset of it is a super key. A relation may have several candidate keys.
  • Primary key (PK) — the one candidate key chosen by the designer to identify tuples. Its values must be unique and never NULL; there is exactly one PK per relation. Shown underlined in a schema.
  • Alternate (secondary) key — every candidate key that was not chosen as the primary key. (Alternate = Candidate − Primary.)
  • Composite (compound) key — a key made of two or more attributes, e.g. (sid, cid) in ENROLLMENT.
  • Foreign key (FK) — an attribute (set) in one relation whose values must match the primary key (or a UNIQUE key) of another (or the same) relation, or be NULL. It implements relationships and is the basis of referential integrity (section 2.4).
Worked example (from the resource notes)

EMPLOYEE(Emp_Id, Name, Aadhaar_No, Email_Id, Dept) with tuples (01, Aman, 7757…, a@gmail.com, 1), (02, Chirag, 4567…, c@gmail.com, 2), (03, Chirag, 8967…, ch@gmail.com, 2), (04, Dev, 7964…, d@gmail.com, 3).

  • Super keys: {Emp_Id}, {Aadhaar_No}, {Email_Id}, {Emp_Id, Name}, {Emp_Id, Aadhaar_No}, {Aadhaar_No, Email_Id}, {Emp_Id, Name, Email_Id}, … (any set containing at least one of the three unique attributes).
  • Candidate keys: {Emp_Id}, {Aadhaar_No}, {Email_Id}. {Name} is not even a super key (two Chirags); {Emp_Id, Name} is a super key but not minimal.
  • Primary key: Emp_Id (short, stable, never changes). Alternate keys: Aadhaar_No, Email_Id.
  • Foreign key: Dept → DEPARTMENT(Dept_No).
Correction (course PDF p. 54)

The PDF gives “C2 → S_Rollno, S_Name” as a candidate key of STUDENT. Since S_Rollno alone is already a key, {S_Rollno, S_Name} is not minimal — it is a super key, not a candidate key. Also, “primary key = the minimum number of candidate keys” should read: the primary key is one of the candidate keys, chosen by the designer.

Facts about foreign keys that exams test

  • An FK may have a different name from the PK it references (Employee.dept → Department.dept_no) but must have the same domain.
  • An FK value need not be unique (many employees work in one department) and may be NULL (employee not yet assigned) unless declared NOT NULL.
  • An FK may reference its own relation — a self-referencing (recursive) FK, e.g. Employee.manager_id → Employee.emp_id.
  • An FK can be part of a primary key: in ENROLLMENT(sid, cid, grade), sid and cid are both FKs and together form the PK.

Counting super keys frequently asked

For a relation with n attributes:

  • If there is a single candidate key with k attributes: every super key = that key + any subset of the other n − k attributes ⇒ 2n−k super keys.
  • With two candidate keys K1, K2 use inclusion–exclusion: |S(K1)| + |S(K2)| − |S(K1 ∪ K2)| = 2n−|K1| + 2n−|K2| − 2n−|K1∪K2|.
Example — PYQ Mid-Sem 2021, Q3(b)

R(A, B, C, D, E) has candidate keys (A) and (BC). Number of super keys?

Super keys containing A: 25−1 = 16. Containing B and C: 25−2 = 8. Containing A, B and C (counted twice): 25−3 = 4. Total = 16 + 8 − 4 = 20.

List: the 16 supersets of A — A, AB, AC, AD, AE, ABC, ABD, ABE, ACD, ACE, ADE, ABCD, ABCE, ABDE, ACDE, ABCDE — plus the supersets of BC that do not contain A — BC, BCD, BCE, BCDE (4 more). 16 + 4 = 20 ✔.

1.6 Codd’s 12 rules

In 1985 Codd published 12 rules (numbered 1–12, plus a “Rule 0”) that a DBMS must satisfy to be called fully relational. No commercial product satisfies all of them; they are a yardstick.

#RuleWhat it says (one line)
0Foundation ruleThe system must manage its databases entirely through its relational capabilities.
1Information ruleAll information — data and metadata — is represented only as values in tables.
2Guaranteed accessEvery value is reachable by table name + primary-key value + column name.
3Systematic treatment of NULLNULLs are supported uniformly for “missing / unknown / not applicable”, distinct from 0 or blank.
4Active online catalogThe description of the database (data dictionary) is stored as tables and queried with the same language.
5Comprehensive data sub-languageOne language must support data definition, manipulation, integrity, authorisation and transactions (SQL).
6View updatingAll views that are theoretically updatable must be updatable by the system.
7High-level insert, update, deleteInsert/update/delete must work on sets of rows, not just one row at a time.
8Physical data independenceChanging storage/access methods must not affect applications.
9Logical data independenceChanging table structure (e.g. splitting a table) must not affect applications that do not use the change.
10Integrity independenceIntegrity constraints are defined in the data sub-language and stored in the catalog, not in application programs (PK not NULL, FK values must exist).
11Distribution independenceUsers should not see whether data is distributed over several sites.
12Non-subversionA low-level (record-at-a-time) interface must not be able to bypass integrity rules.
