1Structure of Relational Databases

1.1 The relational model and RDBMS

A data model is a set of concepts used to describe the structure of a database (data, relationships, constraints) and the operations on it. In Unit 1 you met the hierarchical (tree) and network (graph) models. The relational model, proposed by Dr. E. F. Codd (IBM, 1970), represents everything — both data and the relationships between data — as tables, which mathematically are relations.

Definition

Relational model: a data model in which the database is a collection of relations (tables); each relation has a fixed set of named columns (attributes) and a set of rows (tuples); relationships between relations are represented by matching values (keys and foreign keys) rather than by pointers.

RDBMS (Relational DataBase Management System): a DBMS based on the relational model — Oracle, MySQL, PostgreSQL, Microsoft SQL Server, IBM DB2, SQLite, MS Access. All of them use SQL as their language.

Why it won over the older models:

  • Simple — users see only tables, no pointers or physical paths.
  • Data independence — queries say what data is needed, not how to navigate to it, so the storage can change without changing programs.
  • Solid mathematical foundation — set theory and first-order logic (relational algebra and calculus, sections 3–4), which makes query optimisation possible.
  • Powerful declarative language (SQL) and built-in integrity constraints (section 2).

Mathematical definition

Let D1, D2, …, Dn be the domains of attributes A1, …, An. A relation r on schema R(A1, …, An) is a subset of the Cartesian product D1 × D2 × … × Dn. Each tuple t = ⟨v1, …, vn⟩ has vi ∈ Di (or NULL). We write t[A] or t.A for the value of attribute A in tuple t.

This is why the model is called relational: a table is a mathematical relation (a set of ordered n-tuples) — not because tables are “related” to each other.

Schema vs instance — an analogy

The schema is like the declaration of a variable (int marks[60]), the instance is its current value. The schema of STUDENT stays the same all semester; the instance changes every time a student is admitted or leaves.

1.3 Properties (characteristics) of relations

  1. Each relation has a distinct name within the database.
  2. Each cell contains exactly one atomic (indivisible) value — no lists, no sets, no nested tables. (This is the First Normal Form, studied in Unit 4.) A student’s three phone numbers cannot be stored in one cell.
  3. Attribute names are distinct within a relation, and all values in one column come from the same domain.
  4. No two tuples are identical — a relation is a set, so duplicates are not allowed. Consequence: every relation has at least one key (at worst, the set of all its attributes).
  5. The order of tuples is irrelevant — tuples are identified by their values, not by their position (“row 3” has no meaning).
  6. The order of attributes is irrelevant as long as each value is referred to by its attribute name.
Correction (course PDF p. 70)

The PDF lists “Attribute domain has no significance” and “Tuple has no duplicate value”. The intended (and correct) properties are “the order of attributes has no significance” and “a relation has no duplicate tuples”. A single tuple may of course contain the same value twice (e.g. ⟨5, 5⟩).

SQL tables vs relations

A SQL table is a multiset (bag): unless you declare a PRIMARY KEY or UNIQUE constraint, it may contain duplicate rows, and SELECT keeps duplicates unless you write DISTINCT. Relational algebra (pure theory) never has duplicates.

1.4 NULL values

NULL is a special marker meaning “no value is stored here”. It is not zero, not an empty string and not a space.

Reasons for the occurrence of NULL values in a relation PYQ Mid-Sem 2024

  1. Value unknown — a value exists but is not known at present. Example: a patient’s date of birth is not known at admission.
  2. Value not applicable / does not exist — the attribute does not apply to this tuple. Example: spouse_name of an unmarried employee; apartment_no for someone living in an independent house.
  3. Value not yet available — it will exist later. Example: grade of a course still in progress; return_date of a book not yet returned.
  4. Value withheld / not recorded — it exists but has been deliberately left out (privacy, missing information at entry time). Example: a customer who refused to give a phone number.

NULLs also appear mechanically: when a column is added with ALTER TABLE … ADD (existing rows get NULL), when an INSERT does not mention a column that has no DEFAULT, and in the result of an outer join (padding).

Why NULLs cause trouble

  • Any comparison with NULL (=, <, >, <>) gives UNKNOWN, not TRUE/FALSE ⇒ SQL uses three-valued logic (section 6.3). Hence WHERE x = NULL never matches — you must write x IS NULL.
  • Aggregate functions ignore NULLs (AVG(salary) averages only the non-NULL salaries) — results may surprise you (section 7.1).
  • Ambiguity: a NULL does not tell you which of the four meanings applies.
  • NOT IN with a sub-query that returns a NULL returns no rows at all (section 9.4).

Good design therefore avoids NULLs where possible: use NOT NULL, sensible DEFAULTs, or move optional attributes to a separate table.

1.5 Keys

A key is an attribute or a set of attributes whose values uniquely identify each tuple of a relation. Keys also connect relations (foreign keys).

Definitions
  • Super key — any set of attributes that uniquely identifies every tuple: no two distinct tuples can ever have the same values on it. It may contain extra, unnecessary attributes.
  • Candidate key — a minimal super key: no proper subset of it is a super key. A relation may have several candidate keys.
  • Primary key (PK) — the one candidate key chosen by the designer to identify tuples. Its values must be unique and never NULL; there is exactly one PK per relation. Shown underlined in a schema.
  • Alternate (secondary) key — every candidate key that was not chosen as the primary key. (Alternate = Candidate − Primary.)
  • Composite (compound) key — a key made of two or more attributes, e.g. (sid, cid) in ENROLLMENT.
  • Foreign key (FK) — an attribute (set) in one relation whose values must match the primary key (or a UNIQUE key) of another (or the same) relation, or be NULL. It implements relationships and is the basis of referential integrity (section 2.4).
Worked example (from the resource notes)

EMPLOYEE(Emp_Id, Name, Aadhaar_No, Email_Id, Dept) with tuples (01, Aman, 7757…, a@gmail.com, 1), (02, Chirag, 4567…, c@gmail.com, 2), (03, Chirag, 8967…, ch@gmail.com, 2), (04, Dev, 7964…, d@gmail.com, 3).

  • Super keys: {Emp_Id}, {Aadhaar_No}, {Email_Id}, {Emp_Id, Name}, {Emp_Id, Aadhaar_No}, {Aadhaar_No, Email_Id}, {Emp_Id, Name, Email_Id}, … (any set containing at least one of the three unique attributes).
  • Candidate keys: {Emp_Id}, {Aadhaar_No}, {Email_Id}. {Name} is not even a super key (two Chirags); {Emp_Id, Name} is a super key but not minimal.
  • Primary key: Emp_Id (short, stable, never changes). Alternate keys: Aadhaar_No, Email_Id.
  • Foreign key: Dept → DEPARTMENT(Dept_No).
Correction (course PDF p. 54)

The PDF gives “C2 → S_Rollno, S_Name” as a candidate key of STUDENT. Since S_Rollno alone is already a key, {S_Rollno, S_Name} is not minimal — it is a super key, not a candidate key. Also, “primary key = the minimum number of candidate keys” should read: the primary key is one of the candidate keys, chosen by the designer.

Facts about foreign keys that exams test

  • An FK may have a different name from the PK it references (Employee.dept → Department.dept_no) but must have the same domain.
  • An FK value need not be unique (many employees work in one department) and may be NULL (employee not yet assigned) unless declared NOT NULL.
  • An FK may reference its own relation — a self-referencing (recursive) FK, e.g. Employee.manager_id → Employee.emp_id.
  • An FK can be part of a primary key: in ENROLLMENT(sid, cid, grade), sid and cid are both FKs and together form the PK.

Counting super keys frequently asked

For a relation with n attributes:

  • If there is a single candidate key with k attributes: every super key = that key + any subset of the other n − k attributes ⇒ 2n−k super keys.
  • With two candidate keys K1, K2 use inclusion–exclusion: |S(K1)| + |S(K2)| − |S(K1 ∪ K2)| = 2n−|K1| + 2n−|K2| − 2n−|K1∪K2|.
Example — PYQ Mid-Sem 2021, Q3(b)

R(A, B, C, D, E) has candidate keys (A) and (BC). Number of super keys?

Super keys containing A: 25−1 = 16. Containing B and C: 25−2 = 8. Containing A, B and C (counted twice): 25−3 = 4. Total = 16 + 8 − 4 = 20.

List: the 16 supersets of A — A, AB, AC, AD, AE, ABC, ABD, ABE, ACD, ACE, ADE, ABCD, ABCE, ABDE, ACDE, ABCDE — plus the supersets of BC that do not contain A — BC, BCD, BCE, BCDE (4 more). 16 + 4 = 20 ✔.

2Integrity Constraints

2.1 What and why

Definition

Integrity constraints are rules, declared as part of the database schema, that every legal database state must satisfy. The DBMS checks them automatically whenever data is inserted, updated or deleted, and rejects any operation that would violate them. They guard the database against accidental damage by authorised users — wrong, missing, duplicate or dangling data.

Integrity vs security: integrity protects against accidental invalid changes by authorised users; security protects against unauthorised access (GRANT/REVOKE, Unit 5). Why declare them in the DBMS rather than in programs? Written once instead of in every application, cannot be bypassed, and stored in the catalog where everyone can see them (Codd’s rule 10, integrity independence).

2.2 Domain constraints — data type, NOT NULL, CHECK, DEFAULT

A domain constraint specifies the set of values an attribute may take. Every value must be atomic and belong to the attribute’s domain.

  • Data type — INT, DECIMAL(8,2), VARCHAR(30), DATE … A value of the wrong type is rejected (storing 'A' in an INT age column).
  • NOT NULL — the attribute must always have a value: name VARCHAR(40) NOT NULL.
  • CHECK (condition) — the value must satisfy a condition: CHECK (age BETWEEN 16 AND 40), CHECK (color IN ('red','green','blue','black')), CHECK (salary > 0). A CHECK may also involve several columns of the same row: CHECK (end_date >= start_date) (then it is written at table level).
  • DEFAULT value — value stored when an INSERT does not give one: building VARCHAR(20) DEFAULT 'Main'.
  • User-defined domain (standard SQL): CREATE DOMAIN marks_t AS INT CHECK (VALUE BETWEEN 0 AND 100); then use marks marks_t.
CHECK and NULL

A CHECK constraint is violated only when the condition is FALSE. If the value is NULL the condition is UNKNOWN, which is accepted. So CHECK (age >= 16) still allows a NULL age — add NOT NULL if the value is mandatory. (Older MySQL versions, before 8.0.16, parsed CHECK but silently ignored it.)

2.3 Key constraints and entity integrity — PRIMARY KEY, UNIQUE

  • Key constraint: no two tuples may have the same value for a key. Declared with PRIMARY KEY (the chosen key) and UNIQUE (alternate keys).
  • Entity integrity constraint: no attribute of the primary key may be NULL. Reason: the PK is how we identify a tuple (and how other tables refer to it); a NULL key would make the row unidentifiable, and two NULL keys could not be told apart.

A composite PK or UNIQUE must be written at table level: PRIMARY KEY (student_id, course_id, semester) — this says the combination is unique (a student may take many courses, but not the same course twice in the same semester).

2.4 Referential integrity — FOREIGN KEY

Definition

A referential integrity constraint is specified between two relations. If attribute set FK of the referencing (child) relation R1 refers to the primary key PK of the referenced (parent) relation R2, then for every tuple t1 in R1, the value t1[FK] must either be NULL or be equal to t2[PK] for some tuple t2 in R2.

In words: a foreign key may not point to something that does not exist (“no dangling references”).

2.5 Enforcing integrity constraints

“Enforcing” = where the constraints are written and how/when the DBMS checks them.

  1. Declaratively, in CREATE TABLE (best). Two styles:
    • Column-level — written next to the column: age INT CHECK (age >= 16). Only for single-column constraints. (NOT NULL can only be column-level.)
    • Table-level — written after all columns: PRIMARY KEY (sid, cid), FOREIGN KEY (sid) REFERENCES student(roll_no), CHECK (end_date >= start_date). Needed for multi-column constraints.
    Give constraints names with CONSTRAINT name … so error messages are readable and they can be dropped later.
  2. Added / removed later with ALTER TABLE: 
    ALTER TABLE parts   ADD CONSTRAINT chk_color CHECK (color IN ('green','red','blue','black'));
ALTER TABLE student ADD CONSTRAINT uq_email UNIQUE (email);
ALTER TABLE student ADD CONSTRAINT fk_dept FOREIGN KEY (dept_id) REFERENCES department(dept_id);
ALTER TABLE student DROP CONSTRAINT chk_age;          -- MySQL: DROP CHECK chk_age
    When a constraint is added to a table that already has data, the DBMS first checks the existing rows; if any violates it, the ALTER fails.
  3. Checking time. By default every constraint is checked immediately — after each SQL statement. If it fails, the whole statement is rolled back and an error is returned (the transaction may continue). A constraint declared DEFERRABLE INITIALLY DEFERRED is checked only at COMMIT — needed for “chicken-and-egg” cases such as two tables with FKs to each other (Oracle, PostgreSQL).
  4. General constraints that span several tables cannot be expressed as column/table constraints:
    • Assertion (standard SQL, rarely implemented): CREATE ASSERTION max_staff CHECK (NOT EXISTS (SELECT dept_id FROM employee GROUP BY dept_id HAVING COUNT(*) > 50));
    • Triggers (section 11) — procedural code fired on INSERT/UPDATE/DELETE that can check anything and raise an error.
  5. Application code — the weakest option: can be bypassed by any other program or by direct SQL.

3Relational Algebra

3.1 What relational algebra is

Definition

Relational algebra (RA) is a procedural, formal query language consisting of a set of operations that take one or two relations as input and produce a new relation as output. A query is written as an expression built from these operations, and the expression also describes the order in which the operations are applied (that is what “procedural” means — you say what you want and how to get it).

  • Closure property: the output of every operation is again a relation, so operations can be nested like arithmetic: πsname(σrating > 7(Sailors)). Just as + and × combine numbers, σ, π, ⋈ … combine relations.
  • Set semantics: relations are sets, so results never contain duplicate tuples.
  • Why study it: it is the theoretical foundation of SQL; the DBMS internally translates every SQL query into an RA expression (a query tree) and optimises it by rewriting the expression.

The operators at a glance

The six fundamental operators are σ, π, ρ, ∪, −, ×: every other operator can be written using them (section 3.10).

3.5 Rename (ρ) and assignment (←)

Results of RA expressions have no name. ρ gives a name to a relation and/or its attributes:

  • ρS(E) — the result of expression E is named S.
  • ρS(B1, B2, …, Bn)(E) — named S, and its attributes renamed B1 … Bn.
  • ρ(B1, …, Bn)(E) — only attributes renamed.

Example: ρEmployee(name, address, phone)(Student) renames table Student to Employee and its attributes (course PDF).

Why we need it: (1) to join a relation with itself (self-join) — we need two names, e.g. ρS1(Sailors) and ρS2(Sailors); (2) to make attribute names match for natural join / union; (3) to name intermediate results.

Assignment T ← E stores the result of E in a temporary relation T, so a long query can be written in readable steps:

RedBoats ← σcolor='red'(Boats)
RedRes ← RedBoats ⋈ Reserves
Answer ← πsname(RedRes ⋈ Sailors)
Exam tip

In exams, writing a long query as 2–4 numbered assignment steps is perfectly acceptable, easier to get right, and easier for the examiner to give marks for.

4Relational Calculus

4.1 The idea

Definition

Relational calculus is a non-procedural (declarative) formal query language based on first-order predicate logic. A query describes the properties of the tuples wanted — a condition that the answer must satisfy — and says nothing about how to compute it.

Compare the two ways of asking for “names of sailors with rating > 7”:

  • RA (a recipe): first select the rows with rating > 7, then project the name → πsname(σrating>7(Sailors)).
  • Calculus (a description): “the set of names n such that some sailor with name n has rating > 7” → { t | ∃ s ∈ Sailors (s.rating > 7 ∧ t.sname = s.sname) }.

There are two kinds:

  • Tuple Relational Calculus (TRC) — variables stand for whole tuples (rows). SQL is based on TRC.
  • Domain Relational Calculus (DRC) — variables stand for single attribute values (domain elements). QBE (Query-By-Example) is based on DRC.

Free and bound variables. A variable is bound if it is introduced by a quantifier (∃s or ∀s) — it is a local “loop variable”. A variable that is not bound is free. In a calculus query the only free variable must be the result variable written to the left of the bar.

4.3 Tuple relational calculus (TRC)

General form
{ t | P(t) }

“the set of all tuples t for which the formula P(t) is true”. t is a tuple variable; t.A (also written t[A]) is the value of attribute A in t.

Atoms (building blocks of formulas):

  1. s ∈ R — s is a tuple of relation R;
  2. s.A θ u.B — compare attributes of two tuple variables, θ ∈ {=, ≠, <, ≤, >, ≥};
  3. s.A θ c — compare with a constant.

Formulas are built from atoms with ∧, ∨, ¬, ⇒ and the quantifiers ∃ s ∈ R (F), ∀ s ∈ R (F).

Two ways of describing the result tuple

  • Whole tuples of one relation: { t | t ∈ Sailors ∧ t.rating > 7 } — t ranges over Sailors, so the result has all four attributes.
  • New tuples (projection / combining tables): t is not bound to any relation; we state the value of each of its attributes, e.g. { t | ∃ s ∈ Sailors (s.rating > 7 ∧ t.sname = s.sname ∧ t.rating = s.rating) } — the result has exactly the attributes mentioned for t (sname, rating). This is Korth’s style and what most exams expect.
  • Short-hand used in many books (Navathe, Ramakrishnan): list the output attributes on the left — { s.sname, s.rating | s ∈ Sailors ∧ s.rating > 7 }. Accepted in exams; use one style consistently.

Why calculus is immune to the “two Horatios” trap

In P6 and P7 every condition is attached to one sailor variable s, so “red” and “green” must both hold for the same sailor. In RA you had to remember to intersect sids; in calculus it happens naturally.

Writing “for all” correctly

“s reserved every red boat” = for every boat b: if b is red then s reserved b. Two very common mistakes:

  • ∀ b ∈ Boats (b.color = 'red' ∧ ∃ r …) — wrong: demands that every boat is red; false as soon as one blue boat exists. Use ⇒ with ∀.
  • ∃ b ∈ Boats (b.color = 'red' ⇒ …) — wrong: true for any blue boat (false ⇒ anything is true). Use ∧ with ∃.
Rule of thumb

∃ goes with ∧, ∀ goes with ⇒. And to turn ∀ into something SQL can do, use ∀ b (P ⇒ Q) ≡ ¬ ∃ b (P ∧ ¬ Q) — “there is no red boat that s did not reserve” (this is exactly the double NOT EXISTS in section 4.6).

4.4 Safety of expressions

A calculus expression may describe an infinite relation. Example: { t | ¬ (t ∈ Sailors) } = “every possible tuple that is not a sailor” — infinitely many, and meaningless. Such expressions are unsafe.

Definition

An expression is safe if every value in its result comes from the domain of the expression — the set of constants appearing in the expression plus the values appearing in the relations it mentions. In practice: bind every variable to a relation (∃ s ∈ R, ∀ s ∈ R) and never let the result variable range over “anything not in R”.

Only safe expressions are allowed; with this restriction calculus has exactly the power of RA (section 4.7).

4.5 Domain relational calculus (DRC)

General form
{ ⟨ x1, x2, …, xn ⟩ | P(x1, x2, …, xn) }

x1 … xn are domain variables (each stands for one attribute value). Atoms: ⟨ x1, …, xk ⟩ ∈ R (the values form a tuple of R, in attribute order), x θ y, x θ c. Formulas use ∧ ∨ ¬ ⇒ ∃ ∀ as before.

4.7 Expressive power — Codd’s theorem

  • Codd’s theorem: relational algebra, safe tuple relational calculus and safe domain relational calculus are equivalent in expressive power — every query in one can be written in the others.
  • A language with at least this power is relationally complete. SQL is relationally complete and goes beyond (aggregates, ordering, recursion).
  • None of the three (pure forms) can compute aggregates such as SUM, or a transitive closure (“all ancestors”) — that needs extensions.

5Introduction to SQL — DDL, DML, DCL, TCL

5.1 What SQL is

SQL (Structured Query Language), pronounced “S-Q-L” or “sequel”, is the standard language for relational databases. It was developed at IBM (System R, 1970s, originally SEQUEL) and standardised by ANSI (1986) and ISO (1987); later versions are SQL-92, SQL:1999 (triggers, recursion), SQL:2003 (window functions) and onward. Every RDBMS implements the standard plus its own dialect (Oracle PL/SQL, MySQL, SQL Server T-SQL, PostgreSQL).

  • Declarative / non-procedural — you state what you want; the DBMS’s optimiser decides how.
  • Set-oriented — one statement can read or change many rows (Codd rule 7).
  • Comprehensive — one language for definition, manipulation, control and transactions (Codd rule 5).
  • Keywords are case-insensitive (SELECT = select); string literals in single quotes are case-sensitive in most systems; statements end with ;.

5.6 DCL — GRANT and REVOKE

DCL controls who may do what (authorisation). Privileges are of two kinds:

  • System privileges — the right to perform an action in the database: CREATE SESSION, CREATE TABLE, CREATE VIEW, CREATE USER…
  • Object privileges — the right to act on a particular object: SELECT, INSERT, UPDATE, DELETE, REFERENCES, EXECUTE, ALL PRIVILEGES on a table/view/procedure.
GRANT SELECT, INSERT ON employee TO ravi;               -- give privileges
GRANT UPDATE (salary) ON employee TO hr_manager;         -- column-level privilege
GRANT SELECT ON employee TO ravi WITH GRANT OPTION;      -- ravi may pass the privilege on
GRANT ALL PRIVILEGES ON project TO PUBLIC;               -- every user
GRANT CREATE TABLE TO ravi;                              -- system privilege

REVOKE INSERT ON employee FROM ravi;                     -- take back
REVOKE SELECT ON employee FROM ravi CASCADE;             -- also from everyone ravi granted it to

Roles group privileges: CREATE ROLE clerk; GRANT SELECT, INSERT ON orders TO clerk; GRANT clerk TO ravi, sita; (Details — authorisation graph, CASCADE vs RESTRICT — are in Unit 5, Database Security.)

5.7 TCL — COMMIT, ROLLBACK, SAVEPOINT

UPDATE account SET balance = balance - 500 WHERE acc_no = 'A';
SAVEPOINT after_debit;
UPDATE account SET balance = balance + 500 WHERE acc_no = 'B';
ROLLBACK TO after_debit;      -- undo only the credit
COMMIT;                       -- make the remaining changes permanent
  • COMMIT — makes all changes of the current transaction permanent and visible to others.
  • ROLLBACK — undoes all changes since the last COMMIT.
  • SAVEPOINT name / ROLLBACK TO name — partial rollback inside a transaction.
  • SET TRANSACTION — sets properties (read only, isolation level). Transactions are covered fully in Unit 5.
  • In Oracle and MySQL every DDL statement performs an implicit COMMIT before and after itself.

5.8 Views

A view is a virtual table defined by a stored query; it holds no data of its own — each time it is used, its query runs on the base tables.

CREATE VIEW it_staff_v AS
SELECT emp_id, name, salary
FROM   employee
WHERE  dept_id = 20;

SELECT * FROM it_staff_v WHERE salary > 70000;     -- use it like a table
DROP VIEW it_staff_v;
  • Uses: security (show only some columns/rows — e.g. hide salary), simplicity (hide complex joins), logical data independence (applications use the view even if base tables are restructured).
  • Updatable views: a view on a single table without DISTINCT, GROUP BY, aggregates or set operators, and including the key, can usually be updated (the change goes to the base table). Others need an INSTEAD OF trigger (section 11).
  • WITH CHECK OPTION — rejects inserts/updates through the view that would produce rows the view cannot see.
  • Materialised view — stores the result physically and is refreshed periodically (faster reads, stale data possible).

10Triggers

10.1 What a trigger is

Definition

A trigger is a named block of procedural code stored in the database that the DBMS executes automatically whenever a specified event occurs on a specified table (or view / schema / database). It follows the ECA model:

  • Event — what fires it: INSERT, UPDATE (optionally of certain columns), DELETE; or a DDL / system event;
  • Condition — optional test (WHEN …); the action runs only if it is true;
  • Action — the SQL / PL/SQL statements executed.

Unlike a stored procedure, a trigger is never called explicitly — the event fires it.

General syntax (Oracle style; MySQL/PostgreSQL are very similar)

CREATE [OR REPLACE] TRIGGER trigger_name
{BEFORE | AFTER | INSTEAD OF}  {INSERT | UPDATE [OF col, ...] | DELETE}  [OR ...]
ON table_name
[REFERENCING OLD AS o NEW AS n]
[FOR EACH ROW]                       -- row-level; omit for statement-level
[WHEN (condition)]
BEGIN
    -- action: SQL statements using :NEW.col and :OLD.col  (MySQL: NEW.col, OLD.col)
END;
  • NEW — the row after the change (available in INSERT and UPDATE triggers). OLD — the row before the change (UPDATE and DELETE). INSERT has no OLD, DELETE has no NEW.
  • A BEFORE row trigger may modify NEW (e.g. convert a name to upper case) before it is stored.
  • To reject the operation, raise an error: Oracle RAISE_APPLICATION_ERROR(-20001, 'msg'), MySQL SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'msg', SQLite SELECT RAISE(ABORT, 'msg').

10.5 Use cases, advantages and cautions

Use cases
  • Enforcing complex integrity rules / business rules that CHECK cannot express (multi-table, e.g. “an employee’s salary may not exceed the manager’s”).
  • Auditing — recording who changed what and when.
  • Maintaining derived data — totals, balances, stock levels, denormalised copies.
  • Automatic values — timestamps, generated codes, normalised case.
  • Replication / synchronising tables; sending notifications.
  • Security — blocking operations outside business hours or by certain users; DDL protection.
  • Making views updatable (INSTEAD OF).
Cautions
  • Hidden logic — effects are invisible in the application code; hard to debug.
  • Performance — row-level triggers run for every row of bulk operations.
  • Cascading / recursive triggers — trigger A updates table B whose trigger updates A… can loop (DBMSs limit the depth).
  • Mutating-table errors (Oracle) — a row trigger cannot query the table being modified.
  • Prefer declarative constraints (CHECK, FK) when they suffice — they are faster and clearer.

Trigger vs stored procedure: a procedure is called explicitly (CALL p(…) / EXEC), can take parameters and return values, and can contain COMMIT; a trigger fires implicitly on an event, takes no parameters, and normally cannot COMMIT/ROLLBACK (it runs inside the triggering transaction).

Trigger vs constraint: a constraint (CHECK, FK) is declarative, always enforced on existing and new data, and optimisable; a trigger is procedural and only acts on future events.

11Introduction to NoSQL Databases

11.1 What NoSQL is and why it appeared

Definition

NoSQL (“Not only SQL”) is a family of non-relational database systems that store data in models other than tables — key-value pairs, documents, wide columns or graphs — and are designed for flexible (schema-less) data, very large volumes and horizontal scaling across many commodity machines.

Why it appeared (mid-2000s, Google BigTable 2006, Amazon Dynamo 2007): web-scale companies faced

  • Big data — the 3 V’s: huge volume, high velocity (millions of writes per second), great variety (semi-structured and unstructured data: JSON, logs, posts, images, sensor readings).
  • Changing structure — social-media posts with optional photos/videos/polls/tags; product catalogues whose attributes differ by category. A fixed relational schema needs ALTER TABLE for every change.
  • Scaling limits — an RDBMS scales mainly vertically (bigger server); joins and ACID across many machines are expensive.
  • Availability — a global service must keep answering even when some servers or network links fail.

11.2 Features of NoSQL databases

  • Flexible / dynamic schema (schema-on-read) — records in the same collection may have different fields; no ALTER needed.
  • Horizontal scalability — data is sharded (partitioned) across nodes; add nodes to add capacity.
  • Replication and fault tolerance — copies on several nodes; no single point of failure.
  • High performance for simple operations by key; data that is read together is stored together (denormalised, aggregate-oriented), so few or no joins.
  • BASE instead of strict ACID (most systems; many now offer ACID for single documents or even multi-document transactions).
  • Usually open source, often accessed through APIs rather than SQL (each has its own query language: MongoDB Query Language, CQL for Cassandra, Cypher for Neo4j).

11.4 CAP theorem and BASE

ACID (RDBMS)

Atomicity, Consistency, Isolation, Durability — every committed transaction is all-or-nothing and immediately visible to everyone. Pessimistic: correctness first.

BASE (most NoSQL)

Basically Available — the system always answers (maybe with partial/stale data); Soft state — data may change over time even without input, as replicas synchronise; Eventually consistent — if no new updates arrive, all replicas eventually hold the same value. Optimistic: availability first.

12One-page Revision Sheet

Relational model
  • Relation = table = set of tuples; attribute = column; domain = allowed atomic values; degree = #columns; cardinality = #rows.
  • Schema (structure) vs instance (current rows).
  • No duplicate tuples; order of rows/columns irrelevant; atomic values.
  • NULL: unknown / not applicable / not yet available / withheld. Test with IS NULL.
  • Super ⊇ candidate (minimal) ⊇ primary (chosen, not NULL); alternate = candidate − primary; FK references PK.
  • #super keys with one key of k attrs among n: 2n−k; two keys: inclusion–exclusion.
Integrity constraints
  • Domain (type, NOT NULL, CHECK, DEFAULT) · Key (PRIMARY KEY, UNIQUE) · Entity (PK ≠ NULL) · Referential (FK = existing PK or NULL).
  • Violations: insert/update child FK, delete/update parent PK.
  • Actions: RESTRICT/NO ACTION (reject) · CASCADE · SET NULL · SET DEFAULT.
  • Column-level vs table-level (composite); ALTER TABLE ADD/DROP CONSTRAINT; checked per statement, or DEFERRED to COMMIT; assertions/triggers for multi-table rules.
Relational algebra
  • Fundamental: σ π ρ ∪ − ×  · derived: ∩ ⋈ ÷  · extended: ⟕⟖⟗ γ.
  • ∪ ∩ − need union-compatibility.
  • ⋈θ = σθ(×); natural join drops duplicate column.
  • ÷ for “all/every”: R ÷ S = πX(R) − πX((πX(R) × S) − R). Project dividend first.
  • Patterns: both→∩ of keys; not→−; only→did − did-other; at least 2→self-join ≠; exactly 1→(≥1) − (≥2); max→all − beaten.
Relational calculus
  • TRC {t | P(t)} — tuple variables; DRC {⟨x1..xn⟩ | P} — domain variables.
  • ∃ with ∧, ∀ with ⇒; ∀x P ≡ ¬∃x ¬P.
  • Safe = result values come from the database/constants.
  • RA ≡ safe TRC ≡ safe DRC (Codd) — relationally complete.
  • RA procedural; RC declarative.
SQL
  • DDL CREATE ALTER DROP TRUNCATE RENAME · DML SELECT INSERT UPDATE DELETE · DCL GRANT REVOKE · TCL COMMIT ROLLBACK SAVEPOINT.
  • Order: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
  • WHERE filters rows (no aggregates), HAVING filters groups.
  • COUNT(*) counts rows; other aggregates ignore NULL.
  • Non-aggregated SELECT columns must be in GROUP BY.
  • LIKE: % any string, _ one char. = NULL never true.
Joins & sub-queries
  • Inner (matches) · left/right/full outer (+ unmatched, NULL-padded) · cross (all pairs) · natural (same-named columns) · self (aliases).
  • Right-table filter of a LEFT JOIN goes in ON, not WHERE.
  • Scalar (=), multi-row (IN, ANY, ALL), EXISTS.
  • NOT IN + NULL in sub-query ⇒ no rows; use NOT EXISTS.
  • Correlated = refers to outer row, runs per row (“above own dept average”, “max per dept”).
  • Division in SQL: double NOT EXISTS, or GROUP BY … HAVING COUNT = (SELECT COUNT …).
Triggers
  • ECA: event (INSERT/UPDATE/DELETE, DDL, system) · condition (WHEN) · action.
  • BEFORE (validate/modify NEW) · AFTER (audit, update others) · INSTEAD OF (views).
  • Row-level (FOR EACH ROW, OLD/NEW) vs statement-level.
  • Fired automatically; procedures are called explicitly.
NoSQL
  • “Not only SQL”: key-value (Redis), document (MongoDB), column-family (Cassandra), graph (Neo4j).
  • Flexible schema, horizontal scaling, replication, BASE (basically available, soft state, eventually consistent).
  • CAP: at most 2 of consistency, availability, partition tolerance in a partition.
  • Choose SQL for transactions/integrity, NoSQL for volume/variety/availability — often both.

14.1 Relational model, keys and NULL

Mid-Sem Sep 2024Q3(b)2 marks

Discuss the four reasons that lead to the occurrence of NULL values in a relation.

Show answer

NULL is a special marker meaning “no value is stored”; it is different from 0 or a blank. It occurs because:

  1. Value unknown — it exists but is not known now. E.g. DOB of a patient brought in unconscious.
  2. Value not applicable — the attribute does not apply to that tuple. E.g. spouse_name of an unmarried employee; maiden_name of a man.
  3. Value not yet available / not yet assigned — it will exist later. E.g. grade of a course in progress, dept_id of a newly joined employee.
  4. Value withheld / not recorded — it exists but is intentionally not stored (privacy) or was missed at entry. E.g. a customer who declines to give a phone number.

(NULLs also arise from outer joins and from adding a new column with ALTER TABLE.) Since a comparison with NULL is UNKNOWN, NULLs must be tested with IS NULL, and aggregate functions ignore them.

14.2 Integrity constraints and referential integrity

End-Sem 2023Q2(c)4 marks

What are integrity constraints? How are they useful? Explain any 4 integrity constraints with the help of suitable examples and syntax.

Show answer

Integrity constraints are rules defined on the database schema that every valid database state must satisfy. The DBMS checks them on every INSERT, UPDATE and DELETE and rejects any operation that violates them.

Usefulness: keep data accurate and consistent; prevent duplicates, missing mandatory values and dangling references; defined once in the schema instead of in every program; cannot be bypassed by applications.

  1. Domain constraint (NOT NULL, CHECK, data type, DEFAULT) — each value must come from the attribute’s domain. 
    age    INT CHECK (age BETWEEN 16 AND 40),
name   VARCHAR(40) NOT NULL
    INSERT … age = 12 or a NULL name is rejected.
  2. Key constraint (PRIMARY KEY / UNIQUE) — no two tuples have the same key value. 
    roll_no INT PRIMARY KEY,
email   VARCHAR(50) UNIQUE
    A second student with roll_no 1 is rejected.
  3. Entity integrity — no primary-key attribute may be NULL (a NULL key cannot identify a tuple). Enforced automatically by PRIMARY KEY.
  4. Referential integrity (FOREIGN KEY) — a foreign-key value must match an existing primary-key value of the referenced table, or be NULL. 
    dept_id INT REFERENCES department(dept_id) ON DELETE SET NULL
    Inserting a student with dept_id 99 when no department 99 exists is rejected; deleting a department sets its students’ dept_id to NULL.

Discuss the role of a foreign key constraint in maintaining referential integrity. By providing a referential integrity constraint, what happens when an update or delete or insert operation is performed on a table?

Show answer

A foreign key is an attribute of a child (referencing) table whose values must match the primary key of a parent (referenced) table or be NULL. It ensures that every reference points to a row that really exists — no dangling references — which is referential integrity. E.g. employee.dept_id REFERENCES department(dept_id).

  • INSERT into child (or UPDATE of the FK) with a value not present in the parent → rejected. Inserting into the parent is always fine.
  • DELETE from parent of a row that is referenced → action given by ON DELETE: RESTRICT/NO ACTION (default) rejects the delete; CASCADE deletes the child rows too; SET NULL sets the child FKs to NULL; SET DEFAULT sets them to the default. Deleting a child row is always fine.
  • UPDATE of the parent’s PK that is referenced → action given by ON UPDATE (RESTRICT / CASCADE — child FKs changed to the new value / SET NULL).
FOREIGN KEY (dept_id) REFERENCES department(dept_id)
    ON DELETE CASCADE ON UPDATE CASCADE

End-Sem 2025 (ITITC05)Q2(b)4 marks

Explain referential integrity constraint. Assume that a row in the parent table, whose primary key value = 5, is deleted. Discuss in detail what consequence this deletion has on the child table under the referential integrity constraint.

Show answer

Referential integrity: if FK of child relation R1 references PK of parent R2, then for every tuple t1 of R1, t1[FK] is NULL or t1[FK] = t2[PK] for some tuple t2 of R2.

Let parent department(dept_id PK) and child employee(emp_id, dept_id FK), and suppose employees E1, E3 have dept_id = 5. DELETE FROM department WHERE dept_id = 5;

  • If no child row has FK = 5: the delete simply succeeds; the child table is unaffected.
  • ON DELETE RESTRICT / NO ACTION (default): the delete is rejected with an error because E1 and E3 still refer to 5; both tables unchanged. The user must first delete/reassign those employees.
  • ON DELETE CASCADE: department 5 is deleted and E1 and E3 are deleted automatically (and, if other tables reference E1/E3 with CASCADE, the deletion continues down the chain).
  • ON DELETE SET NULL: department 5 is deleted; E1 and E3 remain with dept_id = NULL (allowed only if the column is nullable).
  • ON DELETE SET DEFAULT: E1 and E3 get the column default (e.g. 0 = “unassigned”), which must itself exist in the parent.

In every case the database never ends up with a child row pointing to the deleted key 5 — that is the guarantee of referential integrity.

Relational algebra vs relational calculus

Relational algebraRelational calculus
procedural — specifies what to retrieve and the sequence of operationsnon-procedural (declarative) — specifies only what to retrieve
based on set theory / algebra of operatorsbased on first-order predicate logic
queries are expressions of operators σ, π, ρ, ∪, −, ×, ⋈, ÷queries are formulas {t | P(t)} (TRC) or {⟨x1..xn⟩ | P} (DRC) with ∃, ∀, ∧, ∨, ¬
order of evaluation fixed by the expressionno order specified
always finite (safe) resultsunsafe expressions possible; restricted to safe ones
“for all” via division ÷“for all” via ∀
e.g. πname(σage>20(Student))e.g. { t | ∃ s ∈ Student (s.age > 20 ∧ t.name = s.name) }

Both have the same expressive power (Codd’s theorem, for safe calculus); RA is closer to query execution plans, TRC to SQL.

Aggregate functions

Functions that take a set of values (a column of a group of rows) and return a single summary value: COUNT, SUM, AVG, MIN, MAX. Syntax FUNC([DISTINCT] column); used in SELECT and HAVING, usually with GROUP BY; all ignore NULLs except COUNT(*).

SELECT dept_id, COUNT(*) AS n, AVG(salary) AS avg_sal, MAX(salary) AS top
FROM   employee
GROUP  BY dept_id
HAVING COUNT(*) >= 3;

Output on the sample DB: dept 10 → 3 employees, dept 20 → 4 (section 7.3).

  • GRANT gives privileges (SELECT, INSERT, UPDATE, DELETE, REFERENCES, ALL, or system privileges like CREATE TABLE) on an object to users or roles. WITH GRANT OPTION lets the receiver pass the privilege on.
  • REVOKE takes privileges back. With CASCADE, privileges the user had passed on are also revoked; RESTRICT refuses if such dependent grants exist.
GRANT SELECT, INSERT ON student TO ravi;
GRANT UPDATE (marks) ON result TO teacher1 WITH GRANT OPTION;
REVOKE INSERT ON student FROM ravi;
REVOKE UPDATE (marks) ON result FROM teacher1 CASCADE;

Example: a clerk is given only SELECT on student so he can view but not change records; if he leaves, REVOKE removes his access.

14.7 Triggers

End-Sem 2024Q2(a)(ii)2.5 marks

What is an SQL trigger? Explain its types and use cases.

Show answer

A trigger is a stored block of SQL/procedural code that the DBMS executes automatically when a specified event (INSERT, UPDATE, DELETE — or a DDL/system event) occurs on a table. It follows the Event–Condition–Action model and is never called explicitly.

CREATE TRIGGER trg_name {BEFORE | AFTER | INSTEAD OF} {INSERT | UPDATE | DELETE}
ON table_name [FOR EACH ROW] [WHEN (condition)]
BEGIN  ...action...  END;

Types:

  • By timing — BEFORE (validate / modify the new row before it is written), AFTER (act after the change: audit, update other tables), INSTEAD OF (on views: replace the statement).
  • By level — row-level (FOR EACH ROW: once per affected row; can use OLD/NEW) and statement-level (once per statement).
  • By event — DML triggers, DDL triggers (CREATE/ALTER/DROP), system/database-event triggers (LOGON, STARTUP …).

Use cases: enforcing complex business rules (e.g. salary may not decrease), auditing changes, maintaining derived values (account balance, stock level), automatic timestamps, preventing DDL changes, making join-views updatable.

CREATE TRIGGER trg_audit AFTER UPDATE OF salary ON emp
FOR EACH ROW
BEGIN
  INSERT INTO salary_audit VALUES (OLD.id, OLD.salary, NEW.salary, CURRENT_DATE);
END;

14.8 NoSQL vs SQL

End-Sem 2024Q1(c)5 marks

A social media company needs to store vast amounts of user-generated content, including comments, likes and shares, which vary greatly in structure. Explain why a NoSQL database might be more suitable for this task than an RDBMS, and describe the type of NoSQL database model you would recommend.

Show answer

Why NoSQL suits this workload better than an RDBMS:

  1. Variable structure (schema flexibility): a post may have text, images, videos, polls, hashtags, mentions, location; comments can be nested. In an RDBMS every new kind of field needs ALTER TABLE or many sparse NULL columns and extra tables. A document store accepts each post as a self-describing JSON document with its own fields.
  2. Volume and velocity: billions of posts and millions of likes per minute. NoSQL databases scale horizontally by sharding across cheap servers; an RDBMS mainly scales vertically.
  3. Availability over strict consistency: it does not matter if a like count is a few seconds stale (eventual consistency, BASE); it does matter that the service never goes down. NoSQL systems are built for replication and partition tolerance (AP in CAP).
  4. Read pattern: a post is usually read together with its comments and counts — storing them together (denormalised) avoids expensive joins.
  5. Semi-structured/unstructured data (text, media metadata) fits naturally.

Recommended model: a document database (e.g. MongoDB / Couchbase) for posts, comments and profiles:

{ "_id": "p9001", "user": "u42", "text": "Sunset at Marine Drive",
  "media": [ {"type": "image", "url": "…"} ], "tags": ["mumbai", "sunset"],
  "likes": 1532, "shares": 87,
  "comments": [ {"user": "u7", "text": "Wow!", "at": "2024-11-02T18:04"} ] }

Complemented by a wide-column store (Cassandra) for the huge stream of like/share events and activity feeds, a key-value store (Redis) for counters and sessions, and a graph database (Neo4j) for the follower network and friend recommendations. Payments/ads billing, which need ACID, remain in an RDBMS.

Practice 9Trigger

product(pid, pname, stock), order_item(oid, pid, qty). Write triggers so that (i) an order line is rejected if the quantity exceeds the available stock, and (ii) the stock is reduced automatically after a valid order line is inserted. Which timing do you use for each and why?

Show answer

(i) must run BEFORE INSERT (so the row can be rejected before it is stored); (ii) AFTER INSERT (update another table only once the row is definitely inserted). Both are row-level.

CREATE TABLE product(pid INT PRIMARY KEY, pname TEXT, stock INT CHECK (stock >= 0));
CREATE TABLE order_item(oid INT, pid INT REFERENCES product, qty INT);
CREATE TRIGGER trg_check_stock BEFORE INSERT ON order_item
FOR EACH ROW WHEN NEW.qty > (SELECT stock FROM product WHERE pid = NEW.pid)
BEGIN
  SELECT RAISE(ABORT, 'insufficient stock');
END;
CREATE TRIGGER trg_reduce_stock AFTER INSERT ON order_item
FOR EACH ROW
BEGIN
  UPDATE product SET stock = stock - NEW.qty WHERE pid = NEW.pid;
END;
