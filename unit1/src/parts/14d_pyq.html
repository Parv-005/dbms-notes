14.4 DBMS structure, architecture, languages and short definitions

End-sem 2022 Q1(b)4 marks

Draw and explain the detailed structure of a database management system.

Show answer

Diagram: the structure figure of section 7.1 — users at the top, then their interfaces, then the query processor, the storage manager and disk storage.

1. Users and interfaces: naive users (application interfaces/forms), application programmers (programs compiled with embedded DML), sophisticated users (query tools/SQL), DBA (administration tools, DDL).

2. Query processor

  • DDL interpreter — interprets DDL statements and records definitions in the data dictionary.
  • DML compiler — translates DML queries into an evaluation plan of low-level instructions; performs query optimisation (picks the cheapest plan).
  • Embedded DML pre-compiler — converts DML embedded in host programs into procedure calls.
  • Query evaluation engine — executes the low-level instructions.

3. Storage manager — interface between stored data and the queries/programs; translates DML into file-system commands.

  • Authorization and integrity manager — checks access rights and integrity constraints.
  • Transaction manager — ensures consistency despite failures (recovery) and concurrency (concurrency control).
  • File manager — allocates disk space and manages on-disk data structures.
  • Buffer manager — moves data between disk and main memory; decides what to cache.

4. Disk storage: data files (the database), data dictionary (metadata — schemas, constraints, users), indices (fast access), statistical data (used by the optimiser).

Mid-sem 2021 Q1(b)4 marks

Does an e-commerce application follow a three-tier architecture? Justify your answer.

Show answer

Yes. An e-commerce application (Amazon, Flipkart) is a classic three-tier system:

  1. Presentation tier (client): the web browser or mobile app shows product pages, cart and checkout forms; it only sends HTTP requests and displays responses. It never connects to the database.
  2. Application tier (middle): web/application servers hold the business logic — user authentication, search, price and discount calculation, stock check, order placement, payment-gateway calls; they issue SQL/NoSQL requests to the database through connection pools.
  3. Data tier: database servers store customers, products, inventory, orders and payments; they enforce constraints and run transactions.

Justification — why 3-tier and not 2-tier:

  • Security: millions of untrusted clients must not hold database credentials or send SQL; the middle tier validates every request.
  • Scalability: app servers can be replicated behind a load balancer; the DB serves pooled connections instead of one per user.
  • Maintainability: a pricing rule changes once on the server, not in every customer’s app; thin clients.
  • Independence: the database can be changed or replicated without affecting the clients.

(In practice it is often n-tier — separate web, application, caching and database layers — which is an extension of 3-tier.)

Mid-sem 2023 Q2(b)1 mark

Give an example of 1-tier architecture. How is it different from 2-tier architecture?

Show answer

Example of 1-tier: a student using MS Access or SQLite on their own laptop, or a DBA working directly at the database server console — user interface, application and database on the same machine.

Difference: in 1-tier everything is local and changes go straight to the database (single user, no network). In 2-tier the client machine runs the user interface and application, and connects over a network to a separate database server through APIs such as ODBC/JDBC; many clients share one database.

End-sem 2023 (COCSC05) Q1(a)4 marks

Highlight the key difference between the following with the help of suitable examples: (i) DDL and DML (ii) candidate key and super key (iii) procedural and non-procedural language (iv) strong and weak entities.

Show answer

(i) DDL vs DML. DDL defines/changes the structure (schema) of the database — CREATE, ALTER, DROP, TRUNCATE; its result is stored in the data dictionary and it is auto-committed. DML accesses and changes the data — SELECT, INSERT, UPDATE, DELETE; it can be rolled back.
e.g. CREATE TABLE emp(id INT PRIMARY KEY, name VARCHAR(30)) is DDL; INSERT INTO emp VALUES (1,'Asha') is DML.

(ii) Candidate key vs super key. A super key is any set of attributes that uniquely identifies a tuple; a candidate key is a minimal super key (no proper subset is a super key). Every candidate key is a super key, not vice-versa.
e.g. STUDENT(Roll, Email, Name): {Roll}, {Email} are candidate keys; {Roll, Name} is a super key but not a candidate key.

(iii) Procedural vs non-procedural. Procedural: the user specifies what data and how to get it (sequence of operations) — relational algebra, PL/SQL, CODASYL DML. Non-procedural (declarative): the user specifies only what — SQL SELECT, relational calculus; the DBMS decides how.
e.g. RA: πname(σdept='IT'(emp)) is a sequence of steps; TRC {t.name | t ∈ emp ∧ t.dept = 'IT'} just describes the result.

(iv) Strong vs weak entity. A strong entity has its own primary key (single rectangle). A weak entity has no key of its own; it is identified by its partial key (discriminator) together with the key of its owner (identifying) entity, and has total participation in the identifying relationship (double rectangle, double diamond).
e.g. EMPLOYEE(EmpID) is strong; DEPENDENT(Name, Age) is weak, identified by (EmpID, DependentName). Details: Unit 3.

End-sem 2023 (COCSC05) Q1(b)4 marks

Briefly describe the following terms with the help of an example: (i) ACID properties (ii) data abstraction (iii) role of DBA (iv) GRANT and REVOKE.

Show answer

(i) ACID — properties of a transaction. Example: transfer ₹500 from A to B. Atomicity: both debit and credit happen or neither. Consistency: A + B is the same before and after. Isolation: another transaction does not see A debited but B not yet credited. Durability: once committed, the transfer survives a crash.

(ii) Data abstraction — hiding storage details through three levels: physical (how stored — files, indexes), logical (what is stored — tables such as ACCOUNT(AccNo, Balance)), view (what a user sees — a customer sees only their own balance).

(iii) Role of DBA — the person with central control of the database: defines the schema (DDL), decides storage structures and access methods, modifies schema and physical organisation, grants authorisation to users, and does routine maintenance (backups, disk space, performance monitoring, recovery).

(iv) GRANT / REVOKE — DCL commands. GRANT gives privileges; REVOKE takes them back.

GRANT SELECT, UPDATE ON account TO clerk1;   -- clerk1 may read and modify account
REVOKE UPDATE ON account FROM clerk1;        -- now clerk1 can only read
Mid-sem 2023 Q5(a)2 marks

Is every superkey a candidate key? Give reasons to justify your answer.

Show answer

No. A candidate key is a minimal superkey; a superkey may contain extra attributes. Every candidate key is a superkey, but a superkey is a candidate key only if no proper subset of it is also a superkey.

Example: STUDENT(Roll, Name, Phone) with Roll unique: {Roll} is a candidate key; {Roll, Name} is a superkey (it identifies tuples) but not a candidate key, because its subset {Roll} already identifies tuples.
