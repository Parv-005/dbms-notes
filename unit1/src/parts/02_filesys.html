2File-processing system vs DBMS

Before DBMSs, organisations kept data in separate files (today: Excel/CSV sheets), each created and managed by its own application program. New needs meant new files and new programs. This is the file-processing system.

2.1 Problems of the file-processing system (Korth’s list — learn all eight)

ProblemWhat it meansExample (university)
1. Data redundancy and inconsistencyThe same data is stored in several files (redundancy). When one copy is updated and others are not, the copies disagree (inconsistency).Address in admissions file changed, fees file still has the old one — which is correct?
2. Difficulty in accessing dataEvery new question needs a new program; no general query language.“Students in Delhi with CGPA > 8” — no program exists; write one or do it by hand.
3. Data isolationData is scattered in files of different formats, so writing programs that combine them is hard.marks.dat is binary, fees.xls is Excel — joining them needs custom code.
4. Integrity problemsConstraints (balance ≥ 0, marks ≤ 100) are buried in program code; adding or changing one means changing many programs.One program forgets the check and stores marks = 120.
5. Atomicity problemsA failure in the middle of an operation leaves data half-updated; files cannot “undo”.Transfer ₹500 A→B: A debited, power fails, B never credited.
6. Concurrent-access anomaliesTwo users updating the same file at once interfere (lost update); files have no concurrency control.Two clerks read balance 1000 and each withdraws 100 — final 900 instead of 800.
7. Security problemsHard to give each user access to only part of the data; whoever can open a file sees all of it.A fees clerk can open the whole marks sheet.
8. No backup / recovery, poor sharingBackup is manual; a corrupted file is lost; a file locked by one user cannot be shared.Excel file “locked for editing by another user”.

2.3 When a file system is still the better choice

A DBMS has overhead (cost, setup, administration, CPU for security/concurrency/recovery). Use plain files when:

  • the data is small and simple and will not change structure (a personal contact list, a to-do app);
  • there is a single user / single application, no concurrent updates (a programme’s configuration file);
  • real-time / embedded systems with tight memory or time limits (a washing-machine controller, a car ECU, sensor loggers);
  • data is written once and read sequentially (log files, scientific instrument dumps, video/audio streams);
  • a one-time job where the cost of designing a database is not justified.
