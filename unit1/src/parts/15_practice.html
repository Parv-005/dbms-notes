15Practice questions (a step harder than the PYQs)

Same pattern as the papers, but each one needs you to apply two or three ideas together. Try writing a full answer before opening the outline.

P15 marks

A city hospital’s pharmacy keeps stock in one Excel file per counter. During a night shift two pharmacists at different counters sell the last strip of the same medicine, a third updates the price in only one file, and a crash corrupts a file in the middle of saving. (a) Name the exact file-system problem shown by each event. (b) For each, name the DBMS component and mechanism that would have prevented it. (c) Give one reason the pharmacy might still hesitate to adopt a DBMS.

Answer outline
  • Double sale → concurrent-access anomaly (lost update) → transaction manager: concurrency control (locking/2PL) serialises the two sales; the second sees stock = 0.
  • Price changed in one file → redundancy + inconsistency → integrated database with one MEDICINE row (price stored once), managed by the storage manager; PK prevents duplicates.
  • Crash mid-save → atomicity / no recovery → transaction manager’s recovery with a write-ahead log: undo the incomplete transaction, redo committed ones; plus backups.
  • Hesitation: cost of software/hardware and training, need for a DBA, single point of failure if the central server goes down (needs replication/UPS).
P25 marks

Classify each change as needing physical or logical data independence (or neither — programs must change), and name the mapping that absorbs it: (i) STUDENT table is partitioned by admission year across two disks; (ii) a column Aadhaar is added to STUDENT; (iii) STUDENT is split into STUDENT_BASIC(Roll, Name, Dept) and STUDENT_CONTACT(Roll, Phone, Email); (iv) the column Phone is deleted because it is no longer collected and an app displays it; (v) a hash index replaces a B+ tree on Roll.

Answer outline
  1. (i) physical — conceptual/internal mapping.
  2. (ii) logical — external/conceptual mapping; existing views simply do not include the new column.
  3. (iii) logical — redefine the old STUDENT view as the join of the two tables on Roll; read-only programs continue (updates through the join view may not be allowed — why logical independence is hard).
  4. (iv) neither — information the program needs no longer exists; no mapping can hide its removal; the app must change.
  5. (v) physical — conceptual/internal mapping. (Note: range queries on Roll become slower — independence protects correctness, not performance.)
P35 marks

An Indian Railways-style system stores Trains, Stations, Routes (ordered stops of a train) and Bookings. (a) Show how the fact “train 12951 stops at Kota and Vadodara, and Vadodara is also a stop of train 12009” would be stored in the hierarchical, network and relational models — draw the record structure for each. (b) For the query “all trains stopping at Vadodara”, explain the work each model does. (c) Recommend a model.

Answer outline
  • Hierarchical Train → Stop(Station): Vadodara record duplicated under both trains. Query: scan every train’s subtree — whole database.
  • Network: TRAIN and STATION records, STOP link records (with sequence number) owned by both. Query: find Vadodara, follow its STOP member chain, go to each owner train — fast, but written as navigation code.
  • Relational: TRAIN(TrainNo, Name), STATION(Code, Name), STOP(TrainNo, Code, Seq, Arr, Dep). Query: SELECT TrainNo FROM stop WHERE code='BRC', an index on STOP.Code makes it fast.
  • Recommend relational: M:N stops, ad-hoc enquiries (between two stations, by date), ACID bookings for seats, data independence.
P45 marks

For an online examination portal used by 50,000 students at once: (a) design the external, conceptual and internal schemas (give at least two external views and name concrete storage choices); (b) justify a 3-tier rather than 2-tier deployment with four distinct reasons specific to exams; (c) which DBMS components from the system-structure diagram are most stressed during the exam, and why?

Answer outline
  • (a) Conceptual: STUDENT, EXAM, QUESTION, OPTION, RESPONSE(Roll, ExamID, QID, Answer, Time), RESULT. Views: student — own paper questions without correct answers, own responses; examiner — question bank with answers, all responses for their exam; admin — attendance/logs. Internal: RESPONSE clustered on (ExamID, Roll), hash index on Roll, questions cached in memory, SSD storage, partitioning by ExamID.
  • (b) Security (no DB credentials/answers on clients; server validates timing and prevents answer tampering), scalability (load-balanced app servers, connection pooling for 50,000 users), central control of rules (time limits, shuffling) changed once, ability to cache question papers in the middle tier to protect the DB.
  • (c) Transaction manager (huge concurrent inserts of responses, must be durable — a submitted answer must survive a crash), buffer manager (hot question pages), authorization manager (every request checked), file manager/log disk for write throughput.
P55 marks

A food-delivery app stores: restaurant menus (items vary — combos, add-ons, sizes), live delivery-partner GPS pings every 5 seconds, orders and payments, customer–restaurant–cuisine preferences for recommendations, and OTP codes valid for 2 minutes. For each, choose RDBMS or a specific NoSQL type and justify in terms of schema, scale and consistency. Then state one risk of using many databases together.

Answer outline
  • Menus → document DB (nested, varying structure, read-heavy).
  • GPS pings → column-family / time-series store (very high write rate, append-only, time-ordered, eventual consistency fine).
  • Orders and payments → RDBMS (ACID; order + payment + restaurant payout atomic; FKs; reporting).
  • Preferences/recommendations → graph DB (traversals customer → cuisine → restaurant → similar customers).
  • OTPs → key-value store with TTL expiry (Redis): simple key lookup, very fast, auto-delete.
  • Risk: keeping data consistent across stores (an order in the RDBMS but not reflected in the cache/graph), more operational complexity, more skills needed.
P64 marks

“Views give both data abstraction and security, but they are not a replacement for integrity constraints.” Explain with an example from a banking database where a view is used correctly for security, and a case where relying on a view (instead of a constraint) would let invalid data in.

Answer outline
  • Security: CREATE VIEW my_account AS SELECT … WHERE cust_id = CURRENT_USER and GRANT SELECT on it only — the customer cannot see others’ accounts.
  • Integrity failure: a branch view WHERE branch='Dwarka' used for inserts does not stop another program inserting directly into ACCOUNT with a negative balance or a non-existent branch; only CHECK (balance >= 0) and FOREIGN KEY (branch) REFERENCES branch on the base table guarantee validity for every path (also WITH CHECK OPTION limits only that view).
  • Point: security controls who; integrity controls what values; constraints belong to the conceptual schema and apply to all users.
P74 marks

A company’s organisation chart (CEO → VPs → managers → employees) is stored relationally as EMP(EmpID, Name, ManagerID). (a) Why might a hierarchical model look attractive for this data? (b) Which query is easy in the hierarchical model but needs special SQL in the relational model? (c) What happens to each model when the company introduces matrix management (an employee reports to two managers)?

Answer outline
  • (a) Data is a strict tree (1:N), accessed top-down — exactly the hierarchical model’s strength; pointer traversal is fast.
  • (b) “All employees under VP X at any depth” — a tree traversal in hierarchical; in SQL needs a recursive query (WITH RECURSIVE) or repeated self-joins.
  • (c) Hierarchical breaks — a child can have only one parent, so the employee must be duplicated (redundancy, inconsistency) or virtual pointers used. Relational adapts by adding a REPORTS_TO(EmpID, ManagerID) table (M:N) — no program needing EMP alone breaks if a view keeps the old shape (logical data independence).
P84 marks

Trace what happens inside the DBMS, component by component, when a clerk runs UPDATE account SET balance = balance - 500 WHERE acc_no = 101; followed by COMMIT, and the power fails one second after COMMIT returns.

Answer outline
  1. Query tool sends the statement → DML compiler parses, checks against the data dictionary, optimiser chooses the index on acc_no (uses statistics) → plan to the query evaluation engine.
  2. Authorization manager checks the clerk has UPDATE privilege; integrity manager checks constraints (e.g. CHECK balance ≥ 0).
  3. Transaction manager starts the transaction, takes an exclusive lock on the row (concurrency control), writes a log record (old and new value).
  4. Buffer manager brings the page into memory (via the file manager), the value is changed in the buffer.
  5. COMMIT: log records are forced to disk (write-ahead logging), lock released, “success” returned. The data page itself may still be only in memory.
  6. Power fails → on restart the recovery manager redoes the committed update from the log → durability. If the failure had been before COMMIT, it would undo it → atomicity.
