14.5 SQL vs NoSQL for an application

End-sem 2025 Q1(c)5 marks

You are hired to design the data storage strategy for a large-scale e-commerce platform like Amazon. Compare SQL and NoSQL databases on the basis of data model, schema flexibility, scalability, consistency and use-case suitability. Based on this comparison, justify which type of database (or combination) would be more appropriate for the e-commerce system and why.

Show answer
BasisSQL (RDBMS)NoSQL
Data modelTables, rows, columns; relationships by PK–FK; joinsKey-value, document (JSON), column-family, graph
Schema flexibilityFixed schema defined before inserting; ALTER for changesFlexible — each document may have different fields
ScalabilityMainly vertical (bigger server); sharding is complexHorizontal — add commodity servers; built-in sharding and replication
ConsistencyStrong; ACID multi-row transactionsUsually eventual consistency (BASE; CAP favours availability)
Use-case suitabilityStructured, critical, relational data with complex queriesHuge volume, high velocity, semi/unstructured data, simple access patterns

Mapping Amazon’s data:

  • Orders, payments, inventory counts, customer accounts → RDBMS. Money and stock must never be wrong; placing an order must atomically reduce stock, create the order and record payment (ACID). Complex reporting (sales by region) needs joins.
  • Product catalog → document store (MongoDB): a phone has RAM/camera fields, a shirt has size/fabric — a flexible schema avoids hundreds of nullable columns.
  • Shopping carts, sessions → key-value store (Redis/DynamoDB): very high read/write rate, simple key access, must stay available.
  • Browsing history, clickstream, logs → column-family store (Cassandra): billions of writes per day, time-ordered, horizontally scalable.
  • “Customers who bought this also bought” → graph database (Neo4j) or analytics over the above.

Conclusion: a combination (polyglot persistence) — an RDBMS as the system of record for transactional data where consistency matters, and NoSQL stores for catalog, carts, activity data and recommendations where scale, flexibility and availability matter. Using only SQL would struggle with scale and schema variety; using only NoSQL would risk inconsistent orders and payments.

An e-commerce platform stores customer reviews, browsing history, product catalogs and transaction records. Explain why a NoSQL database may be preferred for some of these data while an RDBMS is suitable for others. Justify your answer with examples.

DataNatureChoice and reason
Transaction records (orders, payments, refunds)Structured, relational, criticalRDBMS (MySQL/PostgreSQL/Oracle): ACID — an order and its payment must commit together; FK from ORDER to CUSTOMER and PRODUCT; complex financial reports with joins and aggregates; strong consistency for audits.
Product catalogSemi-structured; attributes vary by category; read-heavyDocument DB (MongoDB): each product a JSON document with its own fields and nested variants/images; no schema migration when a new category is added; easy horizontal scaling for heavy reads.
Customer reviewsUnstructured text, ratings, images; huge volume; eventual consistency acceptableDocument DB (reviews embedded or stored per product) or wide-column store; a review appearing a second late is fine.
Browsing historyAppend-only, time-series, very high write rateColumn-family DB (Cassandra/HBase): fast writes partitioned by user and time across many nodes; used for recommendations.

Why: NoSQL is preferred where data is high-volume, schema-flexible and tolerant of eventual consistency (scale-out, availability); an RDBMS is required where data is structured and must be exactly correct (ACID, constraints, joins). Hence the platform should use both.

End-sem 2024 Q1(c)5 marks

A social media company needs to store vast amounts of user-generated content, including comments, likes and shares, which vary greatly in structure. Explain why a NoSQL database might be more suitable for this task than an RDBMS, and describe the type of NoSQL database model you would recommend.

Show answer

Why NoSQL is more suitable here

  1. Varying structure: a post may be text, an image with tags, a video with captions, a poll; comments nest inside comments. A fixed relational schema would need many tables or many NULL columns and frequent ALTERs; NoSQL’s flexible schema stores each item with exactly its own fields.
  2. Volume and velocity: billions of likes/comments per day. NoSQL scales horizontally by sharding across commodity servers; an RDBMS mostly scales up one server.
  3. Availability over strict consistency: a like count that is a few seconds stale is acceptable; NoSQL (BASE, eventual consistency) stays available and fast during failures and across data centres.
  4. Fewer joins: a post with its comments and like counts can be stored together (denormalized) and read in one access, which is faster than joining POST, COMMENT, LIKE tables for every feed load.

Recommended model: a document database (e.g. MongoDB) for posts and comments — each post a JSON document:

{ "post_id": 9012, "user": "u45", "type": "image", "url": "…/img.jpg", "tags": ["travel","goa"],
  "likes": 1532, "shares": 87,
  "comments": [ { "user": "u7", "text": "Nice!", "replies": [ { "user": "u45", "text": "Thanks" } ] } ] }

Complemented by a graph database (Neo4j) for the friend/follower network and recommendations, a wide-column store (Cassandra) for activity feeds and like events, and a key-value store (Redis) for counters and sessions. User accounts and payments (ads billing) can remain in an RDBMS.
