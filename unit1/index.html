Definition — DBMS (write this)

A Database Management System is a collection of interrelated data and a set of programs to access that data. Its primary goal is to provide a way to store and retrieve database information that is both convenient and efficient. It manages large amounts of data, provides mechanisms for defining structures, manipulating data, ensuring safety (security, crash recovery) and sharing (concurrent access) of the data.

Functions of a DBMS (Elmasri): define (specify data types, structures, constraints — stored as metadata), construct (store data on a storage medium), manipulate (query, update, generate reports), share (many users and programs at the same time), and protect (against hardware/software failure and unauthorised access) and maintain the database over its long life.

1.2 Characteristics of the database approach

  1. Self-describing nature — the database stores its own definition (metadata in the catalog), so the DBMS works with any database.
  2. Insulation between programs and data (data abstraction) — programs do not depend on the storage format (program–data independence).
  3. Support of multiple views — each user can see a different subset/derivation of the data.
  4. Sharing of data and multi-user transaction processing — concurrency control makes simultaneous updates correct (ACID).
  5. Plus: controlled redundancy, integrity constraints, security, backup and recovery, efficient query processing.

1.3 Applications

Banking (accounts, loans, transactions), airlines and railways (reservations, schedules — IRCTC), universities (registration, grades), telecom (call records, monthly bills), finance (stock trades), sales and e-commerce (customers, products, orders), manufacturing (inventory, supply chain), HR (payroll), healthcare (patient records), government (Aadhaar, electoral rolls), social media (posts, likes — often NoSQL).

1.4 Schema and instance

Schema (intension)

The overall design / description of the database: relation names, attributes, types, constraints. Specified at design time; changes rarely. Analogy: the type and variable declarations of a program.

Instance (extension, state)

The data stored in the database at a particular moment. Changes with every insert, delete, update. Analogy: the current values of the variables.

There is one schema per level of abstraction: physical schema, logical (conceptual) schema and several sub-schemas (views) — section 4.

2File-processing system vs DBMS

Before DBMSs, organisations kept data in separate files (today: Excel/CSV sheets), each created and managed by its own application program. New needs meant new files and new programs. This is the file-processing system.

2.1 Problems of the file-processing system (Korth’s list — learn all eight)

1. Data redundancy and inconsistencyThe same data is stored in several files (redundancy). When one copy is updated and others are not, the copies disagree (inconsistency).Address in admissions file changed, fees file still has the old one — which is correct?
2. Difficulty in accessing dataEvery new question needs a new program; no general query language.“Students in Delhi with CGPA > 8” — no program exists; write one or do it by hand.
3. Data isolationData is scattered in files of different formats, so writing programs that combine them is hard.marks.dat is binary, fees.xls is Excel — joining them needs custom code.

5. Atomicity problemsA failure in the middle of an operation leaves data half-updated; files cannot “undo”.Transfer ₹500 A→B: A debited, power fails, B never credited.

7. Security problemsHard to give each user access to only part of the data; whoever can open a file sees all of it.A fees clerk can open the whole marks sheet.

2.3 When a file system is still the better choice

A DBMS has overhead (cost, setup, administration, CPU for security/concurrency/recovery). Use plain files when:

  • the data is small and simple and will not change structure (a personal contact list, a to-do app);
  • there is a single user / single application, no concurrent updates (a programme’s configuration file);
  • real-time / embedded systems with tight memory or time limits (a washing-machine controller, a car ECU, sensor loggers);
  • data is written once and read sequentially (log files, scientific instrument dumps, video/audio streams);
  • a one-time job where the cost of designing a database is not justified.

3.2 Disadvantages

  • Cost of software licences, faster hardware, more memory and disk.
  • Complexity — design and administration need trained staff (DBA); a bad design harms everyone.
  • Size — the DBMS itself occupies a lot of disk and memory.

  • Higher impact of failure — data is centralised, so a failure or corruption affects every application (single point of failure, unless replicated).
  • Conversion cost — migrating old files and retraining users.

4Levels of abstraction and the three-schema architecture

Definition — data abstraction

Data abstraction is hiding the complex details of how data is stored and maintained, and showing each user only what they need. Database users are often not computer experts, so the DBMS hides complexity through three levels of abstraction.

4.1 The three levels

LevelDescribesWho works here
Physical (internal) level — lowestHow the data is actually stored: files, record layouts, byte offsets, indexes (B+ trees, hashing), compression, block placement.DBMS developers, DBA (tuning)
Logical (conceptual) levelWhat data is stored and the relationships among it, for the whole database: entities/tables, attributes, data types, keys, constraints. Hides physical details.DBA, database designers, programmers
View (external) level — highestOnly the part of the database a particular user group needs; many views exist for one database. Hides the rest (also for security).End users, applications
Example — university database at all three levels (fits most PYQs)

Physical: STUDENT records are stored in file stu.dat as fixed-length 60-byte records — Roll CHAR(11) at offset 0, Name 30 bytes at offset 11, DeptID 4 bytes at offset 41, CGPA REAL at offset 45 … — with a B+ tree index on Roll and a hash index on DeptID.

Logical: STUDENT(Roll, Name, DOB, DeptID, CGPA, Phone), COURSE(CID, Title, Credits), ENROLLED(Roll, CID, Sem, Grade), FEE(Roll, Sem, Amount, Paid); Roll is the primary key, ENROLLED.Roll is a foreign key.

View: a student sees MyResult(CID, Title, Grade) for their own roll only; the accounts office sees FeeStatus(Roll, Name, Amount, Paid) but no grades; a faculty member sees ClassList(Roll, Name, Grade) for their own course.

4.2 Three-schema (ANSI/SPARC) architecture

Proposed by the ANSI/SPARC committee (1975) to separate user applications from the physical database. One schema is defined at each level:

  • Internal schema — physical storage structure and access paths (uses a physical data model).
  • Conceptual schema — structure of the whole database for the whole community of users (uses a representational model, e.g. relational).
  • External schemas (sub-schemas / user views) — one per user group.

Mappings: the DBMS transforms requests and results between levels. The external/conceptual mapping relates each view to the conceptual schema; the conceptual/internal mapping relates the conceptual schema to the stored files. The levels themselves are only descriptions — the only data that really exists is at the physical level.

4.3 How data abstraction is ensured (achieved) in a DBMS

  1. The DBMS keeps a separate schema for each level in the data dictionary.
  2. Users and programs are written against an external schema (a view) or the conceptual schema, never against files.
  3. The DBMS automatically converts every request through the two mappings down to physical operations, and converts results back.
  4. Declarative languages (SQL says what, not how), views, and the query optimiser hide access paths; GRANT on views hides the rest of the data.

Benefits: users see a simple model; different users get different views; security (hide what a user must not see); and, most importantly, data independence (next section).

Common mistake

Do not confuse the three levels of abstraction (physical / logical / view — about description of data) with 1/2/3-tier architecture (about where the machines/programs run — section 7.2).

5Data independence

Definition

Data independence is the capacity to change the schema at one level of the database system without having to change the schema at the next higher level (and hence without changing application programs). Only the mapping between the two levels changes.

Physical data independence

Change the internal schema without changing the conceptual schema (or views/programs).

Examples: move data from HDD to SSD; add or drop an index; change file organisation (heap → B+ tree / hashing); compress or partition a table; move files to another disk. Only the conceptual/internal mapping changes.

Comparatively easy to achieve; all modern DBMSs provide it.

Logical data independence

Change the conceptual schema without changing external schemas or application programs.

Examples: add a new attribute (Student.Email) or a new table; split STUDENT into STUDENT and ADDRESS; merge two tables. Views are redefined on the new tables so programs still see the old shape. Only the external/conceptual mapping changes.

Harder to achieve.

5.1 Why logical data independence is harder

  • Applications depend heavily on the logical structure — names of tables and columns, their meaning and relationships — far more than on storage details.
  • Removing an attribute or changing its meaning cannot be hidden: a program that needs that data must change.
  • Views that join split tables are not always updatable, so programs that write through the view may break.

Why it matters

Without data independence (file systems), every change in storage format or record structure means finding and rewriting every program that touches the file. With it, the DBA can tune and evolve the database while applications keep running — lower maintenance cost, faster evolution.

6Data models and their comparison

Definition — data model

A data model is a collection of conceptual tools for describing data, relationships between data, data semantics (meaning) and consistency constraints. It gives the structure of the database, and usually a set of basic operations for retrieving and updating it.

6.1 Categories of data models

CategoryLevelExamples
High-level / conceptual (object-based)Close to how users see data: entities, attributes, relationshipsER model, object-oriented model
Representational / implementation (record-based)Understood by users but also directly implemented; data is in fixed-format recordsRelational, network, hierarchical
Low-level / physicalHow data is stored: record formats, orderings, access pathsUnifying model, frame-memory model, index structures
Self-describing / semi-structuredData and schema stored togetherXML, JSON / NoSQL document and key-value stores

The syllabus compares the three record-based models. Use the same data in all three — Department IT, courses DBMS and OS, teacher Rao, students Asha (takes both courses), Vikram (DBMS) and Neha (OS).

6.2 Hierarchical model

  • Data is organised as a tree of record types; each record has exactly one parent (except the root) and any number of children → represents 1:N.
  • Relationships are physical pointers; access starts at the root and goes down (pre-order traversal). Languages are procedural (e.g. DL/I in IBM IMS, 1960s).
  • Advantages: simple and fast for naturally hierarchical data accessed top-down (organisation charts, bill of materials, file directories, XML, Windows registry); parent–child integrity is automatic (deleting a parent deletes children); efficient for 1:N.
  • Limitations: cannot represent M:N or multiple parents without duplicating records (redundancy → inconsistency); rigid — access path is fixed, so queries not following the tree are slow; insertion of a child without a parent is impossible, deletion of a parent loses children (anomalies); little data independence — restructuring the tree breaks programs.

6.3 Network model

  • Data is a graph: records connected by set types (owner → member, each a 1:N link). A member record can belong to many owners, so M:N is modelled with a link (junction) record. Standardised by CODASYL / DBTG (1971); e.g. IDMS, IDS.
  • Advantages: represents M:N and complex relationships without duplication; faster than hierarchical for such data; more flexible access (start anywhere); data integrity through owner–member rules.
  • Limitations: navigational — programmers must know the pointer structure and write record-at-a-time code (“find owner, get next member …”); complex to design and maintain; changing the structure means rewriting programs (poor data independence); no declarative query language.

6.6 Why the relational model became dominant

  1. Simplicity — everything is a table; easy to understand for users and designers.
  2. Data independence — no physical pointers in the model, so storage can change freely.
  3. Declarative querying — SQL says what is wanted; the optimiser finds the access path. Ad-hoc queries need no new programs.
  4. Mathematical foundation — relational algebra, calculus, FD/normalization theory make design and optimisation rigorous.
  5. Integrity and transactions — declarative constraints, ACID.
  6. Standardisation and ecosystem — SQL is an ANSI/ISO standard; tools, skills and vendors are everywhere; hardware became fast enough for joins.

6.7 Other models (brief)

  • ER model — conceptual model of entities, attributes and relationships, drawn as diagrams; used for design and then mapped to tables (Unit 3).
  • Object-oriented model — data as objects with attributes and methods, classes, inheritance (db4o, ObjectDB); good for CAD, multimedia.
  • Object-relational model — relational + user-defined types, arrays, inheritance (PostgreSQL, Oracle).
  • Semi-structured / NoSQL models — key-value, document, column-family, graph (section 9).

7.3 Centralised, client–server, distributed (types of database systems)

  • Centralised — the database lives at one site (e.g. a college library database); simple control, single point of failure.
  • Distributed — data spread over several sites connected by a network but seen as one database; homogeneous (same DBMS everywhere) or heterogeneous.
  • Cloud — DBMS offered as a service (Amazon RDS, Azure SQL, Google Cloud SQL).
  • By model: relational, NoSQL, object-oriented, hierarchical, network (section 6).

  • Graphical (GUI) — schema shown as a diagram; query by pointing (MySQL Workbench).
  • Natural-language — request written in English is interpreted (chatbots, “text-to-SQL”).
  • Interfaces for parametric users — a small set of operations with function keys (bank tellers, ticket counters).
  • Interfaces for the DBA — privileged commands: create accounts, set parameters, grant authorisation, change schema.

8.4 Phases of database design

  1. Requirements collection and analysis — interview users; list data and operations.
  2. Conceptual design — high-level conceptual schema (ER diagram), independent of any DBMS.
  3. Logical design (data-model mapping) — convert ER to the DBMS’s model (relational tables), normalize.
  4. Physical design — choose storage structures, indexes, partitions for performance on the chosen DBMS (e.g. Oracle, DB2).

10How to answer each question type

Unit-1 questions are theory, but they are marked on structure and application. Use these skeletons; fill them with the scenario’s own nouns.

Type 1 — “X uses files / spreadsheets; how will a DBMS help?”
  1. One line: what the current system is and why it is a file-processing system.
  2. Problems now — pick the 4–5 from RIDIACSB that the question names (redundancy, inconsistency, security, concurrency…), each with an example from the scenario.
  3. How a DBMS fixes each — the matching advantage + the mechanism (PK/UNIQUE, FK, CHECK, GRANT/views, transactions/locking, logs/backup, SQL).
  4. Small comparison table (file system vs DBMS, 5–6 rows).
  5. Conclusion; mention one cost (DBMS is costlier) to show balance.
Type 2 — “Explain levels of abstraction for database X”
  1. Define data abstraction (one line).
  2. Draw the three-schema diagram (views → conceptual → internal → disk, mappings).
  3. For each level: definition + a concrete example from X (file/index for physical, table schemas for logical, two different user views).
  4. Say how the DBMS keeps them apart (schemas + mappings) and the benefit asked (security, no duplication, data independence).
Type 3 — “Data independence”
  1. Definition (change one level without changing the next higher).
  2. Physical: definition + example (index, HDD→SSD) + which mapping changes.
  3. Logical: definition + example (add column / split table, views) + mapping.
  4. Why logical is harder; small table.
Type 4 — “Compare models and recommend one for X”
  1. Identify the relationships in X and their cardinality (are there M:N? multiple parents?) and the expected queries.
  2. One paragraph or diagram per model, applied to X’s data.
  3. Comparison table on the bases the question names.
  4. Recommendation (almost always relational), justified by X’s M:N relationships, ad-hoc queries, integrity and data independence; mention where another model would fit (a pure hierarchy, a social graph).
Type 5 — “SQL or NoSQL for X?”
  1. Split X’s data into kinds (transactions, catalog, logs, social graph…).
  2. Compare SQL and NoSQL on the bases asked (table in section 9).
  3. Map each kind of data to RDBMS or a specific NoSQL type with a reason.
  4. Conclude: hybrid / polyglot persistence (usually).
Type 6 — short definitions / differences (2 marks)
  1. Definition of each term (one line each).
  2. 3–4 row difference table.
  3. One example. Diagram if the question says “with diagram”.
Common mistakes
  • Writing a generic advantages list without ever using the scenario’s words (SIR voter rolls, patients, warehouses…) — loses most marks.
  • Calling the view level “the GUI”. A view is a schema (subset of data), not a screen.
  • Saying “hierarchical cannot represent relationships” — it represents 1:N well; it cannot represent M:N without duplication.
  • Saying “NoSQL has no schema” — the schema is flexible / implicit, not absent.

11Useful extras beyond syllabus

History in five lines

1960s: file systems, then navigational DBMSs — IBM IMS (hierarchical, built for the Apollo programme) and CODASYL/IDMS (network). 1970: Codd’s relational paper. Late 1970s–80s: System R, Ingres, Oracle, DB2; SQL standardised (1986). 1990s: object-relational, data warehouses. 2000s onward: web scale → NoSQL (Bigtable, Dynamo, MongoDB, Cassandra) and later NewSQL (distributed SQL with ACID: Spanner, CockroachDB).

ACID in one line each (used in many Unit-1 answers; full treatment in Unit 5)

Atomicity — all or nothing. Consistency — a transaction takes the DB from one valid state to another. Isolation — concurrent transactions do not see each other’s partial work. Durability — committed changes survive crashes. A file system gives none of these (mid-sem 2024 Q1a).

Codd’s 12 rules and DBMS vs RDBMS

Codd’s rules (information rule, guaranteed access, systematic NULLs, active online catalog, comprehensive sub-language, view updating, high-level insert/update/delete, physical and logical data independence, integrity independence, distribution independence, non-subversion) define what a truly relational DBMS is. Rules 8 and 9 are exactly physical and logical data independence. Covered in Unit 2 §1.6; DBMS vs RDBMS in Unit 2 §1.7.

Database security vs integrity (asked in end-sem 2025 Q1b)

Security = protecting the database from unauthorised access, malicious change or destruction (authentication, authorisation/GRANT, views, encryption, auditing). Integrity = keeping data accurate and consistent against accidental errors by authorised users (domain, entity, referential integrity, CHECK). One protects against the wrong people, the other against wrong values.

12One-page revision sheet

Basics
  • Data = raw facts; information = processed data; metadata = data about data (data dictionary).
  • DBMS = interrelated data + programs to access it; goal: convenient and efficient; define, construct, manipulate, share, protect.
  • Schema = design (rarely changes); instance = data at a moment.
  • DBA: schema definition, storage/access methods, modification, authorisation, routine maintenance (backup, space, performance).
File system problems → DBMS cures
  • RIDIACSB: Redundancy/Inconsistency, Difficult access, Isolation, Integrity, Atomicity, Concurrency, Security, Backup.
  • Cures: single integrated copy, SQL, constraints, transactions (ACID), locking, GRANT/views, log-based recovery.
  • Files still fine: small, single-user, embedded/real-time, sequential logs.
  • DBMS cons: cost, complexity, size, overhead, central failure impact.
Abstraction and independence
  • Physical (how stored) → logical (what is stored, relationships) → view (part for one user).
  • Three-schema (ANSI/SPARC): internal, conceptual, external schemas + two mappings.
  • Physical DI: change internal, conceptual unaffected (index, SSD) — easy.
  • Logical DI: change conceptual, views/programs unaffected (add column, split table) — hard.
Models
  • Hierarchical: tree, one parent, pointers, 1:N, M:N by duplication, IMS.
  • Network: graph, owner–member sets, M:N via link records, navigational, CODASYL/IDMS.
  • Relational: tables, values (PK–FK), declarative SQL, high DI, Codd 1970.
  • Relational won: simple, DI, SQL + optimiser, theory, ACID, standard.
Structure and tiers
  • Query processor: DDL interpreter, DML compiler/optimiser, embedded DML precompiler, evaluation engine.
  • Storage manager: authorisation & integrity, transaction, file, buffer managers. Disk: data, indices, dictionary, statistics.
  • 1-tier local · 2-tier client ↔ DB (ODBC/JDBC) · 3-tier client ↔ app server ↔ DB (web apps).
Languages, NoSQL
  • DDL (CREATE, ALTER, DROP, TRUNCATE) · DML (SELECT, INSERT, UPDATE, DELETE) · DCL (GRANT, REVOKE) · TCL (COMMIT, ROLLBACK, SAVEPOINT).
  • Procedural = what + how (RA, PL/SQL); non-procedural = what (SQL, RC).
  • NoSQL: key-value, document, column-family, graph; flexible schema, horizontal scale, BASE. Money → SQL.

End-sem 2025 Q1(a)5 marks

During the Special Intensive Revision (SIR) of electoral rolls, the Election Commission needs to update, verify and correct lakhs of voter records across districts. Currently the data is stored in multiple Excel/CSV files maintained separately by different officers. Analyze the risks of continuing with a file-based system for SIR and justify how adopting a DBMS can improve accuracy, security, deduplication and faster roll revision. Provide five strong arguments.

Show answer

Current situation. Each district / booth officer keeps a separate Excel or CSV file of voters. This is a file-processing system: no common schema, no central control, no constraints, no concurrency control.

Risks of continuing with files

  • Duplicate voters (redundancy): a person who moved from Rohini to Dwarka can appear in both districts’ files; nothing stops the same EPIC or Aadhaar-linked voter being entered twice.
  • Inconsistency: a correction (spelling, address, deceased status) made in one copy is not made in others; different officers hold different “truths”.
  • No validation (integrity): wrong ages (< 18), invalid constituency codes, blank mandatory fields are accepted.
  • Security: files are e-mailed and copied on pen drives; anyone with the file can read or alter every voter’s personal data; no audit trail.
  • Slow revision and lost updates: merging lakhs of rows by hand is slow; two officers editing the same file overwrite each other; a crash corrupts the file with no recovery.

Five arguments for a DBMS

  1. Deduplication by design. One central VOTER table with EPIC_No PRIMARY KEY and UNIQUE (Aadhaar_ref); the DBMS rejects a second entry. SQL can also find near-duplicates (GROUP BY name, father_name, dob HAVING COUNT(*) > 1) across all districts at once.
  2. Accuracy through integrity constraints. CHECK (age >= 18), NOT NULL on name/address, FOREIGN KEY (constituency_id) REFERENCES constituency — invalid data cannot be stored, whoever enters it.
  3. Security. Each officer logs in with an account; GRANT UPDATE only on their district’s view, read-only access for observers; encryption and audit logs show who changed which record and when.
  4. Consistency and concurrent access. All officers work on one copy; transactions and locking let thousands update simultaneously without lost updates; a correction is instantly visible everywhere.
  5. Faster revision, backup and recovery. Indexed SQL queries (e.g. all voters aged 18 by 1 January, all records flagged deceased) run in seconds instead of days of manual merging; automatic backups and log-based recovery protect against crashes; data independence lets the EC add fields (e.g. a verification_status column) without rewriting the officers’ apps.

A DBMS turns many unsynchronised spreadsheets into one controlled, constrained, secure, concurrently-updatable database — which is exactly what an accurate, duplicate-free, quickly revised electoral roll needs.

A small company currently stores its data using a simple file system. The manager wants to switch to a DBMS but is unsure if it would be worth the change. Describe how this transition could benefit the company in terms of data organization, retrieval and security.

Show answer

Data organization.

  • Files: customers, orders, invoices and employees are in separate files of different formats; customer details are repeated in the orders and invoice files → redundancy and inconsistency, and data isolation.

Data retrieval.

  • Files: every new report needs a new program or manual work (“customers who ordered more than ₹1 lakh last quarter”).

  • Files: OS-level access only — whoever opens the salary file sees all salaries; no audit.

Mid-sem 2021 Q1(a)4 marks

What is DBMS? Discuss its disadvantages.

Show answer

A DBMS is a collection of interrelated data and a set of programs to access that data; its goal is to store and retrieve information conveniently and efficiently. It lets users define (DDL), construct, manipulate (DML) and share a database while providing security, integrity, concurrency control and recovery. Examples: Oracle, MySQL, PostgreSQL, SQL Server. Mid-sem 2024 Q1(a)2 marks

How could the lack of support for ACID properties in a file system affect the reliability of data operations compared to a DBMS, especially in financial or transactional applications?

Show answer

Take a transfer of ₹1000 from account A to B (debit A, credit B):

  • No atomicity: a crash after debiting A leaves ₹1000 lost; a file cannot roll back the half-done operation.
  • No consistency: rules like “total money unchanged” or “balance ≥ 0” are not enforced; invalid states are saved.
  • No isolation: two concurrent withdrawals both read balance 5000 and write 4000 — one withdrawal is lost (lost update); reports read half-updated data.
  • No durability: a write still in an OS buffer is lost on power failure even after the customer is told “success”.

A DBMS executes the transfer as a transaction: the log and recovery manager give atomicity and durability (undo/redo), constraints give consistency, and locking (2PL) gives isolation — so financial data stays correct even with failures and thousands of concurrent users.

What is data abstraction? Explain in brief with the help of a suitable diagram.

Show answer

Data abstraction is the process of hiding the complex, irrelevant details of how data is stored and maintained from users, showing each user only the data relevant to them. Since many database users are not computer-trained, the DBMS provides abstraction at three levels:

  1. Physical (internal) level — lowest level; describes how data is actually stored: record formats, file organisation, indexes, block placement.

How are data independence and data abstraction achieved in DBMS?

Show answer

Data abstraction is achieved by the three-schema architecture: internal schema (how data is stored), conceptual schema (what data and relationships), external schemas (user views). Users interact only with views/conceptual schema; the DBMS uses mappings to convert requests down to the stored data and results back. [Draw the three-schema diagram.]

Data independence is achieved because of these mappings: when one level changes, only the mapping to the level above is changed.

Abstraction = separate schemas at three levels; independence = changes absorbed in the mappings between them.

Show answer

2. Query processor

  • Embedded DML pre-compiler — converts DML embedded in host programs into procedure calls.

  • Transaction manager — ensures consistency despite failures (recovery) and concurrency (concurrency control).
  • File manager — allocates disk space and manages on-disk data structures.
  • Buffer manager — moves data between disk and main memory; decides what to cache.

4. Disk storage: data files (the database), data dictionary (metadata — schemas, constraints, users), indices (fast access), statistical data (used by the optimiser).

End-sem 2023 (COCSC05) Q1(a)4 marks

Highlight the key difference between the following with the help of suitable examples: (i) DDL and DML (ii) candidate key and super key (iii) procedural and non-procedural language (iv) strong and weak entities.

Show answer

(i) DDL vs DML. DDL defines/changes the structure (schema) of the database — CREATE, ALTER, DROP, TRUNCATE; its result is stored in the data dictionary and it is auto-committed. DML accesses and changes the data — SELECT, INSERT, UPDATE, DELETE; it can be rolled back.
e.g. CREATE TABLE emp(id INT PRIMARY KEY, name VARCHAR(30)) is DDL; INSERT INTO emp VALUES (1,'Asha') is DML.

(ii) Candidate key vs super key. A super key is any set of attributes that uniquely identifies a tuple; a candidate key is a minimal super key (no proper subset is a super key). Every candidate key is a super key, not vice-versa.
e.g. STUDENT(Roll, Email, Name): {Roll}, {Email} are candidate keys; {Roll, Name} is a super key but not a candidate key.

(iii) Procedural vs non-procedural. Procedural: the user specifies what data and how to get it (sequence of operations) — relational algebra, PL/SQL, CODASYL DML. Non-procedural (declarative): the user specifies only what — SQL SELECT, relational calculus; the DBMS decides how.
e.g. RA: πname(σdept='IT'(emp)) is a sequence of steps; TRC {t.name | t ∈ emp ∧ t.dept = 'IT'} just describes the result.

(iv) Strong vs weak entity. A strong entity has its own primary key (single rectangle). A weak entity has no key of its own; it is identified by its partial key (discriminator) together with the key of its owner (identifying) entity, and has total participation in the identifying relationship (double rectangle, double diamond).
e.g. EMPLOYEE(EmpID) is strong; DEPENDENT(Name, Age) is weak, identified by (EmpID, DependentName). Details: Unit 3.

Why: NoSQL is preferred where data is high-volume, schema-flexible and tolerant of eventual consistency (scale-out, availability); an RDBMS is required where data is structured and must be exactly correct (ACID, constraints, joins). Hence the platform should use both.

A social media company needs to store vast amounts of user-generated content, including comments, likes and shares, which vary greatly in structure. Explain why a NoSQL database might be more suitable for this task than an RDBMS, and describe the type of NoSQL database model you would recommend.

Show answer

Why NoSQL is more suitable here

  1. Varying structure: a post may be text, an image with tags, a video with captions, a poll; comments nest inside comments. A fixed relational schema would need many tables or many NULL columns and frequent ALTERs; NoSQL’s flexible schema stores each item with exactly its own fields.
  2. Volume and velocity: billions of likes/comments per day. NoSQL scales horizontally by sharding across commodity servers; an RDBMS mostly scales up one server.
  3. Availability over strict consistency: a like count that is a few seconds stale is acceptable; NoSQL (BASE, eventual consistency) stays available and fast during failures and across data centres.
  4. Fewer joins: a post with its comments and like counts can be stored together (denormalized) and read in one access, which is faster than joining POST, COMMENT, LIKE tables for every feed load.

Recommended model: a document database (e.g. MongoDB) for posts and comments — each post a JSON document:

{ "post_id": 9012, "user": "u45", "type": "image", "url": "…/img.jpg", "tags": ["travel","goa"],
  "likes": 1532, "shares": 87,
  "comments": [ { "user": "u7", "text": "Nice!", "replies": [ { "user": "u45", "text": "Thanks" } ] } ] }

Complemented by a graph database (Neo4j) for the friend/follower network and recommendations, a wide-column store (Cassandra) for activity feeds and like events, and a key-value store (Redis) for counters and sessions. User accounts and payments (ads billing) can remain in an RDBMS.

A city hospital’s pharmacy keeps stock in one Excel file per counter. During a night shift two pharmacists at different counters sell the last strip of the same medicine, a third updates the price in only one file, and a crash corrupts a file in the middle of saving. (a) Name the exact file-system problem shown by each event. (b) For each, name the DBMS component and mechanism that would have prevented it. (c) Give one reason the pharmacy might still hesitate to adopt a DBMS.

Answer outline
  • Double sale → concurrent-access anomaly (lost update) → transaction manager: concurrency control (locking/2PL) serialises the two sales; the second sees stock = 0.
  • Price changed in one file → redundancy + inconsistency → integrated database with one MEDICINE row (price stored once), managed by the storage manager; PK prevents duplicates.

Classify each change as needing physical or logical data independence (or neither — programs must change), and name the mapping that absorbs it: (i) STUDENT table is partitioned by admission year across two disks; (ii) a column Aadhaar is added to STUDENT; (iii) STUDENT is split into STUDENT_BASIC(Roll, Name, Dept) and STUDENT_CONTACT(Roll, Phone, Email); (iv) the column Phone is deleted because it is no longer collected and an app displays it; (v) a hash index replaces a B+ tree on Roll.

P64 marks

“Views give both data abstraction and security, but they are not a replacement for integrity constraints.” Explain with an example from a banking database where a view is used correctly for security, and a case where relying on a view (instead of a constraint) would let invalid data in.

Answer outline
  • Security: CREATE VIEW my_account AS SELECT … WHERE cust_id = CURRENT_USER and GRANT SELECT on it only — the customer cannot see others’ accounts.
  • Integrity failure: a branch view WHERE branch='Dwarka' used for inserts does not stop another program inserting directly into ACCOUNT with a negative balance or a non-existent branch; only CHECK (balance >= 0) and FOREIGN KEY (branch) REFERENCES branch on the base table guarantee validity for every path (also WITH CHECK OPTION limits only that view).
  • Point: security controls who; integrity controls what values; constraints belong to the conceptual schema and apply to all users.
P74 marks

A company’s organisation chart (CEO → VPs → managers → employees) is stored relationally as EMP(EmpID, Name, ManagerID). (a) Why might a hierarchical model look attractive for this data? (b) Which query is easy in the hierarchical model but needs special SQL in the relational model? (c) What happens to each model when the company introduces matrix management (an employee reports to two managers)?

Answer outline
  • (a) Data is a strict tree (1:N), accessed top-down — exactly the hierarchical model’s strength; pointer traversal is fast.
  • (b) “All employees under VP X at any depth” — a tree traversal in hierarchical; in SQL needs a recursive query (WITH RECURSIVE) or repeated self-joins.
  • (c) Hierarchical breaks — a child can have only one parent, so the employee must be duplicated (redundancy, inconsistency) or virtual pointers used. Relational adapts by adding a REPORTS_TO(EmpID, ManagerID) table (M:N) — no program needing EMP alone breaks if a view keeps the old shape (logical data independence).
P84 marks

Trace what happens inside the DBMS, component by component, when a clerk runs UPDATE account SET balance = balance - 500 WHERE acc_no = 101; followed by COMMIT, and the power fails one second after COMMIT returns.

Answer outline
  1. Query tool sends the statement → DML compiler parses, checks against the data dictionary, optimiser chooses the index on acc_no (uses statistics) → plan to the query evaluation engine.
  2. Authorization manager checks the clerk has UPDATE privilege; integrity manager checks constraints (e.g. CHECK balance ≥ 0).
  3. Transaction manager starts the transaction, takes an exclusive lock on the row (concurrency control), writes a log record (old and new value).
  4. Buffer manager brings the page into memory (via the file manager), the value is changed in the buffer.
  5. COMMIT: log records are forced to disk (write-ahead logging), lock released, “success” returned. The data page itself may still be only in memory.
  6. Power fails → on restart the recovery manager redoes the committed update from the log → durability. If the failure had been before COMMIT, it would undo it → atomicity.
